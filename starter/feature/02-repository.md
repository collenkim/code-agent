# [feature 02] Repository

> **선행**: [01] Entity · **다음**: [03] Command · Query 처리
> **근거**: 참조 표준 도메인의 `repository/`

## 0. 사용법

참조 표준의 Repository 가 **어떤 조회를 어떤 모양으로 선언하는지**를 이 도메인에 옮긴다.
스펙의 유스케이스가 요구하는 조회만 만든다 — "있으면 편할" 메서드를 미리 만들지 않는다.

**do-not-touch**: `outputDirs` 밖에 파일을 만들지 않는다. 엔티티를 고쳐야 한다면 만들지 말고 `note`.

## 1. 입력 게이트

- [ ] [01] 산출물이 「앞 단계에서 이미 만든 파일」에 실려 있다
- [ ] 스펙에 유스케이스 목록이 있다 — 조회 메서드는 여기서만 나온다. 없으면 `ask`
- [ ] 참조 표준 Repository 가 실려 있다

## 2. 규칙 게이트

| 규칙 | 근거 | 위반 시 |
|---|---|---|
| 기반 인터페이스·제네릭 인자·어노테이션은 참조 표준과 같다 | 참조 표준 Repository | 무효 |
| 단건 조회의 조건(테넌트·삭제 표시 등)은 참조 표준의 단건 조회와 **같은 조건 집합**이다 | 참조 표준 | 무효 |
| 스펙의 유스케이스에 대응하지 않는 조회 메서드를 만들지 않는다 | 스펙 | 무효 |
| 다른 도메인의 Repository 를 만들거나 고치지 않는다 | 경계 | 무효 |

## 3. 작업 — 스켈레톤

1. 참조 표준 Repository 의 선언부를 그대로 가져와 타입 인자만 [01] 의 엔티티로 바꾼다
2. 참조 표준의 **단건 조회**를 찾아 조건 집합을 확인하고, 같은 조건으로 이 도메인의 단건 조회를 만든다
3. 스펙의 유스케이스마다 필요한 목록·검색 조회를 참조 표준의 같은 성격 메서드 모양으로 만든다
4. 참조 표준에 없는 조회 방식(네이티브 쿼리·별도 구현체 등)이 필요하면 만들지 말고 `ask`

## 4. 자가검증 체크리스트

- [ ] 만든 파일이 계획의 목록과 같은가
- [ ] 단건 조회 조건이 참조 표준의 것과 같은 항목으로 구성되는가
- [ ] 모든 조회 메서드가 스펙의 유스케이스 하나로 되짚어지는가
- [ ] 참조 표준에 없는 어노테이션·기반 타입을 들이지 않았는가

## 5. 산출물 → 다음 단계 입력

- **산출물**: Repository
- **[03] 입력**: 조회 메서드 이름 — 처리 계층이 이것만 부른다
