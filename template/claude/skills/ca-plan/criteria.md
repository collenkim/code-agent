# ⑤ plan.json · ⑦ 07-test-spec.md 작성과 독립 검토 기준

## plan.json

참조 도메인의 파일 구조를 따르고, 없는 파일을 발명하지 않는다.

- `files[]` — 파일마다 `requirements` 에 담당 R 번호. 어느 파일에도 닿지 않는 항목이 있으면 제출이 거부된다.
- `sequence[]` — 실행할 단계 key를 순서대로, 파일이 있는 단계를 정확히 한 번씩 쓴다. **이 순서대로 실제 실행된다.**
  의존 관계를 지키고 02의 Risk가 큰 것을 먼저 배치한다. 파일 묶음의 임의 이름은 받지 않는다.
- `tasks[]` — `{ "id":"T1", "stage":"단계 키", "title":"구체적 작업", "requirements":["R1"], "files":["src/a.ts"], "dependsOn":[], "acceptance":["AC-R1-1"] }`.
  파일 소유자는 정확히 하나, 의존성은 앞 Task, 순서는 sequence를 따른다. 같은 단계에 여러 Task를 둘 수 있다. 실제 완료는 구현 후 검증·리뷰로 판정한다.
- `approach` — 구현 방법 한 문단: 03 의 설계를 어떤 방식으로 옮기는가(기존 것을 확장 / 새로 만들고 갈아끼움).
- 신규라면 실행 가능한 소스 뼈대·진입점·필요한 실행 설정·테스트를 기존 단계의 Task에 포함한다. 외부 의존성이 있으면 기존 패키지 관리자의 준비 명령과 잠금 파일도 계획한다. 도구가 정해져 있으면 그대로 사용하고 다시 선택시키지 않는다.
- **`fix`** — `sequence[0]` 은 `kind: "test"` 단계여야 하고, `files[]` 에 그 단계의 파일(재현 테스트)이 있어야 한다. 둘 중 하나라도 없으면 제출이 거부된다.
  그 단계에 적는 파일은 **그 단계가 밝힌 테스트 자리 안**이어야 한다 — 고칠 파일을 거기 적으면 거부된다.
- **`refactor`** — 지시서의 preserve 문장을 그대로 옮긴다. **기준 커밋에 이미 있던 `kind: "test"` 단계의 파일은 `files[]` 에 넣을 수 없다** —
  동작이 보존되는지 보는 것이 그 테스트다. 고쳐야 할 이유가 보이면 질문으로 낸다.
- openQuestions 가 남아 있으면 제출되지 않는다 — 질문으로 낸다.

## 07-test-spec.md — 구현 전에 쓴다

구현을 보고 쓰면 구현을 베낀 테스트가 된다.

- `테스트 케이스` 표: `TC-<n>` | 수준(Unit/Integration/E2E) | 대상 AC | 케이스 | 기대 결과
- **04 의 모든 AC 가 최소 한 TC 에 걸린다.** TC id 는 중복 없이. 수준은 테스트 전략 문서를 따르고, 올리거나 내리면 `안 하는 것` 에 근거를 단다.
- AC 하나당 정상 1 + 04 의 `예외` 에서 온 실패 경로 n 으로 기계적으로 출발한다.
- 실패 경로 TC도 최종 실행 결과는 passed여야 한다. 해당 요구의 잘못된 입력·경계값·권한 거부·외부 실패에 대해 예상 오류뿐 아니라 저장 상태·외부 호출 등 바뀌면 안 되는 결과를 단언하도록 정의한다. 해당하지 않는 경우는 근거를 적고 불필요한 TC를 발명하지 않는다.
- `02`가 지목한 기존 기능·호출자·공유 모듈의 회귀 위험을 기존 테스트 또는 승인할 새 TC에 연결한다. 필수 회귀 테스트가 없는데 영향 없음으로 처리하지 않는다. 설정된 전체 테스트 명령은 유지하고 이번 변경 테스트만 실행하는 명령으로 좁히지 않는다.
- **TC 표에는 실제 실행할 테스트만 넣는다.** 언어·도구 선택, 파일 범위, 기존 테스트 보존, 코드 스타일을 ‘실행하지 않는 TC’로 만들지 않는다. 이런 제약은 계획·check·보존 검사·리뷰의 확인 항목에 기록하고 해당 기능의 AC/TC와 함께 추적한다. `안 하는 것`에 적었다고 TC 표의 실행 의무가 사라지지 않는다.
- **refactor는 기존 테스트 이름의 TC ID와 케이스를 먼저 확인해 재사용한다.** 기존 테스트를 수정할 수 없는데 명세에 새 ID만 만들어 두지 않는다. 새 동작 테스트가 꼭 필요하면 허용된 범위의 새 파일을 계획하거나 범위 변경을 명확히 알린다.
- **`fix` 는 `## 재현` 절이 필수다** — 결함을 재현하는 TC id 를 `- TC-1` 로 한 줄씩. 수준은 무엇이든 되고, 적은 id 는 표에 실재해야 한다.
  여기 적힌 TC 는 `code-agent repro` 가 **지금 코드에서 실패하는 것을 보기 전에는** 고칠 파일을 쓸 수 없게 만든다.
  지시서에 `## 오류 로그` 가 있고 그 발생 조건을 로컬에서 만들 수 없으면 `- 방식: 로그 근거 — <사유>` 줄을 더한다 — 그 TC 는 로그의 입력·상태를 담은 회귀 TC 로, 수정 전 실패를 요구하지 않고 수정 후 통과해야 한다. 로그가 없는 지시서는 로그 근거로 계획할 수 없다.

## 독립 검토 (critic)

초안, `01`~`04`, `07-test-spec.md`, 아키텍처·컨벤션·테스트 전략, 참조 표준 파일, 원문 지시서와 원문 대조를 근거로 반박 검토한다.
요구사항 적합성 검토는 요구·AC·예정 TC의 대응을 읽는 검토다. 이 단계에서 코드를 실행하거나 테스트 도구 적합성 검증을 추가하지 않는다. 정리 과정의 의미 누락·임의 제외를 확인한다.

필수 문서에 확인 필요·TODO·TBD가 남으면 전환이 막힌다. 근거 파일과 줄이 실재해야 하고 AC에는 구체적 내용, BR에는 실제 파일:줄 또는 답변된 Q 번호가 있어야 한다. 이는 형식·근거 검사이며 내용의 타당성은 critic과 사용자 승인이 판단한다.
