# ② 영향도 조사와 02-analysis.md 작성 기준

**공통 KNOWLEDGE 는 단서다.** `doc/knowledge/` 의 데이터 사전 · API 목록 · 업무 규칙·용어집에
이번 요구가 닿는 키가 있어도 **현재 코드와 호출자 영향을 조사하고 근거를 확인한 뒤 인용한다** — 키와 그것에 기대는 사실 한 줄을 옮겨 적고 차이만 쓴다.
검증되지 않은 기존 지식을 확정 사실로 쓰지 않는다. KNOWLEDGE 파일은 쓰지 않는다 — 갱신은 반영(deliver)에서 사람이 고른다.

- `기존 시스템 분석` — 닿는 파일·모듈이 지금 하는 일, 근거는 `path:line`.
  **`fix`·`refactor` 는 여기가 게이트다** — `해당 없음` 으로 비울 수 없고 근거 `path:line` 이 최소 하나 있어야 `code-agent next` 가 넘어간다.
  `fix` 는 **결함이 나는 경로**를, `refactor` 는 **지금 동작**을 적는다.
- `영향 범위` — 표: `R 번호 | 닿는 파일/모듈 | 부르는 곳 | 파급`. **01 의 모든 R 이 한 줄 이상.** 영향이 없으면 근거와 함께 `없음`
- `Risk` — 깨뜨릴 수 있는 기존 기능·호출자·공유 데이터와 원인·완화를 `path:line` 근거로 적는다. 외부 계약·오류 처리·저장 상태·공통 설정 중 실제 변경이 닿는 곳을 확인한다. 필요한 회귀 케이스와 읽어야 할 관련 파일 경로도 남겨 계획·리뷰로 넘긴다. 영향 없음은 근거가 있을 때만 쓰고, 확인하지 못한 것은 아래 규칙대로 처리한다 — 영향이 없다고 단정하지 않는다.
- 모호한 점은 나눈다 — 업무 규칙·범위는 질문으로 내고, 기본값을 댈 수 있는 기술 세부는 `01-requirements.md` 의 `## 가정` 에 더할 내용으로 근거와 함께 적는다.

**완료 문서에는 `확인 필요`·TODO·TBD를 남기지 않는다** — 남으면 다음 단계로 넘어가지 못한다. 사람이 정할 것은 질문으로 내고, 조사로 확인하지 못한 기술 범위는 `조사 한계`처럼 사실 그대로 적는다(이전 버전 작업의 writer는 메인이 질문으로 돌릴 수 있게 목록으로 돌려준다).
