`.claude/skills/ca-feature/SKILL.md` 의 절차를 그대로 따른다 — 같은 단계 스킬을 같은 순서로 돈다.
다른 점은 아래 넷이고, **전부 코드가 막는다** (지시가 아니다).

- **영향도 (`/ca-impact`)**: `02-analysis.md` 의 `기존 시스템 분석` 은 **결함이 나는 경로까지** 적는다 — 증상이 어느 코드 경로에서 나는지.
  `해당 없음` 으로 비울 수 없고 근거 `path:line` 이 최소 하나 있어야 `code-agent next` 가 넘어간다.
- **테스트 명세 (`/ca-plan`)**: `07-test-spec.md` 에 `## 재현` 절을 두고 결함을 재현하는 TC id 를 `- TC-1` 로 한 줄씩 적는다.
  거기 적은 id 는 `테스트 케이스` 표에 실재해야 하고, **수준(Unit/Integration/E2E)은 무엇이든 된다.** 없으면 `plan submit` 이 거부한다.
- **계획 (`/ca-plan`)**: `sequence[0]` 은 `kind: "test"` 단계여야 하고, `files[]` 에 그 단계의 파일이 있어야 한다.
  그 단계에 적는 파일은 **그 단계가 밝힌 테스트 자리 안**이어야 한다 (`code-agent context` 가 그 자리를 찍어 준다) —
  고칠 파일을 테스트 단계에 적어 넣는 계획은 거부된다. '재현 먼저' 를 단계 이름표로 재기 때문이다.
  고칠 파일은 지시서의 scope 안에서만, 보존 조건(preserve)은 문장 그대로 옮긴다.
- **구현 (`/ca-implement`)**: 커서가 **테스트 단계에 먼저** 선다. 재현 테스트를 쓰고 Bash: `code-agent repro` —
  지금 코드에서 그 TC 가 **실패**하는 것을 본 뒤에야 hook 이 고칠 파일 쓰기를 연다.
  고치고 나서 쓴 테스트는 결함을 재현한 적이 없다. 재현을 본 순간 `kind: "test"` 단계의 파일은 **언다**
  (단언을 약하게 하면 재현이 증거가 아니게 된다). 고친 뒤 `check` → `test` 에서 **같은 TC 가 이제 통과**해야 끝난다.

**재현 테스트의 이름에 TC id 를 남긴다** (컨벤션의 `테스트 규칙`). `code-agent repro` 는 재현 TC id 가 **실패한 그 실행의 출력**에
찍혀야 인정한다 — 파일에 적어 둔 id 는 세지 않는다. 파일을 grep 한 것은 *무엇이* 실패했는지 말해 주지 않아, 다른 TC 의 실패도
깨진 import 도 같은 `failed` 로 보이기 때문이다.

원인을 확신할 수 없으면 추정으로 계획하지 않고 `questions.md` 에 가설과 확인 방법을 질문으로 남긴다.
`code-agent repro` 가 `재현하지 못했습니다` 로 끝나면 고치지 말고 그대로 보고한다 — 재현하지 못한 결함은 고쳤는지 알 수 없다.
`재현 TC 가 실패한 실행의 출력에 없습니다` 도 같다 — 테스트 이름에 id 를 넣어 다시 돌리거나, 그래도 안 되면 보고한다.
