**질문·동의** — 사람에게 묻거나 승인·확정·반영을 받기 직전에 `.claude/skills/ca-answer/SKILL.md`를 읽고 그 절차(`AskUserQuestion`·같은 세션 동의)를 따른다. 일반 답변은 승인이 아니며, 적용 뒤에는 이 흐름을 자동으로 이어간다.

너는 **메인 에이전트**다. `code-agent` 가 거부하면 **사유를 그대로 전하고 멈춘다.**
검증 결과는 **네가 보고하는 것이 아니라 명령이 돌아서 남은 것만** 유효하다.

**자리 확인** — Bash: `code-agent status`. 스테이지가 `check` 가 아니면 **멈춘다.**
아직 이르면 status 의 `다음:` 줄이 가리키는 명령을 먼저 하라고 전하고, 이미 지났으면 `code-agent back check` 로
되감아야 한다고 전한다 — 무엇이 무효가 되는지는 그 명령이 찍는다. **되감기는 사용자가 되돌리라고 말했을 때만** 돌린다.
(`test` · `review` · `integrate` 에서 검증이 실패해 돌아오는 길은 되감기가 아니다 — `code-agent check` 가 커서를 이 자리로 데려온다.)

## 하는 일

**전체 작업 흐름에서는** 계획된 테스트 작성이 끝난 상태에서 Bash: `code-agent verify --json`을 호출한다. CLI가 `check → 결과 판정 → test → 결과 판정`을 연속 실행하고 기존 게이트를 통과하면 `review`까지 이동한다. 아래 단일 단계 명령을 중복 실행하지 않는다.

- `node: review` — `/ca-review` 절차로 이어간다. `next`를 추가 호출하지 않는다.
- `node: repair` — 반환된 `problems`, `evidence`, `plannedFiles`를 근거로 아래 수정 루프를 수행하고 `code-agent verify --json`으로 재검증한다.
- `node: diagnose` — 미실행·실행 오류·TC 결과 미확인 원인을 확인한다. 환경·결과 수집 문제를 해결한 뒤 `code-agent verify --json --retry`로 check부터 다시 실행한다. 변경 없는 실패를 자동 반복하지 않는다. 실행 기록의 `환경 오류:` 줄은 `code-agent.json`의 `environmentErrors`에 맞은 실패다 — 코드를 고치지 말고 환경(Docker·DB 등)을 사용자에게 확인받는다. 코드를 그대로 둔 재실행은 회차를 쓰지 않는다. 같은 환경 실패가 반복되는데 선언이 없으면 사용자에게 그 문구의 선언을 제안한다(직접 고치지 않는다).
- `node: decision` — 한도를 사용했다. 아래 질문·재계획·재승인 절차로 연결한다. 이 응답 자체는 승인이나 사용자 답변이 아니다.
- 명령 자체가 거부되면 사유를 보고하고 멈춘다. 종료 코드 1과 유효한 노드 JSON은 인계 요청이며, JSON 없는 오류와 구분한다.
- 검증은 빌드·전체 테스트라 오래 걸릴 수 있다. Bash 도구의 timeout 을 최대(600000ms)로 주고, 그보다 긴 저장소는 백그라운드 실행(`run_in_background`) 뒤 완료 알림을 기다린다. 도중에 끊겨 실행 기록이 없는 회차는 코드를 고치지 않았다면 같은 회차로 다시 돈다 — 고쳐 쓰기 한도를 쓰지 않는다.

**정적 검증 단계만 요청받았으면** 기존 명령을 사용한다:

1. Bash: `code-agent check` — `build` 와 품질·보안 기준이 적은 명령을 돌려 증거(`.code-agent/work/<ID>/<대상>.verify.json`)에 적고 ⑧ `08-validation.md` 를 렌더한다.
   전체 로그는 `.code-agent/log/` 에 남고 출력에는 요약과 실패 꼬리만 나온다. 네가 직접 돌린 빌드는 게이트를 열지 못한다.
2. 실패가 있으면 아래 **↺ 수정 루프**.

## 끝

전부 통과면 Bash: `code-agent next` — 거부되면 사유를 그대로 전하고 멈춘다.
통과하면 무엇이 몇 회차에서 통과했는지 짧게 보고한다. 전체 작업 흐름에서는 `/ca-test` 절차로 자동으로 이어가고, 정적 검증 단계만 요청받았으면 여기서 마친다.

## ↺ 수정 루프

`check` · `test` · `review` · `integrate` 가 함께 쓴다. 회차는 **코드가 센다** (`code-agent.json` 의 `fixRounds`, 기본 2):

1. 실패·지적마다 어느 **계획 파일**의 문제인지 가른다. `code-agent context` 가 준 계획 파일 목록이 기준이고, 네 기억이 아니다.
2. **계획 안** — `ca-implementer` 에게 파일별로 맡긴다. 무엇이 왜 실패했는지(명령 · outcome · 로그 **경로**)와 고칠 파일만 넘긴다.
   끝나면 **`code-agent check` 부터 다시** 돈다 — 중간부터 잇지 않는다. `check` 는 `test` · `review` · `integrate` 어디서 불러도
   커서를 그 자리로 되감으므로, 스테이지를 되돌리려고 따로 할 일은 없다 (`code-agent back` 도 필요 없다). 그 뒤 `next` 로 같은 게이트를 다시 전부 지난다. 전체 흐름에서는 `code-agent verify --json`이 이 check·test 실행과 게이트 전이를 대신 수행한다.
3. **계획 밖** — 고치지 않는다. `questions.md`에 기록하고 공통 선택 절차로 처리 방향을 받는다. 범위를 넓히기로 답했어도 그 일반 답변을 승인으로 적용하지 않는다. 구현은 멈추고 재계획·재승인(`plan submit` → `plan` 공통 동의 절차)으로 연결한다. 승인된 동의 적용 후 검증 흐름을 이어간다. 필요한 답이 없으면 미응답으로 남긴다.
4. 얼어 있는 테스트 파일(`kind: test` 단계)은 기본적으로 수정할 수 없다. 범위는 동결 여부와 무관하게 계획 파일 목록으로 정한다.
   `review` 단계에서 독립 리뷰어의 실행·결과가 기록된 `계획 안` 지적이 해당 파일을 가리킬 때만 수정할 수 있다. 승인된 AC는 유지하고, 수정 뒤 `check`부터 재검증·재리뷰한다.
   이 조건이 없으면 근거와 함께 보고한다. 요구사항·AC 변경은 재승인이 필요하다.
   `fix` 는 `code-agent repro` 가 재현을 본 순간부터 언다 (테스트가 한 번 돌기 전이라도).
   리뷰 지적으로 fix 테스트를 보완하면 다음 `check`가 기준 코드 + 수정 테스트의 격리 재현을 자동 갱신한다. 작업 코드를 되돌리지 않는다. 기준 코드에서도 통과해 버린 테스트는 보완을 요구하며, 재현 갱신 후 수정 코드의 check·test·독립 리뷰를 다시 거친다.
   `refactor` 는 **기준 커밋에 이미 있던** 테스트 파일이 처음부터 잠겨 있다 — 그것이 깨졌다면 고칠 것은 테스트가 아니라 리팩토링한 코드다.
5. 한도를 넘기면 hook 이 계획 파일 쓰기를 전부 거부한다. **덮지 않는다** — 무엇이 몇 회차에서 왜 막혔는지 사용자에게 보고하고 **멈춘다.**
