# code-agent 사용성·실행 순서·요구사항 추적 보완

2026-10-01 후속 수정. [최초 검토](2026-10-01-process-review.md)의 사용성 부족, 계획과 실행 순서 불일치, 요구사항 추적 공백을 대상으로 한다. 이 문서는 변경 후 동작을 설명하며 최초 관찰 결과는 별도로 보존한다.

**후속 상태:** 아래에서 미해결로 남긴 F2·F5·F6과 실제 모델 검증은 [검증·리뷰 후속 보완](2026-10-01-validation-review-improvements.md)에서 이어서 처리했다. 아래 테스트 수치는 이 문서 작성 당시의 기록이다.

## 계획대로 했는데 순서가 달라진 이유

기존 구현은 승인 화면의 순서를 `plan.json.sequence`에서 읽었지만, 실제 구현 순서는 매니페스트의 `stages`에서 다시 만들었다. 계획이 `test → code`여도 매니페스트가 `code → test`이면 기능 개발에서 실제로 후자 순서로 진행했다. 에이전트가 상황을 판단해 계획을 바꾼 것이 아니라 **서로 다른 데이터를 실행 기준으로 삼은 결함**이다.

이제 승인 화면·Task·실행 커서가 같은 `sequence`를 사용한다. 매니페스트는 단계의 정의와 파일 경계를 제공한다. 순서가 잘못됐으면 임의 정렬하지 않고 제출을 거부한다. 승인 후 순서를 수정하면 기존 승인이 무효이며, 재승인 전에는 다음 구현 단계로 이동하지 못한다.

## 변경 결과

| 요청 | 이전 | 변경 후 | 근거 |
|---|---|---|---|
| 요구사항부터 시작 | 설정이 없으면 접수 불가, 접수 중 문서 준비 불가 | 설정 없이 ID·원문 접수 → 문서 준비 → 같은 접수로 복귀 | `request.ts`, `docsCommands.ts`, ca-request/ca-next |
| 쉬운 초기 선택 | 세부 기술·문서별 선택 반복 | 신규는 웹·API(JavaScript), 자동화(Python), 직접 선택. 기존은 설정 재사용, 부족한 부분만 준비 | `setup.ts`, ca-adopt/ca-docs |
| ID·문서 확인 부담 | ID 입력 필수, POLICY 개별 확인 4회 | ID 생략 시 WORK 번호 자동 발급, `confirm doc all` 1회. 확인 도중 내용 변경 시 기록하지 않음 | `requestBegin`, `confirmDoc` |
| 계획과 실행 일치 | 승인 순서와 실행 순서가 별개 | 파일이 있는 단계 각각 1회, 누락·중복·알 수 없는 단계·빈 이유 차단. fix는 테스트 먼저 | `sequenceProblems`, `plannedStages`, `next` |
| 원 요구 누락 방지 | 분석에 적힌 R만 이후 검사 | 확정 요구·완료 조건·제약을 REQ/DONE/CON으로 식별하고 R의 출처·인용과 전량 대조 | `sourceTrace.ts`, `requireRequirements` |
| 요구별 Task | R→계획 파일만 연결 | sequence·파일에서 T1… 자동 생성. R·파일·순서·완료 기준·진행 상태 표시 | `planTasks`, `formatPlan`, `status` |
| 판단하기 쉬운 보고 | R→AC→파일→TC 중심 | 접수 요구→R 표 + Task 목록 + 기존 AC·TC·검증 결과. 코드가 생성하는 보고 영역에 포함 | `renderTraceBlock`, `deliverProblems` |

Task는 구현 단계 단위다. 한 요구가 여러 Task에 걸치거나 여러 요구가 같은 Task에 묶일 수 있다. 별도 Task 원본을 중복 저장하지 않고 승인된 계획에서 생성하며, 파일 작성·검증·최종 반영 상태를 구분한다.

## 사용자 흐름

1. `/ca-feature "원하는 기능"`으로 시작한다. 버그 수정은 `/ca-fix`, 동작을 보존하는 구조 개선은 `/ca-refactor`다. 기존 기능 확장은 feature를 쓴다.
2. 준비가 필요하면 목적에 맞는 추천 구성을 선택한다. 에이전트가 공통 문서·설정을 만들고, 사용자는 내용을 읽고 `code-agent confirm doc all`로 확인한다. 설정이 이미 갖춰져 있으면 생략한다.
3. 정리된 요구를 `confirm request <ID>`로 확정한다. `/ca-next`가 분석·영향도·설계·Task 계획을 작성한다. 업무 규칙·범위 등 필요한 질문만 받는다.
4. `code-agent approve`로 계획을 승인한다. `/ca-next`가 계획 순서대로 구현·검증·리뷰·통합을 수행한다.
5. 완료 보고를 보고 `code-agent deliver`로 로컬 반영한다.

일반 작업의 사람 판정은 **요구사항 확정·계획 승인·반영 확인 3회**를 유지한다. 최초 준비 때는 추천 선택과 공통 문서 확인이 더해진다. 모호한 요구, 검증 실패, 계획 변경에는 추가 상호작용이 필요하다. Git 기준 커밋이 전혀 없는 저장소는 준비 파일의 최초 커밋이 필요하다.

추천 설정은 경량 시작점이다. 준비 단계에서는 문서·설정·단계 규칙을 만들며 실제 애플리케이션 소스와 테스트는 승인된 Task에서 작성한다. 기존 프로젝트에는 신규 설정을 덮어쓰지 않는다. 기술 선택을 모르면 기본안과 이유를 제시하되 업무 규칙을 임의로 결정하지 않는다.

## 검증과 한계

회귀 테스트는 [process.test.ts](../../src/test/process.test.ts)에 있다. 설정 없는 접수와 원문 유지, 신규 설정의 기존 파일 보호, 문서 일괄 확인의 변경 감지, 확정 요구의 누락·잘못된 인용 차단을 검사한다. 임시 Git 프로젝트에서는 승인한 test→code 순서, 재승인 없는 순서 변경 차단, 실제 Node 구문 검사·테스트·깨끗한 worktree 통합, 완료 보고까지 검사한다. Python 추천 명령도 실제 구문 오류·TC 실행과 계획 밖 캐시 미생성을 검사한다.

| 검증 | 결과 |
|---|---|
| 최종 `npm test` (컴파일 포함) | **529개 중 525 통과, 실패 0, 건너뜀 4** · 120 suites · 약 357초 |
| 추가 흐름 테스트 단독 실행 | **7개 모두 통과** · Python 실제 실행 포함 |
| `git diff --check` | 통과 |
| 건너뜀 | 기존과 동일: 대소문자 구분 관련 2개, Windows 파일 권한 관련 2개 |

최종 전체 실행은 Python 명령·여러 줄 요구사항·비교 연산자 누락 검사까지 반영한 작업 트리를 대상으로 했다. [검증 집계](evidence/process-fix-test-summary.json)에 명령과 수치를 보존했다. 상세 로컬 로그는 `dist/process-fix-complete-tests.log`에 있다. 제품 코드와 테스트는 수정했으며 아직 커밋·배포하지 않았다.

- 승인과 리뷰 내용은 테스트 fixture다. 실제 Claude Code가 코드를 생성하거나 독립 리뷰어가 수행한 결과를 검증한 것으로 보지 않는다. 초보자의 실제 질문 횟수·완주율은 아직 측정하지 않았다.
- 자동 추적의 기준은 **사람이 확정한 요구 내용·완료 조건·제약**이다. 원문을 정리하는 과정의 의미 누락이나, 인용했지만 실제로 구현하지 않은 동작까지 문자열 대조로 증명하지는 않는다. 사람의 요구 확정과 AC·TC·리뷰가 함께 필요하다.
- 최초 검토의 TC skip 통과 문제(F2), 동결 테스트에 대한 리뷰 범위 계약(F5), 독립 리뷰 실행 증명(F6)은 이번 변경에 포함하지 않았다. 이 수정만으로 전체 코드 생성·리뷰 품질이 완성됐다고 판단하지 않는다.
- 이미 설치된 프로젝트의 스킬에는 배포 후 `code-agent update`가 필요하다. 새 CLI 소스·템플릿은 수정했으며, 외부 프로젝트 설치본이나 배포된 바이너리는 변경하지 않았다.
