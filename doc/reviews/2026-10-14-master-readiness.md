# 상위 조정자·러너 연결 준비 — 작업 경험·발견 보고·상태 조회 (2026-10-14)

`(이 커밋)`의 변경 경위와 검증 결과다. 현재 동작은 [프로세스 흐름도](../process-flow.md) §3.2·§5.3·§5.4·§8·§9, [사용 가이드](../usage.md) 5절, [설계](../design.md) §1 '외부 실행기와의 경계'·§2.6 이 정본이다.

## 요청

기존 개발 절차를 유지하면서 나중에 상위 조정자(master-agent)가 연결할 수 있게 — 프로젝트 작업 경험 기록·검색, 진행 중 발견의 구조화 보고, 상태·증거·재개를 읽는 버전 있는 기계 판독 계약. master-agent·LangGraph·조직 UI·Jira·Notion 연동·원격 push·PR·배포는 만들지 않고, master 없이 CLI 와 두 호스트에서 단독으로 동작해야 한다. 측정하지 않은 개선율은 주장하지 않는다.

## 기존 기능 판정

현재 브랜치(`53e81d4`)의 코드로 다시 확인한 판정이다.

| 요구 | 판정 | 근거·처리 |
|---|---|---|
| 경험 기록(문제·환경·시도·원인·해결·근거·조건, ID·버전) | 확장 | 새 선택 기록 `doc/work/<ID>/experience.md` — KNOWLEDGE 종류에 넣지 않았다 |
| 경험 검색, 정책과 구분 | 확장(재사용) | `knowledgeIndex` 의 낱말 분해·최신성 계산·`knowledge find`·`context` 참고 문서 절을 그대로 쓰고 경험은 따로 센다 |
| 경험 → 정책 | 기존 충족 | `knowledge.proposal.md` → `deliver` 동의의 항목 선택 |
| 발견 보고 | 확장 | `.code-agent/work/<ID>/findings.json` · `finding report·list` |
| 분류 a·b 의 처리 | 기존 충족 | a — `check` 수정 루프와 원인별 한도, b — `back plan` 재계획·재승인 |
| 분류 c·d | 확장(보고만) | 외부 조정 보고·후속 후보. 다른 저장소 수정·새 권한 없음 |
| 버전 있는 상태 조회 | 확장 | `status --json`(스키마 `code-agent.state` v1) |
| 승인·무효 원인·재시도 사용량·검증 묶임 | 기존 충족(노출만) | `approvalOf`·`staleEarliest`·`retrySummary`·`verifyView` 를 그대로 부른다 |
| 재개 코드·오래된 요청 거부 | 확장 | `nextHint` 판정 순서를 고정 코드로, `--expect-*` 대조 |
| 같은 요청 중복·이전 시도의 늦은 결과 | 기존 충족 | 계획 배정의 `dispatchId` 대조(취소·교체 배정의 늦은 결과는 되돌리지 않고 늦은 결과로만), 끝맺지 못한 동의 적용은 다시 돌리지 않음(`applyLocked`). 상태 조회는 그 자리를 알리기만 한다 |
| 프로세스 생존·로그·종료·취소·실행 소유권 | 러너 책임 | 상태 조회는 `ownership.process: "unverified"` 로 비워 둔다 |
| 조직 권한·배정·전체 DAG·예산·서비스 간 승인·전체 복구 | master 책임 | 만들지 않았다 |

계획 작업의 시도 기록·고아 판정·승인 무효화·재시도 한도·재진입 안내는 이미 있었다. 이를 전체 실행의 복구 보장으로 넓히지 않았고 같은 판정을 다시 구현하지 않았다 — 상태 조회는 그 함수들을 부른다.

## 정한 것과 대안

이어서 진행하라는 지시에 따라 아래는 묻지 않고 기본값으로 정했다. 업무 정책이나 파괴적인 상태 이행은 아니다.

| 결정 | 고른 것 | 대안과 고르지 않은 이유 |
|---|---|---|
| 경험 기록의 자리 | 원래 작업 폴더의 선택 파일 `experience.md` | KNOWLEDGE 6번째 문서 — 정본(현재 동작·확정 정책)과 당시 관찰이 한 문서에 섞이고 반영마다 사람 선택이 필요해진다. `.code-agent/` — 사람이 읽고 리뷰할 수 없다 |
| 경험 ID·수정 | `EXP-<작업 ID>-<순번>`, 지난 작업 폴더는 고치지 않고 뒤 작업이 같은 ID 의 버전 +1 | 전역 순번 — 병렬 작업의 반영이 같은 번호를 낼 수 있다. 원래 파일 수정 — 반영된 작업 폴더(이력)를 바꾸게 된다 |
| `검증됨` 판정 | 그 버전을 쓴 작업의 `verify.json` 에서 그 단계 마지막 회차가 모두 통과 | 모델 선언 — 요구가 금지. 사람 확인 동의 추가 — 별도 승인 단계를 늘린다 |
| 발견의 자리·정체 | 코드만 쓰는 `findings.json`, ID 는 작업·분류·제목·근거 목록의 해시 | 작업 폴더 마크다운 — 버전 대조·중복 판정을 모델 쓰기와 함께 지킬 수 없다. 제목만 해시 — 근거가 다른 발견을 하나로 합친다 |
| 상태 인터페이스 | 기존 `status` 의 `--json` | 별도 어댑터 명령 — 같은 판정의 두 번째 진입점이 생긴다 |
| 직접 재개 명령 | 두지 않는다 | 재개 실행기 — 기존 명령·동의 경로가 이미 승인·임대·한도를 확인하고, 상태·승인 파일을 고쳐 잇는 길을 만들 위험이 있다. 실행 직전 `--expect-*` 대조로 오래된 요청을 거른다 |
| 초안 자리 | `doc/work/<ID>/{experience,finding}.draft.json` 고정, 기록 뒤 삭제, 반영 커밋에서 제외 | 아무 경로 — 저장소 루트 초안이 계획 밖 변경으로 잡혔다(아래). 제외하지 않음 — 거부된 초안의 비밀 값이 반영 커밋에 들어갈 수 있다 |

## 구현

- `sensitiveText.ts` — 경험·발견이 쓰기 전에 지나는 검사. 개인 키·AWS 접근 키·GitHub·Slack 토큰·`sk-` 키·JWT·인증 헤더·URL 계정 정보·비밀 값 대입과 6줄 넘는 칸·코드 블록. 걸린 값은 다시 출력하지 않는다.
- `experience.ts`·`experienceCommands.ts` — 초안 스키마(칸 길이 상한), ID·버전·중복(문제+원인+적용 조건) 판정, 같은 작업 안 갈아 끼우기, `revises`·`supersedes`, 상태(`검증 근거 없음`·`대체됨`·`버전 충돌` 포함), 최신성은 `knowledgeIndex` `freshness` 를 그대로(일반화만). 잠금 `experience.lock`.
- `findings.ts` — 분류·경로, 정체·버전·재전송·오래된 갱신, 닫을 때 `resolution`, d 의 차단 거부, `links` 존재 확인(⑨ 지적·질문·계획 배정), 관련 프로젝트 확인 규칙, 손상·모르는 버전에서 멈춤, `finding list --json`.
- `workAttempt.ts`·`stateView.ts` — 시도 식별자와 `status --json`. 판정 순서와 칸은 흐름도 §3.2·사용 가이드 5절.
- 연결 — `hook.ts` 모델 명령·임대 밖 읽기 목록·`experience.md` 쓰기 거부, `commands.ts` `status` 의 `발견:`·`작업 경험:` 줄, `contextRender.ts`·`knowledgeCommands.ts` 경험 절, `deliver.ts` 초안 제외, `ca-check` 수정 루프 3항·`ca-integrate` 3절 3항.

## 진행 중 고친 것

- 실제 CLI 확인에서 저장소 루트에 둔 초안이 `status` 의 계획 밖 변경으로 잡혔다 → 초안 자리를 작업 폴더로 정하고 기록 뒤 지운다(다른 자리 초안은 지우지 않는다).
- 비밀 값 때문에 거부된 초안은 남겨 고치게 하는데, 작업 폴더째 커밋하는 반영이 그 초안을 담을 수 있었다 → `deliveryExcludes` 에 두 초안 자리를 넣었다(커밋·커밋 뒤 대조·동의 미리보기가 같은 규칙).
- `finding list --work` 의 값이 경로 조각으로 쓰였다 → 작업 ID 꼴만 받는다.
- 상태 조회의 `git status` 가 색인을 갱신할 수 있었다 → `GIT_OPTIONAL_LOCKS=0`.
- 손상된 승인 원장 시험이 마지막 줄만 바꿔 사슬 검사를 지나갔다(사슬은 다음 줄이 앞 줄을 묶는다) → JSON 이 아닌 줄을 덧붙여 시험한다.

## 확인하지 않은 것

- 실제 모델 세션 — Claude·Codex 가 수정 루프에서 발견을 남기고 반영 준비에서 경험을 고르는지(모델 행동)는 실행하지 않았다. 유료 평가가 필요하다.
- 실제 러너·상위 조정자와의 왕복 — 이 저장소에 없다. 계약은 단위 시험과 CLI 실행으로만 확인했다.
- 다른 PC 의 동의 적용·실행 중 배정의 프로세스 생존 — 상태 조회는 확인하지 않는다(러너 몫).
- 민감 정보 검사는 꼴 검사다 — 모든 자격 증명 형식을 잡는다고 확인하지 않았다.
- 대상 프로젝트 설치본 — `code-agent update --templates-only --host <호스트>`와 호스트 재시작 뒤에 템플릿 변경이 적용된다.

## 남은 일 — 상위 조정자·러너가 구현할 계약

- 러너: 실행 직전 `status --json --expect-state <v> --expect-work <ID> --expect-attempt <시도>` 재조회(종료 코드 3 이면 실행하지 않는다), `ready` 일 때만 기존 재개 경로로 모델 세션을 띄움, `ownership-conflict`·`wait` 의 프로세스 생존 확인과 사람 확인 뒤 `takeover`, 실행 로그·종료·취소, `--run-id` 로 실행 ID 상관관계.
- 상위 조정자: 저장소별 `status --json`·`finding list --json` 수집, `needs-human`·`reapproval-required`·`limit-reached`·`unobservable` 을 사람에게 연결, 분류 c 발견의 관련 프로젝트 확정과 서비스 간 조정, 재배정·PR 중복 방지·전체 복구. code-agent 의 승인은 그 저장소의 동의 절차로만 받는다 — 전달한 조직 ID·승인 문자열은 권한이 아니다.
