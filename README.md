# code-agent

**요구사항을 받아 코드를 작성하고, 테스트·리뷰를 거쳐 로컬 커밋까지 진행하는 Claude Code·Codex용 개발 에이전트입니다.** 신규 개발, 기존 기능 추가·변경, 버그 수정, 리팩토링을 지원합니다. 사용자는 원하는 동작을 설명하고, 필요한 업무 질문에 답하고, 요구사항·계획·최종 결과를 확인합니다.

code-agent는 **Claude Code와 Codex에서 실행하는 개발 절차**입니다. 별도 서버나 MCP 서버를 띄우지 않습니다. 호스트별 스킬·서브에이전트·훅을 설치하고 같은 프로젝트의 대화에서 요구사항을 전달합니다.

| 환경 | 설치 | 대화에서 시작 |
|---|---|---|
| Claude Code | `code-agent init --host claude` | `/ca-request <요구사항>` |
| Codex | `code-agent init --host codex` | `$ca-request <요구사항>` |
| 두 환경 함께 | `code-agent init --host both` | 사용할 호스트에서 시작 |

Codex는 설치 후 다시 열고 프로젝트 훅을 검토·신뢰해야 합니다. `code-agent doctor`와 `update`는 설치된 호스트를 인식합니다. Codex의 사용자 확인 방식과 지원 범위는 [Codex 연동](doc/codex.md)을 참고하세요. 아래 `/ca-*` 예시는 Claude 기준이며 Codex에서는 같은 이름의 `$ca-*` 스킬을 사용합니다.

## 무엇을 하는가

| 단계 | 에이전트가 하는 일 | 사용자가 하는 일 |
|---|---|---|
| 준비 | 요청 원문을 보관하고 공통 문서·프로젝트 설정을 확인합니다. 없으면 분석 전에 준비합니다. | 신규 프로젝트라면 추천 구성 또는 원하는 기술을 선택하고 공통 문서를 확인합니다. |
| 요구 확인 | 원문과 정리 내용을 대조하고 누락·범위·완료 조건을 확인합니다. | 필요한 업무 질문에 답하고 요구사항을 확정합니다. |
| 계획 확인 | 요구사항 분석, 영향도 조사, 설계, 작업 Task와 테스트 계획을 작성합니다. | 변경 범위·Task·실행 순서·검증 방법을 보고 계획을 승인합니다. |
| 개발·검증 | 승인된 순서로 코드·테스트를 작성하고 빌드·테스트·독립 리뷰·통합 검증을 수행합니다. | 계획 변경이나 해결할 수 없는 문제가 있을 때 판단합니다. |
| 결과 확인 | 요구사항별 결과, 변경 파일, 남은 위험과 되돌리기 방법을 정리합니다. | 결과를 확인하고 로컬 커밋을 승인합니다. |

기존 프로젝트의 언어·프레임워크·아키텍처·테스트 도구는 재사용합니다. 신규 프로젝트에는 웹·API용 JavaScript/Node.js, 자동화용 Python 또는 직접 선택을 안내합니다. 추천 구성에는 단일 애플리케이션 구조, 기능별 폴더·모듈, 기본 테스트 도구가 포함됩니다. 실제 소스와 테스트는 계획 승인 후 작성합니다.

일반 작업의 기본 판정 지점은 **요구사항 확정, 계획 승인, 결과 반영**입니다. Claude는 같은 화면의 선택 도구, Codex는 준비된 확인 메시지에 대한 실제 사용자 응답으로 확인합니다. 최초 준비에서는 POLICY 4종 확정과, 최초 Git 커밋이 없을 때 필요한 준비 파일의 기준 커밋을 `setup` 확인 하나로 묶습니다. 준비가 끝난 프로젝트에서 작업마다 반복하지 않으며, 공통 문서를 변경하면 다시 확인합니다. 업무 규칙이 모호하거나 계획 변경이 필요하면 추가 질문을 합니다.

완료 범위는 작업 브랜치의 **로컬 커밋**까지입니다. 원격 push, PR/MR 생성, 서비스 배포는 현재 자동 수행하지 않습니다.

## 동작 구조

```text
사용자 → 호스트의 ca-request 스킬 → 메인 에이전트가 단계별 스킬 실행
                                      ├─ 분석·조사·작성·테스트·리뷰 서브에이전트
                                      └─ 도구 호출 → hook → code-agent CLI 판정

호스트별 사용자 동의 → 초기 준비 · 요구사항 확정 · 계획 승인 · 결과 반영
프로젝트 파일 → 공통 문서 · 작업 문서 · 소스·테스트 · 상태·검증 증거
```

| 구성 | 역할 |
|---|---|
| Claude Code·Codex 메인 대화 | 현재 상태에 맞는 스킬을 읽고 개발을 진행합니다. 필요한 서브에이전트를 호출합니다. |
| 호스트별 스킬 18개 | Claude는 `.claude/skills/`, Codex는 `.agents/skills/`의 `ca-*/SKILL.md`에 접수·단계별 절차를 정의합니다. |
| 호스트별 서브에이전트 8개 | Claude는 `.claude/agents/ca-*.md`, Codex는 `.codex/agents/ca-*.toml`에 분석·조사·작성·구현·테스트·검토 역할을 정의합니다. |
| hook 등록 8개 | PreToolUse의 `hook` 1개, AskUserQuestion의 PreToolUse·PostToolUse `consent-event` 2개, Stop 1개, 리뷰어의 SubagentStart·SubagentStop `review-event` 2개입니다. 도구 경계, 실제 사용자 선택, 턴 종료, 독립 리뷰를 각각 관찰합니다. 분석·조사·설계·계획의 SubagentStart·SubagentStop `planning-event` 2개도 등록합니다. |
| `code-agent` CLI | 상태 전환, 승인·범위 검사, 검증 명령 실행, 증거 기록, 로컬 반영을 처리하고 종료합니다. 상주 서버가 아닙니다. |

위 8개 훅은 Claude 기준입니다. Codex는 도구 실행 전·사용자 메시지·서브 에이전트 시작과 종료·턴 종료의 5종 훅을 하나의 어댑터에 연결합니다.

`init`은 위 설정을 **설치만** 합니다. 호스트나 개발 작업을 자동으로 시작하지 않습니다. 설치한 프로젝트에서 사용할 호스트를 실행합니다. 별도 메인 에이전트를 등록할 필요는 없습니다.

단계 절차는 스킬에 있고, 승인·변경 범위·검증 결과의 통과 조건은 CLI와 hook이 검사합니다. hook은 모델의 실수를 줄이는 장치이며 로컬 사용자를 통제하는 보안 경계는 아닙니다. Claude Code의 프로젝트 스킬 방식은 [공식 스킬 문서](https://code.claude.com/docs/en/skills)에서 확인할 수 있습니다.

## 설치와 실행

### 1. 필요한 환경

- 설치·인증을 마친 **Claude Code**: 터미널에서 `claude`를 실행할 수 있어야 합니다.
- **Git**: 작업 브랜치, 기준 커밋, 통합 검증에 사용합니다.
- **Node.js 22 이상**: npm 방식의 code-agent 설치·실행에 필요합니다. 단일 실행 파일을 사용하면 code-agent 자체에는 별도 Node 설치가 필요 없습니다.
- 개발할 프로젝트의 실행 환경: Java, Node.js, Python 등 해당 코드의 빌드·테스트에 필요한 도구입니다.

단일 실행 파일에도 Claude Code와 Git, 대상 프로젝트의 실행 환경은 별도로 필요합니다. 자세한 설치 조건은 [설치 문서](doc/install.md)를 참고하세요.

### 2. code-agent 설치

아래는 이 저장소를 `C:\IdeaProjects\code-agent`에 받은 경우의 PowerShell 예시입니다. 경로는 실제 저장소 위치로 바꿉니다.

```powershell
npm install -g "C:\IdeaProjects\code-agent"
code-agent --help
```

실행 파일 배포를 사용하려면 OS에 맞는 `code-agent` 실행 파일을 PATH에 둡니다. 직접 만드는 방법은 [단일 실행 파일 빌드](doc/install.md#2-단일-실행-파일-만들기)에 있습니다.

### 3. 개발할 프로젝트에 설치하고 Claude Code 실행

**일반 터미널에서 실행합니다.** code-agent 소스 저장소가 아니라 실제 개발할 프로젝트 폴더로 이동합니다. 폴더가 아직 없으면 먼저 만듭니다.

```powershell
cd "C:\work\my-app"
code-agent init
claude
```

`init`은 `.claude/skills`, `.claude/agents`, `.claude/settings.json`, `CLAUDE.md`의 code-agent 블록 등을 설치합니다. 공통 설계 문서나 애플리케이션 코드를 만드는 단계는 아닙니다. 프로젝트 신뢰 확인이 나오면 폴더와 설치 내용을 확인합니다.

### 4. 요구사항 입력

**Claude Code의 대화 입력창에서 실행합니다.** PowerShell에 입력하는 명령이 아닙니다.

```text
/ca-request 주문을 등록하고 주문 번호로 조회할 수 있게 해 주세요.
```

`/ca-request`는 모든 작업의 공통 접수입니다. ID를 생략하면 `WORK-0001` 형식으로 발급합니다. 티켓 ID가 있으면 `/ca-request ORD-12 요구사항`처럼 입력합니다. 명확한 작업 종류는 요청에서 판단하고, 애매할 때만 묻습니다.

이후에는 화면에 나온 질문과 확인에 답하면 자동으로 다음 절차를 이어갑니다. `/ca-next`는 중단되거나 세션을 다시 연 작업을 재개할 때 사용합니다. 현재 위치는 `/ca-status`로 확인합니다.

### 질문에 답하는 방법

모든 `/ca-*` 명령은 확인할 내용이 생기면 Claude Code의 **선택형 질문 도구(`AskUserQuestion`)**를 사용합니다. 에이전트가 질문과 선택지를 만들고, 근거가 있는 추천에는 이유를 붙입니다. 선택하거나 도구의 직접 입력으로 답하면 그 답을 기록하고 같은 명령에서 이어갑니다. 질문마다 `/ca-answer`를 입력할 필요는 없습니다. `/ca-answer`는 중단된 미응답 질문을 다시 여는 명령입니다.

초기 언어·구성은 JavaScript/Node, Python 표준 도구, TypeScript/Node, Python/FastAPI, Java/Spring Boot, Kotlin/Spring Boot, Go의 7개 후보를 제공합니다. 요청 목적과 기존 설정에 맞춰 추천하며, 기존 구성이 있으면 재사용합니다. 언어·아키텍처처럼 대안이 많은 질문은 실제 후보를 최소 5개 제시하고, 두 가지 범위 중 고르는 질문은 불필요하게 늘리지 않습니다.

선택지가 5개 이상이면 전체 목록을 먼저 보여 주고 `다른 선택지`·`앞 선택지`로 이동합니다. Claude 도구가 화면당 최대 4개 옵션을 받기 때문입니다. 취소·보류는 답으로 처리하지 않으며, 도구를 사용할 수 없으면 미응답 상태를 유지하고 대화형 Claude Code에서 재개하도록 안내합니다. [Claude 질문 도구 사양](https://code.claude.com/docs/en/agent-sdk/user-input#question-format)

업무 질문의 답과 문서·요구사항 확정, 계획 승인, 결과 반영은 기록 목적이 다르지만 모두 같은 선택 화면을 사용합니다. 확정·승인에는 CLI가 준비한 질문을 그대로 표시하고 hook이 관찰한 실제 사용자 선택만 사용합니다. 채팅에 “승인”이라고 쓴 문장이나 모델이 만든 답변은 승인으로 처리하지 않습니다.

레거시 프로젝트에 공통 문서가 없거나 부족하면 **소스·설정 기준으로 작성(추천) / 사용자 선택·입력으로 작성 / 기존 문서 연결** 중 작성 방식을 한 번 고릅니다. 입력한 방향이 현재 코드와 다르면 현행과 변경할 방향을 구분해 기록합니다. 문서 준비 자체가 코드 변경을 승인하지는 않습니다. 빈 저장소는 초기 구성 선택으로 문서·설정을 준비하고, 필수 문서 확정 전까지 분석을 시작하지 않습니다. 이미 문서와 설정이 준비됐다면 이 선택을 반복하지 않습니다.

## 요구사항부터 완료까지

기본 진행은 **같은 Claude Code 대화 안에서** 끝납니다. 사용자는 내용을 읽고 선택하며, 에이전트는 그 응답이 확인되면 이어서 작업합니다. 별도 TTY는 필수가 아닙니다.

| 순서 | 입력할 곳 | 진행 방법 |
|---|---|---|
| 1. 접수 | Claude Code | `/ca-request <요구사항>`을 입력합니다. 원문을 저장하고 공통 문서·설정을 확인합니다. |
| 2. 초기 준비가 필요한 경우 | Claude Code | 기존 구성을 재사용하거나 신규 구성을 선택합니다. POLICY 4종과 필요한 최초 기준 커밋의 준비 파일을 `setup` 확인에서 함께 검토합니다. 확인 후 같은 접수를 이어갑니다. |
| 3. 요구사항 확정 | Claude Code | 원문 대조·범위·완료 조건을 읽고 선택 화면에서 확정합니다. 수정 요청·보류도 선택할 수 있습니다. |
| 4. 분석·계획 | Claude Code | 분석 → 영향도 → 설계 → Task·테스트 계획을 이어서 작성합니다. 업무 질문이 나오면 선택 도구에서 답합니다. |
| 5. 계획 승인 | Claude Code | Task별 요구사항·파일·순서·가정을 읽고 선택 화면에서 승인합니다. |
| 6. 개발·검증 | Claude Code | 승인된 순서의 구현 → 빌드·테스트 → 독립 리뷰 → 통합 검증을 진행합니다. 계획 안의 실패·지적은 수정 후 다시 검증합니다. |
| 7. 결과 반영 | Claude Code | KNOWLEDGE 갱신 항목을 고르고, 요구사항별 결과와 실제 커밋할 경로 목록을 확인하면 작업 브랜치에 로컬 커밋합니다. |

확인 절차는 에이전트가 `code-agent consent prepare <action.json>`을 호출하고, 반환된 `toolInput` 전체(`questions`와 `metadata.source`)를 수정 없이 `AskUserQuestion`에 전달하는 순서입니다. PreToolUse·PostToolUse hook이 같은 세션의 질문과 응답을 관찰하면 `code-agent consent status <ID>`로 상태를 확인하고, 승인된 요청만 `code-agent consent apply <ID>`로 실행합니다. 남은 질문이 있으면 반환된 질문을 이어서 표시합니다. 확인 이후 파일·Git 상태나 플러그인 설명이 바뀌면 새 확인이 필요합니다.

기존 `confirm`·`approve`·`deliver`를 일반 터미널에서 직접 실행하는 방식도 사용할 수 있습니다. 이 경로는 화면에 표시된 단어를 입력하는 TTY 확인을 유지합니다.

### 개발과 검증의 기준

- **요구사항 추적:** 원문 → 구조화 요구·완료 조건·제약 → 분석 R → Task·파일·수락 기준(AC)·테스트(TC) → 실제 결과를 연결합니다. 원문 미연결과 요구사항의 Task 누락은 차단합니다.
- **계획대로 실행:** 실제 구현 순서는 승인된 `plan.sequence`를 따릅니다. 순서를 바꾸려면 계획 재제출과 재승인이 필요합니다.
- **테스트 시점:** 초기 적합성 검토는 원문·AC·예정 TC의 문서 대조입니다. 실제 테스트는 구현 후 기존 명령으로 실행합니다. 버그 수정은 구현 전에 대상 TC의 실패를 먼저 재현합니다.
- **테스트 결과:** 콘솔과 이번 실행이 생성·갱신한 JUnit 보고서를 자동 수집합니다. TC 이름만 있거나 생략·미실행·판정 불가인 결과는 성공으로 처리하지 않습니다. 사용자에게 러너별 선택을 요구하지 않습니다.
- **독립 리뷰:** `ca-reviewer`가 요구사항의 명확성·기능 위반·기존 기능에 미치는 영향·전체 테스트와 실패 케이스의 검증을 대조합니다. 영향도 문서에 지정한 호출자·공유 모듈·기존 테스트도 읽습니다. 필요한 근거가 없으면 검증 공백으로 보고합니다. 시작·완료와 결과는 hook이 기록하며 메인이 지적을 임의로 “해결” 처리할 수 없습니다. 수정 후 재검증과 새 리뷰를 받습니다.
- **실패 케이스:** 잘못된 입력·권한 거부·외부 실패 등 요구에 해당하는 상황을 검증하는 테스트입니다. 예상 오류와 보존 조건을 단언하며 테스트 자체는 통과해야 합니다. 생략·미실행은 통과가 아닙니다.
- **통합 검증:** 기준 커밋의 격리 worktree에 변경을 적용해 다시 빌드·테스트합니다. 버그 재현 테스트를 리뷰 후 보완했을 때도 격리된 기준 코드에서 실패를 재확인합니다.

## 명령 선택

### Claude Code 안에서 입력

`/ca-request`와 작업 종류별 명령을 연속으로 모두 입력할 필요는 없습니다. 하나로 접수하면 질문·확인을 거쳐 자동으로 이어가며, 중단 후 재개할 때만 `/ca-next`를 사용합니다.

| 명령 | 용도 |
|---|---|
| `/ca-request [ID] <요구사항>` | **모든 작업의 공통 접수.** 종류 판단, 원문 보관, 준비, 요구사항·계획·결과 확인을 같은 화면에서 거쳐 계속 진행합니다. |
| `/ca-feature [ID] <요구사항>` | **신규 개발·기능 추가·기능 변경**을 명시하는 진입점. 같은 접수·확인·자동 진행 절차를 `feature`로 사용합니다. |
| `/ca-fix [ID] <결함>` | 버그 수정. 공통 접수 후 실패 재현 → 수정 규칙을 적용합니다. |
| `/ca-refactor [ID] <요구사항>` | 동작을 보존하는 구조 개선. 기존 테스트를 보호합니다. |
| `/ca-next` | 중단된 접수·작업을 현재 상태에서 재개합니다. 필요한 확인도 같은 화면에서 이어갑니다. |
| `/ca-answer` | 중단된 미응답 질문을 선택 도구로 다시 열고 진행을 잇습니다. |
| `/ca-status` | 현재 위치, 막힌 이유, 다음 할 일을 확인합니다. |
| `/ca-adopt` · `/ca-docs` | 공통 문서와 프로젝트 설정을 도입·보완합니다. 접수 중 준비가 필요할 때도 같은 절차를 사용합니다. |

## 기존 설치 갱신과 문제 해결

**code-agent 소스를 고친 것과 대상 프로젝트에 설치된 절차를 갱신한 것은 별개입니다.** `init`은 `template/`의 파일을 프로젝트로 복사하므로 이미 설치한 `.claude/`와 `CLAUDE.md`에는 이전 지시가 남을 수 있습니다.

**`code-agent update`는 로컬 Git 소스에 연결된 설치본의 자동 갱신 명령입니다.** code-agent 소스 저장소의 upstream을 `pull --ff-only`로 받고, 의존성이 바뀌었거나 설치가 필요하면 잠금 파일 기준으로 `npm ci --include=dev`를 실행하고 빌드합니다. 이어서 새로 빌드한 CLI로 대상 프로젝트의 스킬·에이전트·hook·공통 지시를 적용하고 `doctor`로 점검합니다. 소스 저장소에 미커밋 변경이 있거나 이력이 분기되어 fast-forward할 수 없으면 중단합니다.

| 설치 방식 | code-agent 자체 갱신 | 개발 대상 프로젝트에 적용 |
|---|---|---|
| 로컬 Git 소스에 연결된 설치 (`npm link` 또는 연결된 로컬 경로 설치) | `code-agent update`가 upstream fast-forward, 잠금 의존성 설치, 빌드를 수행합니다. | 같은 명령이 새 CLI로 적용하고 `doctor`를 실행합니다. |
| Git 소스가 없는 npm 패키지 | Git 자동 갱신을 지원하지 않는다고 안내합니다. 새 패키지는 별도로 설치합니다. | `code-agent update --templates-only` → `code-agent doctor` |
| 단일 실행 파일 | Git 자동 갱신을 지원하지 않는다고 안내합니다. 실행 파일은 새 버전으로 교체합니다. | `code-agent update --templates-only` → `code-agent doctor` |

이 문서의 `npm install -g "C:\IdeaProjects\code-agent"` 예시처럼 로컬 경로로 설치한 경우, 전역 패키지 경로가 원본 폴더에 연결돼 있다면 첫 번째 방식입니다. `npm root -g`로 전역 패키지 위치를 확인하고, Windows에서는 그 아래 `code-agent` 폴더의 `LinkType`·`Target`을 `Get-Item`으로 확인할 수 있습니다. `Get-Command code-agent`는 실제 실행되는 명령 경로를 보여 줍니다.

**실제 개발 대상 프로젝트에서** 실행합니다. 여러 프로젝트에 설치했다면 각 프로젝트에 적용합니다.

```powershell
cd "C:\work\my-app"
code-agent update
```

현재 설치본의 템플릿만 적용하려면 `code-agent update --templates-only`를 사용합니다. 이 옵션은 fetch·pull·의존성 설치·빌드를 하지 않습니다. 직접 수정한 개발본은 필요한 빌드를 먼저 수행한 뒤 이 옵션으로 적용할 수 있습니다.

Claude Code 안에서는 “code-agent를 업데이트해 주세요”라고 요청하면 `action: "update"`의 같은 세션 확인을 거쳐 실행합니다. 갱신 후에는 **Claude Code를 종료하고 같은 프로젝트에서 다시 열어야 새 hook이 활성화됩니다.** `/ca-status`로 상태를 확인하고 `/ca-next`로 기존 접수·작업을 재개합니다. `doctor`에서 공통 문서가 아직 없다고 나오면 준비 단계에서 해결합니다.

| 증상 | 확인할 것 |
|---|---|
| `init` 뒤 아무 개발도 시작되지 않음 | 정상입니다. 같은 프로젝트에서 `claude`를 실행하고 `/ca-request`를 입력합니다. |
| `/ca-request`가 보이지 않음 | 실행 폴더와 `.claude/skills/ca-request/SKILL.md`를 확인합니다. `update`·`doctor` 후 Claude Code를 다시 엽니다. |
| 수정했는데 옛 안내가 나옴 | CLI 빌드·전역 설치 경로·프로젝트 설치 사본을 각각 확인합니다. Windows의 `Get-Command code-agent`와 `code-agent doctor`가 경로 확인에 도움이 됩니다. |
| 같은 화면의 확인이 처리되지 않음 | `consent status`와 `doctor`에서 질문 상태·consent hook 설치를 확인합니다. 갱신했다면 Claude Code를 다시 엽니다. 직접 CLI 승인 명령은 일반 TTY에서도 사용할 수 있습니다. |
| 소스 자동 갱신이 중단됨 | code-agent 소스 저장소의 미커밋 변경·upstream·분기 상태를 확인합니다. 강제 초기화나 임의 병합으로 넘어가지 않습니다. 현재 번들 적용만 필요하면 `--templates-only`를 사용합니다. |
| 준비 또는 작업이 중단됨 | `/ca-status`의 이유와 다음 할 일을 확인합니다. 문서 미확정·미응답·계획 변경·검증 실패를 해결한 뒤 `/ca-next`로 이어갑니다. |

`update`는 다른 hook, `CLAUDE.md`의 code-agent 블록 밖 내용, 모델 오버라이드를 보존합니다. 번들에 없는 과거 `ca-*` 파일은 사용자 파일일 수 있어 자동 삭제하지 않고 보고합니다. 해당 목록은 검토 후 정리해야 합니다.

## 요구 분석·설계·계획

신규 작업은 `planning prepare`·`dispatch`로 담당·입력·출력·선행 조건을 정하고 실제 서브 에이전트 실행 결과를 확인합니다. 영역 조사는 기본 3개까지 병렬 배정하며, 동일 입력 결과는 재사용합니다. 설계와 계획은 ca-analyst, 영향도 정리는 ca-writer, 독립 반박 검토는 ca-critic이 맡습니다. 미결 질문·오래된 근거·차단 지적이 있으면 진행하지 않습니다.

계획에는 단계 안의 독립 `tasks`를 정의하고 파일 소유·의존성·수락 기준을 연결합니다. 기존 작업은 이전 형식으로 재개합니다. [계획 작업 안내](doc/planning.md)에 계약과 복구 절차를 설명합니다.

## 검증 노드 실행

전체 작업 흐름에서 `code-agent verify`가 정적 검증·테스트 실행·결과 판정을 연속 처리합니다. `program` 노드는 코드로 실행하고, 실패 분석·수정·독립 리뷰가 필요한 `agent` 노드와 사용자 판단이 필요한 `human` 노드에서는 작업 요청을 반환합니다.

```powershell
code-agent verify
code-agent verify --json
```

통과하면 리뷰 단계로 이동합니다. 실패하면 `repair`(수정), `diagnose`(실행·결과 수집 문제 확인), `decision`(한도 초과)을 구분합니다. 수정 후 같은 명령으로 재개하며 환경 문제를 해결하고 동일 입력을 다시 실행할 때는 `--retry`를 사용합니다. 승인·계획 범위·테스트 동결·수정 한도는 기존 규칙을 적용합니다. 상세 절차는 [사용 가이드](doc/usage.md#검증-노드-실행기)를 참고하세요.


대상 프로젝트에서 로컬 개발본을 쓰려면 이 저장소에서 `npm link`를 실행한 다음, 대상 프로젝트에서 `code-agent init --cli C:/IdeaProjects/code-agent/dist/agent/cli.js`를 사용합니다. `--cli`에는 PC별 절대 경로가 들어가므로 팀 공용 설치와 구분합니다.

관찰된 계획 작업 도입 이전의 전체 흐름은 신규·기능 개선·버그 수정·리팩토링 4유형에서 실제 모델로 접수부터 로컬 반영까지 확인했습니다. 승인 입력은 명시적인 자동 fixture였으며 **실제 초보자 사용성 측정은 아닙니다.** 대형 프로젝트·사용자 정의 테스트 출력·다양한 결함의 리뷰 정확도는 추가 확인 범위입니다. 관찰된 계획 작업의 검증은 [최신 변경 기록](doc/reviews/2026-10-02-planning-orchestration.md)에, 이전 검증 노드 회귀 결과는 [당시 검증 기록](doc/reviews/2026-10-02-verification-workflow.md), 이전 같은 세션 확인·업데이트 결과는 [당시 기록](doc/reviews/2026-10-02-session-confirmation-update.md)으로 구분합니다. 실제 사람의 질문 화면 조작과 노드화 이후 토큰·시간 절감량은 별도 실측 대상입니다.
