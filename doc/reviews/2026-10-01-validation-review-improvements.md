## 후속 점검 — README·접수 진입점·실행 안내

사용자 요청에 따라 README를 프로젝트 목적 → 구조 → 설치·실행 → 완료까지의 사용 흐름 → 명령 → 결과물 → 갱신·문제 해결 순서로 다시 구성했다. 문장 중간의 불필요한 개행과 과거 개발 단계 중심의 설명을 정리하고, 일반 터미널과 Claude Code 입력창의 명령을 분리했다.

## 최신 기능 판정 — 잔여 보완 적용 후

기존 언어·프레임워크·테스트 도구를 재사용한다. 초기 준비는 설정·실행 환경·Git 상태만 확인하며 테스트를 실행하지 않는다. 요구사항 적합성 검토는 원문·AC·예정 TC의 문서 대조다. 구현 후 기존 명령으로 테스트하고 그 결과를 요구사항에 연결한다. 버그 수정만 구현 전에 실패 재현을 수행한다. 러너별 결과 수집은 에이전트 내부 처리이며 사용자 선택 단계로 추가하지 않았다.

| Task | 적용 내용 | 판정 / 근거 |
|---|---|---|
| RW1 신규 준비 | `setup`으로 환경·기존 명령 확인. `setup baseline`은 준비 파일을 보여주고 TTY 확인 뒤 최초 커밋. 실제 소스·실행 설정·테스트는 승인 Task에서 생성 | 구현·회귀 검증 완료. 신규 실모델도 접수부터 로컬 반영까지 완료 |
| RW2 미응답 | 주석·구분선만 있는 답변은 미응답 처리, 실제 여러 줄 답변은 유지 | 재현 사례를 회귀 테스트로 전환해 통과 |
| RW3 원문 추적 | 원문 인용→REQ/DONE/CON/OUT 연결과 반영·제외·미연결 표. 미연결은 에이전트가 제출 단계에서 보완하고 확정 게이트도 차단 | 구현·접수 회귀 통과. 의미 보존 자체는 사람과 critic의 검토 대상 |
| RW4 쉬운 진행 | 명확한 작업 종류 자동 분류, 기존 기술 선택 재사용, 업무 질문만 요청, 답변 후 재개, 사용자 안내는 5단계로 요약 | 지시문 보완 완료. 사람의 터미널 확정·승인은 유지. 실제 초보자 사용성 측정은 별도 |
| RW5 기존 테스트 | 기존 명령 유지. 콘솔 결과와 이번 실행이 생성·갱신한 JUnit XML 자동 수집. 오래된 보고서·생략·미실행을 성공으로 인정하지 않음 | 파서·보고서 회귀 통과. 실제 Gradle/Maven 프로젝트 실행은 이번 범위에 없음 |

모두 독립 리뷰 시작·완료가 관찰됐고 반영 뒤 작업 커서가 지워졌다. 원격 push는 하지 않았다. 최초 문서 확인과 신규 기준 커밋까지 포함한 판정 fixture는 각각 5·4·5·5회다. `questions.md`는 모두 0개였지만 대화에 나온 질문까지 센 수치가 아니므로 ‘사용자 질문 0회’라고 판정하지 않는다. 모델 턴은 사람의 선택 횟수와도 다르다.

버그 수정·리팩토링은 실행되지 않는 절차 확인용 TC를 계획에 넣어 재승인 1회가 발생했다. 이 발견을 반영해 TC 표에는 실제 실행할 테스트만 쓰도록 안내를 보완했고, 새 테스트를 만들지 않는 리팩토링에서 기존 파일에 없는 TC ID를 계획하는 경우 승인 전에 차단한다. 접수 미연결도 사용자에게 확정을 요청하기 전에 에이전트가 보완하도록 출력과 스킬을 정리했다. **이 마지막 보완은 아래 회귀 검증으로 확인했으며, 선택 횟수 감소를 별도 실모델 실행으로 재측정하지 않았다.**

리뷰 결함별 근거와 수정 후 결과는 [리뷰 품질 기록](evidence/review-quality-2026-10-01.json)에 있다. 재실행 도구는 [전체 흐름 평가](../../scripts/evaluate-full-flow.cjs)와 [리뷰 평가](../../scripts/evaluate-review.cjs)다. 실제 모델 호출은 비용이 발생하는 명시적 실행이며 `npm test`에 포함하지 않는다.

README는 시작 흐름, usage는 실행 방법, requirement는 원문 대조 규격, design은 강제 규칙, install은 설치·갱신·제거를 맡도록 정리했다. 과거 보고서는 당시 증거로 보존하고 최신 판정으로 연결했다. 옛 hook 2개 안내, 재현 테스트 수정 시 되돌리기 안내, JUnit 어댑터를 사용자에게 요구하는 설명을 현재 동작에 맞게 수정했다.

아직 일반화하지 않는 범위는 **실제 초보자의 사용성, 다양한 대형 프로젝트, 사용자 정의 테스트 출력, 다양한 결함에 대한 리뷰 정확도**다. 아래 과거 기록의 ‘미완료’ 표시는 발견 당시 상태이며 현재 판정은 위 표를 따른다.

## 실제로 달라진 동작

### 테스트와 버그 재현

- 명령 종료 코드가 0이어도 필수 TC가 skipped·not-run·unknown이면 다음 단계로 이동하지 못한다.
- 테스트 파일에 `TC-1` 주석이 있거나 일반 로그에 ID가 나오는 것만으로 통과시키지 않는다.
- 동일 TC의 여러 실행 중 실패나 생략이 있으면 성공 한 건으로 덮지 않는다.
- 버그 재현은 지정한 TC 자체가 failed여야 한다. TC-1 통과와 다른 TC의 실패가 같은 명령에서 발생해도 TC-1의 재현으로 인정하지 않는다.
- TC별 실패 상태가 없는 구버전 재현 기록도 재사용하지 않는다. 구현 파일 쓰기·단계 전환·검증을 막고 실제 재현을 다시 요구한다.
- 통합 검증은 깨끗한 worktree에서 얻은 TC 결과를 별도로 확인한다. 앞선 작업 트리의 테스트 성공을 재사용하지 않는다.

지원 출력: TAP, Node spec, unittest verbose, pytest verbose, Go JSON, `code-agent-test` JSONL. 지원되지 않는 출력은 unknown으로 차단한다. 결과 어댑터는 승인된 테스트 명령에서 **러너의 실제 결과**를 다음 형식으로 출력할 수 있다.

```json
{"type":"code-agent-test","id":"TC-1","status":"passed"}
```

허용 상태는 passed·failed·skipped·not-run이다. JUnit XML 파일을 직접 읽는 기능은 이번 범위에 포함하지 않았다. 기존 프로젝트가 TC 결과를 출력하지 않았다면 업데이트 전에 테스트 결과 형식도 맞춰야 한다.

### 리뷰와 수정 루프

1. 검증이 통과한 코드에서 `code-agent review`로 회차를 연다.
2. 메인이 독립 `ca-reviewer`를 호출한다.
3. SubagentStart·SubagentStop hook이 해당 리뷰어의 실행을 관찰하고 결과를 `09-review.md`에 자동 기록한다.
4. 메인은 지적을 수정한다. 동결 테스트는 승인된 계획에 포함되고 관찰된 열린 지적이 해당 파일을 가리킬 때만 수정할 수 있다. refactor의 기준 커밋 테스트는 계속 보호한다.
5. 수정 후 check → test → 새 리뷰 회차를 거친다. 이전 지적의 해결 여부도 리뷰어가 다시 확인한다. 단, fix에서 재현 이후 테스트 트리가 바뀌면 통합 단계가 추가로 차단한다. 현재는 수정 코드를 유지한 채 기준 코드에 새 테스트를 적용해 재현을 갱신하는 경로가 없어, 이 루프만으로 완료되지 않는다.

리뷰 도중 코드가 바뀌거나 다른 에이전트의 완료가 들어오면 기록하지 않는다. 새 호출보다 오래된 transcript의 완료 보고도 재사용하지 않는다. 메인이 지적 상태를 ‘해결’로 바꾸거나 결과를 ‘없음’으로 덮으면 게이트가 막는다. 코드 파일부터 수정한 뒤 동결 테스트를 수정하는 순서도 허용하되 최종 통과에는 새 코드 상태의 재리뷰가 필요하다.

실행 관찰은 Claude Code hook과 보호된 작업 기록을 신뢰 경계로 삼는다. 리뷰 판단의 정확성까지 자동 증명하는 기능은 아니다. hook 이벤트·필드와 SubagentHandback 처리는 [Claude Code 공식 hook 문서](https://code.claude.com/docs/en/hooks)를 확인하고 구현했다.

## 실제 모델 검증

Claude Code 2.1.286을 사용했다. 시나리오별 임시 Git 저장소에서 실행했으며, 공통 문서·요구사항·계획·승인은 명시적인 **테스트 fixture**다. 실제 모델이 소스와 테스트를 작성하고, 실제 검증 명령과 독립 리뷰어를 실행하도록 했다. 별도의 사용자 답변은 주입하지 않았다.

| 시나리오 | 실제 모델 작업 | 테스트 / 통합 | 독립 리뷰 | 도달 상태 |
|---|---|---|---|---|
| 신규 | value 함수와 TC-1·TC-2 생성 | 각각 2/2 passed | 시작·완료 관찰, 지적 없음 | deliver 대기, 차단 사유 0 |
| 기능 개선 | 기존 함수에 음수 오류 처리 추가 | 각각 2/2 passed | 시작·완료 관찰, 지적 없음 | deliver 대기, 차단 사유 0 |
| 버그 수정 | 0을 잘못 반환하는 결함 재현 후 수정 | TC-1 failed 재현 → 각각 2/2 passed | 시작·완료 관찰, 지적 없음 | deliver 대기, 차단 사유 0 |
| 리팩토링 | 반환 분기 중복 제거 | 기존 테스트 보존, 각각 2/2 passed | 시작·완료 관찰, 지적 없음 | deliver 대기, 차단 사유 0 |

네 저장소 모두 HEAD가 초기 커밋 그대로다. 반영 확인·커밋·push를 모델이 대신 실행하지 않았다. 리팩토링 테스트는 기준 커밋과 바이트 단위로 동일하다. CLI가 보고한 모델은 Sonnet 5.5와 일부 하위 에이전트의 Opus 5.5이며, 보고 비용 합계는 약 $2.45다. 이는 실제 청구액 확인이 아니라 CLI의 사용량 보고다.

코드·테스트, TC 결과, 재현, 검증 명령, 리뷰 실행 기록은 [실모델 증거](evidence/model-evaluation-2026-10-01.json)에 보존했다. 재실행 도구는 [evaluate-model.cjs](../../scripts/evaluate-model.cjs)이며 실제 모델 호출은 명시적으로 실행해야 한다. `prepare` → `run new/enhance/fix/refactor` → `collect` 순서다.

### 재검토에 따른 판정 정정

앞선 남은 항목 표는 실측 범위에 치우쳐 구현 보완을 충분히 드러내지 못했다. 최초 검토의 완료 기준으로 보면 **T2(신규 준비), T6(동결 테스트 수정 후 완주), T8(선택·확인 단순화), T9(실제 전체 완주)는 부분 완료**다. 이미 고친 세부 결함과 상위 Task 전체 완료를 구분한다. T3의 추적은 확정된 구조화 요구부터 유효하며, 원문을 구조화하면서 빠진 의미까지 확인하는 기능은 아니다.

다음은 진행 단계 순서의 잔여 Task다. P1은 진행 차단·답변/요구 누락에 영향을 주는 항목, P2는 사용성·검증 확장이다. 구현 공백은 코드 대조, 재현된 결함은 파서 실행, 검증 공백은 기존 실모델 평가 범위를 근거로 판정했다.

| Task | 단계 / 우선순위 | 남은 문제와 판정 | 사용자 영향 | 완료 기준 |
|---|---|---|---|---|
| RW1 | 프로젝트 준비 / P1 | **구현·사용성 공백.** 추천 설정은 문서·설정까지 생성한다. 기준 커밋이 없으면 수동 최초 커밋 안내로 끝나며, 실행 환경·의존성·실제 뼈대 생성까지 하나의 준비 흐름으로 연결되지 않았다 | 빈 폴더에서 시작한 초보자가 Git와 실행 환경을 직접 해결해야 함 | 기존 파일을 보존하며 환경·Git 준비 상태를 먼저 진단. 필요한 초기화·최초 커밋 파일을 명확하게 제시하고 사용자 확인 뒤 처리. 소스 뼈대는 승인된 Task에서 생성하고 실행까지 확인 |
| RW2 | 요구사항 질문 / P1 | **재현된 판정 결함.** 빈 `[Answer]:` 뒤 HTML 주석 또는 `---`만 있어도 답변이 있다고 파싱함 | 실제 답을 받지 않은 질문이 ‘미응답’ 목록에서 사라질 수 있음 | 주석·구분선만 있는 답은 미응답. 실제 여러 줄 답변은 보존. 단계 전환에서도 미응답을 차단하는 회귀 검증 |
| RW3 | 접수 → 분석 / P1 | **추적 범위 공백.** 원문 → 구조화 요구 사이의 누락 검사는 없음. ‘CSV 내보내기 + 관리자 제한’ 중 제한을 구조화 문서에서 빼도 현재 출처 검사는 통과 | 분석 이후 연결표가 완전해도 최초 요구가 빠질 수 있음 | 확정 전 원문과 정리본의 누락·변경·제외를 비교해 보여주고 확인. 의미 누락 사례로 검증; 문자열 일치만으로 의미 보존을 보증하지 않음 |
| RW4 | 질문·단계 안내 전반 / P2 | **사용성 공백.** `/ca-answer`는 모르면 비워 두고 끝나며 `/ca-next` 재호출을 안내. 사용자 결정이 필요한 업무 질문과 추천으로 해결 가능한 기술 질문을 구조적으로 구분하지 않음. 별도 터미널 확정·승인·반영 3회가 남음 | ‘추천대로’의 적용 범위가 불명확하고 사용자가 다음 명령을 기억해야 함 | 업무 결정은 필요한 경우만 질문. 기술 선택은 추천과 이유를 제시하고 재사용. 답변 뒤 자동 재개하고 사용자에게 현재 단계·할 일 하나를 안내. 승인 보장은 유지하며 실제 선택·명령 전환 횟수 측정 |
| RW5 | 테스트 설정·검증 / P1 | **호환성 공백.** 테스트 파서는 JUnit XML과 요약 출력만으로 TC 결과를 얻지 못함. 도입 스킬의 `gradlew test` 예제에는 TC 결과 변환 설정이 없음 | 실행에 성공해도 결과 형식이 맞지 않으면 unknown으로 막히며 초보자가 어댑터를 직접 준비해야 함 | 도입 시 결과 형식 적합성 확인. 지원하는 러너별 실제 결과 어댑터와 예제를 제공하고 성공·실패·생략을 검증. 결과 누락을 성공으로 완화하지 않음 |
| RW6 | 리뷰 수정 → 통합 / P1 | **복구 경로 공백.** 리뷰 지적으로 fix 테스트를 수정할 수 있지만 통합에서는 최초 재현 테스트 해시와 다르면 차단. `repro` 재실행은 구현 파일이 이미 바뀌었다며 되돌리기를 요구함 | 정당한 테스트 보완도 수정 코드를 수동으로 되돌리거나 계획을 다시 준비해야 함 | 작업 코드를 보존한 격리 환경에서 기준 코드 + 수정 테스트로 대상 TC 실패를 다시 확인하고, 수정 코드에서 통과·재리뷰까지 이어감. 단언 삭제 등 결함을 재현하지 못하는 변경은 계속 차단 |
| RW7 | 독립 리뷰 / P2 | **검증 공백.** 리뷰 실행 관찰은 검증했으나 실제 결함 탐지 성능은 확인하지 않음. 실모델 4건은 모두 ‘지적 없음’ | 리뷰어가 실행됐다는 사실만으로 검토 품질을 평가할 수 없음 | 권한 누락·경계값·회귀 등 결함을 넣은 사례와 정상 사례로 탐지·누락·오탐 및 수정 후 재검토 결과 기록 |
| RW8 | 전체 완료 / P2 | **검증 공백.** 실모델 평가는 준비된 계획·테스트용 승인에서 시작해 deliver 직전에 끝남 | 요구사항만 제시한 초보자가 최소 선택으로 완료한다는 최종 목표는 아직 입증되지 않음 | 신규·개선·수정·리팩토링을 실제 접수부터 시작. 사람의 확인·반영까지 수행하며 질문 수·수동 개입·소요 시간·Task·TC·리뷰 결과 보존. fixture 승인을 사람 승인으로 계산하지 않음 |

- RW6: [리뷰 수정 권한](../../src/agent/review.ts)의 `findingOpensFile`, [통합 해시 검사](../../src/agent/evidence.ts)의 `stageProblems`, [재현 선행 조건](../../src/agent/validate.ts)의 `repro`. [P6의 17b 사례](../../src/test/p6.test.ts)는 테스트 약화 차단을 검증하며, 정당한 테스트 보완의 복구 완료까지 검증한 사례는 아니다.
- RW7·RW8: [실모델 실행 범위](../../scripts/evaluate-model.cjs), [기존 실행 기록](evidence/model-evaluation-2026-10-01.json).

RW2·RW3·RW5의 최소 입력과 실제 파서 결과는 [재현 코드](evidence/remaining-work-probes.cjs)와 [결과](evidence/remaining-work-probes.json)에 보존했다. 제품 코드 변경이나 새로운 전체 회귀·실모델 실행은 이번 재검토에서 수행하지 않았다.

### 기존 실측 범위

| 남은 항목 | 이번에 확인한 범위 | 아직 확인하지 않은 범위 |
|---|---|---|
| 초보자 사용성 | 준비된 계획 이후 4개 실모델 시나리오 | 원문 접수부터 기술 선택·질문·실제 TTY 승인·반영까지 사람의 경험과 소요 시간 |
| 리뷰 품질 | 독립 실행·결과 연결과 우회 차단 | 의도적으로 심은 다양한 결함을 찾아내는 비율. 이번 실모델 4건은 모두 지적 없음이었음 |
| 프로젝트 다양성 | 작은 Node 프로젝트 실모델 검증, Python 추천 명령 자동 검증 | 실제 프레임워크·DB·외부 연동·JUnit 결과 어댑터 |

소스와 설치 템플릿을 수정한 상태이며 커밋·배포는 하지 않았다. 이미 도입한 프로젝트에는 새 버전의 `code-agent update`가 필요하고, `code-agent doctor`에서 SubagentStart·SubagentStop hook을 확인한다. 기존의 실행 관찰 없는 리뷰 기록은 새 게이트를 통과하지 못하므로 독립 리뷰를 다시 수행해야 한다.
