# 대시보드 요청의 작업 임대 판정 통일

구현 커밋: `c75f7a8`.

## 문제

master-agent 의 재현(`master-agent/.master-agent/consent-lease-repro.cjs`)에서 작업이 없는 프로젝트에 끝난 작업의 `lease.json`이 남아 있으면 준비 요청이 조회에서는 `canRespond:true`인데 서명된 제출은 `busy`로 거절되고 원래 요청은 `pending`으로 남았다.

platform-gateway 의 실제 상태(2026-10-22 01:34Z, 읽기 전용 조회)도 같은 조건이었다: 브랜치 `feature/YSIJ-263`에 작업 커서가 없고, 임대는 끝난 작업 `YSIJ-263`의 Claude 세션 `c9e815eb`(마지막 활동 2026-10-21 05:59Z)가 남긴 것이며, 기준 커밋 동의 `040c8494…`(01:10:58Z, 다른 세션 `038affb3`이 실행 `run-mviughs6-fef84d43`에서 준비)가 대기 중이라 적용 버전 `1.0.0-f8c67b89bd53`의 갱신도 이 동의 하나로 보류됐다.

원인은 두 가지였다.

- 수신·소비의 `validateContext`는 임대 파일이 있고 세션만 다르면 거절했다. 임대가 지금 작업의 것인지, 풀린 것인지, 무활동인지, 다른 호스트인지는 보지 않았다. 작업을 닫는 `removeCursor`는 `lease.json`을 남기므로, 끝난 작업 뒤의 준비·접수 동의는 다른 세션이면 언제나 막혔다. `takeover`도 작업이 없으면 아무것도 하지 않아 사람이 풀 방법이 없었다.
- 조회의 `interactionView`는 임대를 보지 않아 수신과 판정이 달랐다.

## 변경 범위

현재 계약은 [대시보드 질문·동의 연동](../dashboard-interactions.md)의 요청 계약·지원 범위 문단과 [흐름도](../process-flow.md) §4.2 '임대·재개'에 있다. 여기에는 바뀐 자리만 적는다.

- `lease.ts`에 원래 세션 밖 경로의 판정 `leaseConflict`(문구·detail 포함)를 두었다. 대시보드 요청의 조회·수신·소비·적용·재개(`interactionService.ts`), Codex 권한 전달(`master/codexPermissions.ts`), 종료 세션 복원(`master/recovery.ts`)은 임대를 따로 읽지 않고 이 판정을 쓴다.
- 조회 출력에 `leaseConflict`를, 수신 거절의 `error.detail`에 `received:false`·`requestId`·`status`를 더했다. 수신 처리기의 `Stop`은 `internal` 대신 `invalid-state`로 낸다.
- `interactionSources.ts`: 질문 문서 요청의 원래 세션을 지금 작업의 임대에서만 고르고, 대시보드 답 전에 대상 변경·다른 채널의 응답으로 닫힌 동의의 요청을 `failed` 대신 `superseded`와 사유로 닫는다(적용 실패는 `failed` 그대로).
- 재개 지시(`continuationPrompt`)가 작업을 열기 전의 응답을 원래 지시서의 최초 접수로 잇고, 그 밖에 작업이 없는 응답에는 접수를 지시하지 않는다.
- 버전·템플릿 적용(`runtimeApply.ts` `applyHere`) 직후 확인 대상이 바뀐 미응답 동의를 대상 변경으로 닫는다(`consent.ts` `discardChangedConsents`). 버전 적용 잠금(`runtime.lock*`)은 동의 스냅샷에서 뺀다.

## 설계 판단

판정을 hook 의 `leaseDecision`에 맞춘 근거: 임대는 같은 작업의 상태를 두 세션이 모르는 사이 바꾸는 사고를 막는 장치이고, 작업이 없을 때(준비·접수) hook 도 임대를 보지 않는다. 다른 작업·대상의 임대, 푼 임대, 30분 무활동 임대는 다음 진행 명령이 넘겨받으므로 대시보드가 더 엄격할 근거가 없다. 반대로 같은 세션 ID라도 다른 호스트의 임대는 주인이 아니다 — 이전 수신·전달 판정은 호스트를 보지 않았다. Codex 권한 전달과 종료 세션 복원도 함께 맞췄다. 수신만 완화하면 다른 작업·무활동 임대에서 수신은 통과하는데 전달·복원은 막히기 때문이다. 적용(drain) 중 임대 충돌은 이전처럼 답을 보존한 `failed`로 남긴다.

재개 지시의 작업 전 판정: 활성 작업이 없다는 것만으로는 작업 전이라 할 수 없다 — 반영 뒤의 갱신·모델 동의도 작업이 없다. 그래서 접수·문서 세션이 있거나 접수 앞 동의(준비·문서·기준 커밋·요구사항)일 때만 최초 접수를 지시한다. 접수 ID는 접수 세션에서만 읽는다. 실행 기록의 `workId`는 그 실행을 시작할 때의 작업이라 끝난 작업일 수 있어 쓰지 않는다.

버전 적용: `runtime.json`·`templates.json`(`.code-agent`)과 스킬 사본(`.claude`·`.agents`·`.codex`)은 동의 스냅샷이 묶는 제어 루트에 있어(`SNAPSHOT_EXCLUDED` 밖), 적용은 대기 중인 동의를 그대로 승인할 수 없게 만든다. 그대로 두면 조회는 응답 가능으로 보이고 응답 때 폐기된다 — 이번 문제와 같은 불일치다. 그래서 적용 직후 실제 스냅샷이 바뀐 미응답 동의만 닫고, 응답을 시작했거나 대시보드 답을 받은 동의는 그 채널의 적용 대조에 맡긴다. 비교는 버전 적용 잠금 안에서 하므로 그 잠금 파일을 스냅샷에서 뺐다 — 빼지 않으면 같은 내용의 재반영도 모든 미응답 동의를 닫는다. 갱신 동의의 적용은 부모 프로세스가 동의 잠금을 쥔 채 새 릴리스의 자식을 기다린다. 자식은 잠금 주인이 같은 PC 의 부모이고 그 동의가 적용 중일 때만 잠금을 다시 잡지 않고 닫는다. 다른 주인이면 기다리지 않고 남기며, 남은 동의는 응답 때의 대조가 닫는다. 닫을 때는 새 상태 값을 만들지 않고 기존 대상 변경 폐기(`discard`)를 쓴다.

수신 거절은 질문 원장을 쓰지 않는다 — 처리기가 던지면 원장을 쓰기 전에 끝나므로 응답·commandId 가 남지 않고, 요청의 revision·challenge 도 그대로다. `interaction.respond`는 master 명령 기록도 거치지 않아 같은 commandId 로 다시 내도 처음부터 다시 검사한다. 다만 수신 중 동의 대상 변경을 발견하면 동의 쪽 폐기는 남고, 요청은 다음 조회의 동기화가 `superseded`로 닫는다.

승인·증거·작업 기록·질문 원장의 형식과 상태 값은 그대로이고 출력 필드만 더했으므로 `STATE_SCHEMA`를 유지한다.

## platform-gateway 적용

사람이 진행한다. 이 변경의 릴리스를 설치하고 프로젝트에서 `code-agent update --release <새 ID>`(또는 대시보드 확인)로 적용하면, 기준 커밋 동의 `040c8494…`는 대상 변경으로 닫히고 대시보드 요청 `6f492eed…`는 `superseded`와 사유로 남는다. 보류 사유였던 이 동의의 열린 창(30분)은 01:40:58Z에 지났고, 적용은 그때의 진행 중인 일을 다시 본다. master 에서 `run-mviughs6-fef84d43`을 `resume`하면 같은 세션 `038affb3`이 기준 커밋을 다시 준비하고, 승인 뒤 재개 지시가 원래 지시서로 최초 접수를 잇는다. 끝난 `YSIJ-263`의 임대는 작업이 없으므로 거절 근거가 아니다.

## 검증

Windows 11·Node 24.19.0, 기준 커밋 `f8c67b8`. `npm run build` 통과.

집중 시험(`dashboardLease.test` 5개, `dashboardContinuation.test` 9개, 모두 통과). 처음 더한 8개는 `src/agent`를 기준 커밋으로 되돌린 빌드에서 모두 실패했다. 뒤에 더한 6개 중 4개(작업·접수 없는 응답의 재개 지시, 같은 내용의 템플릿 재반영, 부모가 쥔 동의 잠금, 접수 중 질문 문서의 세션)는 해당 수정만 되돌린 빌드에서 실패했고, 2개(작업이 열린 뒤의 재개 지시, 수신 중 대상 변경의 `invalid-state`)는 동작을 고정하는 시험이다.

- 임대: 작업이 없을 때 끝난 작업의 임대, 다른 작업·대상·푼·무활동 임대는 조회·수신을 막지 않는다. 지금 작업을 다른 세션·호스트가 쥐면 조회부터 `canRespond:false`·`leaseConflict`, 수신은 `busy`·`received:false`이고 대기를 유지하며, 임대를 푼 뒤 같은 revision·challenge 로 낸 제출이 접수된다. 조회 뒤 소유·HEAD 가 바뀌면 수신 때 다시 거절한다. 접수 중 질문 문서 요청은 끝난 작업 임대의 세션이 아니라 접수를 연 실행의 세션에 묶인다.
- 재개: 중복 제출·적용 중 재시작에서 준비 커밋·적용·재개 실행이 한 번씩이다. 작업 전 기준 커밋 승인은 원래 실행의 `links`·세션으로 최초 접수를 잇고, 접수 중 준비 승인은 그 접수 ID 를 쓴다. 요구사항 동의로 작업이 열리면 그 작업을 잇고, 작업·접수가 없는 모델 변경 승인은 접수를 지시하지 않는다.
- 동의 정리: 버전 적용으로 확인 대상이 바뀐 미응답 동의는 대상 변경으로 닫히고 요청은 `superseded`이며, 같은 세션의 재준비 요청이 응답을 받는다. 같은 내용의 템플릿 재반영은 동의를 닫지 않는다. 갱신 동의 적용 중에는 부모가 쥔 잠금일 때만 닫는다. 수신 중 대상 변경은 `invalid-state`·`received:false`로 거절되고 요청은 다음 조회에서 `superseded`다.

master-agent 재현 스크립트(`consent-lease-repro.cjs`)를 수정 빌드에 연결하면 제출이 접수된다.

최종 전체 회귀: `npm test` 1,728개 중 1,724개 통과, 실패 0개, 플랫폼 생략 4개, 약 763초.

## 확인하지 않은 범위

- 사용자의 릴리스 저장소 설치, platform-gateway 적용, 실제 대시보드 화면 확인은 하지 않았다. master-agent 화면의 `received:false`·`leaseConflict` 표시는 master-agent 쪽에서 맞춘다.
- Codex 권한 전달·종료 세션 복원·`complete` 소비의 임대 갈래와, 다른 채널의 응답으로 닫힌 동의의 `superseded` 사유는 시험을 더하지 않았다(같은 판정 함수·같은 동기화 분기를 쓴다).
- 열린 창 안에서 `update`를 실행하면 적용은 예약되지만, 예약 기록(`runtime.json` `pending`)도 동의 스냅샷 대상이라 그 동의는 응답 때 폐기된다. 기존 동작이며 이번 범위 밖이다.
- 버전 적용의 진행 중 판정은 동의 종류의 영속 요청을 보지 않는다(`pendingInteractionMarker`). 대시보드 답을 받고 적용을 기다리는 동의가 있을 때 창 밖이면 적용이 진행되고, 그 동의의 적용은 대상 변경으로 실패해 드러난다. 기존 동작이며 위임 계약 영역이라 바꾸지 않았다.
