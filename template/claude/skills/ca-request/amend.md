# 같은 ID의 후속 요청 — 요구 변경안

확정된 요구가 있는 작업에 추가·수정·삭제·보완 요청이 오면 쓴다. 진행 중·완료 뒤 모두 같은 ID와 최초 종류를 유지한다. 새 ID로 나누지 않는다. 완료된 작업이면 같은 ID로 `request begin`을 다시 열고 시작한다.

1. Bash: `code-agent request` — `확정된 요구 — 개정 N`의 항목 ID와 새 ID 시작 번호, 변경 형식 예시가 나온다.
2. `request.json`을 그 형식으로 쓴다.
   - `original`: 사람이 **이번에** 준 글 그대로. 최초 원문과 앞 개정의 원문은 코드가 보존한다.
   - `revision`: `{"parent": N, "mode": "amend"}` — N은 위 확정 개정 번호.
   - `changes`: 원문이 말한 것만. 추가 `{"op":"add","section":"REQ|DONE|CON|OUT","id":"<새 ID>","text":"…"}`, 수정 `{"op":"modify","id":"<같은 ID>","text":"<고친 문장 전체>"}`, 삭제 `{"op":"remove","id":"…","reason":"<사람이 말한 이유>"}`.
   - 언급하지 않은 항목은 그대로 남는다. 다시 적지 않는다. 지우는 것은 사람이 지우라고 한 항목뿐이다.
   - 사람이 요구 전체를 바꾸라고 했을 때만 `"mode": "replace"`, 그 원문 인용 `replaceQuote`, 전체 목록(`requirements`·`done`·`constraints`·`outOfScope`)을 쓴다.
   - `sourceMap`: 이번 원문 인용 → 바뀐 항목 ID. 이미 있는 요구를 다시 말한 부분은 그 항목 ID로 잇는다.
   - 머리말 값은 바꿀 때만 고친다. 진행 중 작업의 `target`은 바꾸지 않는다 — 다른 대상이면 사람에게 묻는다.
3. 어느 항목을 바꾸는지, 추가인지 수정인지 원문으로 정할 수 없을 때만 묻는다.
4. SKILL.md 5로 제출한다. 대기 중 변경안이 있으면 그 변경까지 포함해 같은 parent로 다시 낸다. 같은 변경안·같은 원문의 재전송은 새 개정을 만들지 않는다. 오래된 parent로 겹친다는 거부를 받으면 1부터 다시 한다.
5. 확정 화면에는 변경과 최종 전체가 함께 나온다. 확정 전에는 진행·계획 배정이 멈춘다. 반려하면 직전 확정 개정으로 되돌아가 이어간다. 확정 결과가 분석으로 되감았다고 하면 브랜치·코드는 그대로이니 분석 단계부터 이어간다.
