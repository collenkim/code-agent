# 작업 지시서 규격 (Work Order)

code-agent 로 들어오는 **모든** 작업이 통과해야 하는 입구 규격이다.

목적은 셋이다.

1. **AI 가 추론으로 메우는 자리를 없앤다.** 정해지지 않은 것은 정해질 때까지 진행되지 않는다.
2. **문서를 통일한다.** 회사·프로젝트마다 내용은 달라도 봉투는 같다.
3. **사람이 통제한다.** 시작 조건과 승인 지점이 코드로 강제된다. 외부 툴(Jira 등) 연동은 이 봉투에 값을 채우는 일이 된다.

> 이 문서는 **규격**이며 구현이 아니다. 구현 상태는 [구현 순서](#구현-순서)에 적는다.

## 형식 — 봉투는 하나다

`--spec` 으로 넘기는 문서 중 **첫 장**의 머리말(front-matter)에 속성을 둔다.

```markdown
---
kind: refactor
id: PROJ-1421
title: 정산 배치의 트랜잭션 경계 정리
target: app/settlement
scope: [app/settlement, app/common/tx]
preserve: [SettlementFacade 공개 시그니처, settlement_* 테이블 스키마]
approver: team-lead
---

## 현재 구조의 문제
...
```

### 형식 규칙

| 규칙 | 이유 |
|---|---|
| 파일 **맨 첫 줄**이 `---` 이어야 한다 | 앞에 무엇이 오면 머리말인지 본문인지 구분이 모호해진다 |
| 값은 **문자열** 또는 **문자열 배열**만 | 중첩을 허용하면 회사마다 다른 모양이 다시 생겨 통일이라는 목적이 무너진다 |
| 배열은 `[a, b]` 또는 `-` 목록 | 둘 다 흔하다. 파서가 감당할 만한 범위다 |
| 알 수 없는 속성이 있으면 **거부** | 오타를 조용히 넘기면 "선언했는데 안 걸리는" 상태가 된다 |
| `kind` 는 정해진 값 중 하나여야 한다 | 오타 하나가 다른 파이프라인을 태운다 |
| 머리말은 `--spec` 문서 중 **정확히 한 장**에만 | 둘 이상이면 어느 것이 지시서인지 순서에 의존하게 된다. 0 장이든 2 장이든 거부한다 |

> **YAML 전체를 지원하지 않는 것은 의도다.** 의존성이 붙고(현재 `zod` + SDK 둘뿐), 중첩·앵커·멀티라인을 허용하는 순간 "봉투가 하나"라는 성질이 사라진다. 스칼라와 문자열 배열만 지원하는 파서는 의존성 0으로 쓸 수 있다.

### 왜 `kind` 마다 포맷을 나누지 않나

나누면 파서가 나뉘고, 외부 툴 매핑이 나뉘고, 사람이 "이 작업은 어느 양식이더라"를 매번 판단하게 된다. **통일성은 봉투가 하나일 때만 생긴다.** `kind` 가 바꾸는 것은 *어떤 속성이 필수인가*와 *본문에 무엇이 들어가야 하는가*뿐이다.

## 예약 속성

code-agent 가 **실제로 분기·검사에 쓰는** 속성이다. 이 목록은 늘리지 않는다 — 늘리는 만큼 회사별 차이를 담을 자리가 사라진다.

| 속성 | 값 | 파이프라인이 이것으로 무엇을 하나 |
|---|---|---|
| `kind` | 아래 5종 중 하나 | 필수 슬롯 집합 · 실행할 단계 · 계획의 모양을 결정한다 |
| `id` | 외부 티켓 키 또는 작업 식별자 | `out/` · 산출물 · 턴 기록이 이것에 묶인다. 감사 추적의 축 |
| `title` | 한 줄 | 사람이 목록에서 식별한다 |
| `target` | 대상 하나 또는 **여럿** (`kind` 마다 의미가 다르다) | "어디를" 이 없으면 시작할 수 없다. 대상마다 진행이 갈라진다 |
| `scope` | 이번에 건드려도 되는 경로 | 단계별 `outputDirs` 위에 얹히는 **작업 단위 경계** |
| `preserve` | 바뀌면 안 되는 것 | 개선·리팩토링의 본체. 계획·검수·게이트가 이것을 대조한다 |
| `approver` | 승인자 | 계획 승인 게이트(2차)가 기다리는 대상 |

### `scope` 와 `outputDirs` 는 다른 것이다

- `outputDirs` (매니페스트) — **이 단계가** 파일을 놓을 수 있는 곳. 프로젝트 상수다.
- `scope` (작업 지시서) — **이번 작업이** 건드려도 되는 곳. 작업마다 다르다.

둘 다 통과해야 반영된다. 교집합이 실제 허용 범위다.

### `preserve` 는 경로가 아니라 계약이다

`scope` 는 경로 목록이지만 `preserve` 는 "무엇이 보존되어야 하는가"다. 경로로 표현되는 것도 있고(스키마 파일) 아닌 것도 있다(공개 시그니처, 응답 포맷).

- 경로로 쓰인 것 → **코드가** 대조한다 (변경 시도 거부)
- 문장으로 쓰인 것 → **검수 단계가** 대조한다 (위반으로 보고)

둘을 섞어 쓸 수 있게 두되, 경로로 쓸 수 있는 것은 경로로 쓰는 편이 강하다. 코드의 대조는 모델의 선의를 거치지 않는다.

### 대상이 여럿일 때 — 대상마다 따로 돈다

`target` 은 배열을 허용한다. 지시서 하나가 대상 여럿을 다루면 **대상마다 독립된 왕복이 돈다.**

```
작업 지시서 1건  (id: PROJ-1421)
  ├─ 대상 A  →  out/PROJ-1421/a/   계획 · 질문 · 턴 루프 · 승인
  ├─ 대상 B  →  out/PROJ-1421/b/   〃
  └─ 대상 C  →  out/PROJ-1421/c/   〃
```

| | 지시서 단위 | 대상 단위 |
|---|---|---|
| 0차 게이트 (속성) | **한 번** | — |
| 1차 게이트 (슬롯) | — | **대상마다** |
| 계획 · 질문 · 턴 기록 | — | **대상마다** |
| 2차 승인 | — | **대상마다** |
| `scope` · `preserve` | **한 번** (상한선) | 매니페스트가 더 좁힌다 |

- **슬롯 검사가 대상마다 도는 이유**는 대상마다 필요한 것이 다르기 때문이다. 도메인 A 에는 상태 전이가 있고 B 에는 없다. 본문에서 그 대상의 근거를 찾지 못하면 **그 대상에 대한 질문**이 된다 — 질문에는 이미 대상 라벨이 붙는다.
- **승인이 대상마다인 이유**는 계획이 대상마다 다르기 때문이다. 대상 A 의 계획을 승인한 것이 B 의 계획 승인이 될 수는 없다. 승인 기록은 같은 `id` 아래 묶인다 — 티켓 하나에 코멘트 여럿인 것과 같다.
- **`scope`·`preserve` 는 지시서 단위로 남긴다.** 대상별로 두면 속성이 중첩 구조가 되어 "문자열 배열만"이라는 형식 규칙이 깨진다. 지시서 값은 **상한선**이고, 대상별 실제 범위는 매니페스트가 그 안에서 계산한다.
- **대상 간 의존은 전제하지 않는다.** 배열 순서는 순서일 뿐 의존이 아니다. 정말 순서가 필요하면(공통 모듈을 먼저 고쳐야 한다면) 지시서를 나눈다. 나누는 편이 승인 단위로도 옳다.

> 대상별로 `preserve` 가 정말 달라야 한다면, 그건 한 지시서로 묶을 작업이 아니라는 신호다.

## kind — 작업 종류

기존 README 의 "세 가지 모드"를 이 속성이 흡수한다. 모드는 사람이 기억하는 개념이었고, `kind` 는 문서에 적혀 코드가 읽는 값이다.

| `kind` | 언제 | 산출물 | 근거 |
|---|---|---|---|
| `bootstrap` | 신규 프로젝트를 처음 만들 때 | `code-agent.json` · 컨벤션 문서 · 공통 모듈 | 사람의 결정 + 공식 스캐폴더 출력 |
| `adopt` | 기존(레거시) 저장소에 도입할 때 | `code-agent.json` · 컨벤션 문서 · 기본 문서 초안 | **이미 있는 코드** |
| `feature` | 기능·도메인을 추가할 때 | 새 코드 + 테스트 | 같은 저장소의 참조 표준 |
| `fix` | 결함을 고칠 때 | 변경된 코드 + 재현 테스트 | 재현 조건 + 기존 코드 |
| `refactor` | 동작을 바꾸지 않고 구조를 고칠 때 | 변경된 코드 | **보존 조건** + 기존 테스트 |

```
신규 저장소:   bootstrap → feature(첫 도메인) → feature · fix · refactor …
레거시 저장소: adopt     → feature · fix · refactor …
```

### `kind` 가 결정하는 세 가지

| | 어떻게 |
|---|---|
| **어느 슬롯이 필수인가** | 입력 규격(`spec-schema.json`)의 슬롯마다 `requiredFor: ["feature", "fix"]` |
| **어느 단계를 도는가** | 매니페스트 `stages[]` 의 `kinds` 필터. `refactor` 는 Entity~Controller 를 순차 생성하지 않는다 |
| **계획의 모양** | `feature` 는 *만들 파일 목록*, `refactor` 는 *고칠 파일 + 보존 조건*. 계획 스키마가 갈라지는 지점 |

세 번째가 실제 작업량이다. 현재 계획 스키마(`src/core/plan.ts`)는 `domainName`·`domainDirName`·`files[]` 를 필수로 요구해 `refactor` 에 채울 값이 없다.

## kind 별 필수 속성

| 속성 | `bootstrap` | `adopt` | `feature` | `fix` | `refactor` |
|---|:---:|:---:|:---:|:---:|:---:|
| `kind` | 필수 | 필수 | 필수 | 필수 | 필수 |
| `id` | 필수 | 필수 | 필수 | 필수 | 필수 |
| `title` | 필수 | 필수 | 필수 | 필수 | 필수 |
| `target` | 프로젝트명 | 저장소 경로 | 도메인·모듈명 | 증상이 나는 지점 | 대상 경로 |
| `scope` | — | 문서 출력 위치 | 매니페스트가 정함 | **필수** | **필수** |
| `preserve` | — | — | 권장 | **필수** | **필수** |
| `approver` | 프로젝트가 정함 | 프로젝트가 정함 | 프로젝트가 정함 | 프로젝트가 정함 | 프로젝트가 정함 |

- `bootstrap` 에 `preserve` 가 없는 것은 **보존할 것이 아직 없기 때문**이다. 자리를 비워 두는 게 아니라 해당이 없다.
- `feature` 의 `scope` 는 도메인 디렉토리가 매니페스트에서 계산되므로 생략할 수 있다. 명시하면 더 좁힌다.
- `approver` 의 필수 여부만은 프로젝트가 정한다. 승인자 개념이 없는 조직도 있고, 없는데 필수로 걸면 아무 작업도 시작되지 않는다.

## 본문 — 강제하지 않는다

본문 섹션은 **권장이지 검사 대상이 아니다.**

검사하는 것은 형식이 아니라 **내용이 있느냐**다. 입력 규격(`spec-schema.json`)이 선언한 슬롯이 본문 어디에선가 근거와 함께 읽히면 통과한다. 섹션 제목이 무엇이든 상관없다.

> **이 완충이 없으면 레거시에 못 들어간다.** 이미 갖고 있는 요구사항 문서를 양식에 맞춰 다시 쓰게 만드는 순간, 도입 비용이 도입 가치를 넘는다.

### kind 별 권장 섹션

<details open>
<summary><b>bootstrap</b></summary>

- 무엇을 만드는지 · 누가 쓰는지
- 주요 도메인 목록 (이름만이라도)
- 이미 정해진 제약 — 사내 표준, 운영 환경, 기존 시스템 연동

</details>

<details open>
<summary><b>adopt</b></summary>

- 저장소 개요 — 무엇을 하는 시스템인지
- 도입 목적 — 무엇부터 code-agent 로 하려는지
- 알려진 문제 — 조사 단계가 확인할 것

</details>

<details open>
<summary><b>feature</b></summary>

- 요구사항 · 워크플로우 · 상태 전이
- 데이터 정의 — 필드 · 타입 · 제약 (DDL 을 그대로 붙여도 된다)
- API · 화면 정의
- **수락 기준** — 무엇이 통과하면 끝인가

</details>

<details open>
<summary><b>fix</b></summary>

- **재현 조건** — 없으면 재현 테스트를 만들 수 없다
- 현재 동작 · 기대 동작
- 영향 범위 — 같은 원인이 다른 곳에도 있는지
- **수락 기준**

</details>

<details open>
<summary><b>refactor</b></summary>

- 현재 구조의 문제
- 목표 구조
- **동작 보존 근거** — 어떤 테스트가 통과하면 보존된 것인가
- **하지 않을 것** — 이번에 같이 고치고 싶어질 것들을 미리 못 박는다

</details>

`refactor` 의 마지막 항목이 중요하다. 리팩토링에서 실패는 "못 고쳐서"가 아니라 **"같이 고쳐서"** 일어난다.

## 프로젝트 확장 속성

회사·프로젝트마다 다른 것은 전부 여기다. `code-agent.json` 옆에 선언한다.

```json
{
  "workOrder": {
    "attributes": [
      { "name": "requester",  "required": true },
      { "name": "priority",   "required": true,  "values": ["P1", "P2", "P3"] },
      { "name": "system",     "required": true,  "values": ["billing", "crm", "batch"] },
      { "name": "sprint",     "required": false },
      { "name": "riskLevel",  "required": true,  "values": ["low", "high"] }
    ],
    "requireApprover": true
  }
}
```

- **code-agent 는 존재와 값 유효성만 검사한다.** 파이프라인은 이 값들을 쳐다보지 않는다.
- 이 선을 지켜야 특정 회사의 지식이 에이전트 소스에 들어가지 않는다. 예약 속성과 확장 속성을 가르는 기준은 하나다 — **파이프라인이 그 값으로 분기하는가.**

## 게이트 4층

| 층 | 검사 | 검사 주체 | 실패 시 |
|---|---|---|---|
| **0차** | 작업 지시서 속성 — 존재 · 값 유효성 | **코드** | **프롬프트를 만들지 않는다. 모델에 한 글자도 가지 않는다** |
| **1차** | `kind` 별 필수 슬롯 — 근거 인용 포함 | 모델 추출 + **코드 대조** | 질문으로 전환 → `blocked` |
| **2차** | 계획 승인 | **사람** | 승인 전에는 생성 단계로 넘어가지 않는다 |
| **3차** | 경계 · do-not-touch · `preserve` · 자가검증 | 코드 + 모델 | 반영 거부 또는 재시도 |

### 불변식 — 층은 건너뛸 수 없다

**앞 층을 통과하지 않은 상태에서 뒤 층으로 갈 수 없다.** 0차가 통과되지 않았는데 1차가 도는 상태, 1차가 미충족인데 계획 승인을 받는 상태는 만들지 않는다.

| | |
|---|---|
| 0차 우회 옵션 | **없다.** 만들지 않는다 |
| 1차 우회 옵션 | 현재 `--force` 가 미결 질문을 무시하고 진행한다 — **같은 구멍이므로 없앤다** |
| 2차 우회 옵션 | 없다 |

> 예외를 하나 두면 그 자리가 우회로가 된다. 급할 때 쓰라고 만든 옵션은 급할 때만 쓰이지 않는다.

층을 건너뛰지 않는다는 것은 **구현 순서에도 적용된다.** 0차 없이 1차만 먼저 넣는 중간 상태를 만들지 않는다 — [구현 순서](#구현-순서)의 A 가 곧 0차다.

### 0차 — 모델을 부르기 전에 막는다

현재 `decideTarget` 의 `blocked` 는 질문 미답변에만 걸리고, 그건 이미 모델을 한 번 부른 뒤다. **0차는 그보다 앞, 계획 단계 이전이다.** 속성이 없으면 프롬프트 자체가 만들어지지 않는다.

이 층이 "1차로 막는다"의 실체다. 여기가 없으면 통제는 모델이 협조하는 동안만 유지된다.

무엇까지 검사하나 — **여기서 걸리는 것은 전부 사람이 문서를 고쳐야 풀린다.**

| 검사 | |
|---|---|
| 머리말이 정확히 한 장에 있는가 | 형식 |
| 필수 속성이 `kind` 별로 다 있는가 | 존재 |
| `kind` 가 5종 중 하나인가 · 확장 속성이 선언된 `values` 안에 있는가 | 값 |
| 모르는 속성이 섞여 있지 않은가 | 오타 |
| `scope` 경로가 대상 저장소에 **실제로 있는가** | 실재 |
| `target` 이 경로인 종류(`adopt`·`fix`·`refactor`)면 그것도 | 실재 |

마지막 두 줄이 중요하다. 경로 오타는 첫 프롬프트가 아니라 **작업을 접수하는 자리**에서 드러나야 한다. 서버가 작업을 만들 때 매니페스트·컨벤션·참조 표준을 실제로 읽어 보는 것과 같은 발상이다.

**`target` 의 실재를 모든 종류에 묻지는 않는다.** 종류마다 그 값이 가리키는 것이 다르기 때문이다 — `bootstrap` 의 대상은 프로젝트 이름이고, `feature` 의 대상은 **이제부터 만들** 도메인이라 아직 디렉토리가 없다. 실재를 물을 수 있는 것은 이미 있는 코드를 다루는 셋뿐이다. `preserve` 도 묻지 않는다 — 경로와 문장을 섞어 쓰기 때문이다.

### 1차 — 질문을 코드가 만든다

모델은 자유형 본문에서 슬롯을 채우되 **원문 인용을 함께** 내야 한다. 인용이 없는 값은 코드가 미충족으로 처리한다.

> **이것이 추론 방지의 실제 장치다.** 모델이 관행으로 채우면 인용을 붙일 수 없고, 인용이 없으면 자동으로 질문이 된다. 질문 생성이 모델의 자각에 의존하지 않는다.

무엇이 필요한지는 프로젝트가 선언한다 — `code-agent.json` 옆의 `spec-schema.json` 이다. 선언하지 않은 프로젝트에서는 이 층이 돌지 않는다.

```json
{
  "slots": [
    { "key": "data",   "title": "저장할 데이터 항목", "requiredFor": ["feature"],
      "question": "저장할 데이터 항목은 무엇인가요? 이름과 의미." },
    { "key": "repro",  "title": "재현 조건",          "requiredFor": ["fix"],
      "question": "어떤 조건에서 재현되나요?" },
    { "key": "accept", "title": "수락 기준",          "requiredFor": ["feature", "fix", "refactor"],
      "question": "무엇이 통과하면 끝인가요?" }
  ]
}
```

`requiredFor` 가 `kind` 와 만나는 자리다. 같은 문서라도 `fix` 면 재현 조건이 필수이고 `feature` 면 아니다.

### 뽑아 놓은 항목은 캐시가 아니라 파생물이다

추출 결과는 `out/.spec-slots.json` 에 스펙 해시와 함께 남는다. **스펙이 바뀌면 그 순간 무효가 되어 다시 뽑는다.**

| | |
|---|---|
| 정본 | 언제나 문서다. 파생물이 문서를 대신하지 않는다 |
| 무효 조건 | 스펙 해시 불일치. `orderHash`·`planHash` 와 같은 장치다 |
| 왜 필요한가 | 앞서 뽑은 것을 그대로 믿으면 **문서를 고쳐 게이트를 우회**할 수 있다 |

### 사람이 답한 것도 항목을 채운다

질문에는 어느 항목에서 나왔는지가 붙는다(`intake:states`). 사람이 답을 적으면 그 항목은 채워진 것으로 보고 **다시 묻지 않으며**, 그 답이 계획 프롬프트에 그대로 실린다. 모델을 한 번 더 부르지 않는다.

### 확정된 항목은 축약해 싣는다

확정된 항목은 근거와 함께 계획·생성 프롬프트 머리에 실린다. 같은 이유로 **생성 프롬프트의 컨벤션 전문 덤프도 걷어냈다** — 계획 단계가 이미 "이번에 실제로 걸리는 규칙만" 근거와 함께 뽑아 두는데, 그것을 버리고 문서를 통째로 싣던 자리였다.

- 축약본에는 **근거가 붙는다.** 근거 없는 축약은 요약이 아니라 소실이다.
- 모자라면 모델이 `read` 로 원문을 확인한다. **그 요청이 잦아지면 축약이 지나쳤다는 신호**이고, `log` 의 탐색 요청 수가 그것을 알려 준다.
- 검수 단계는 축약본이 아니라 **컨벤션 원문**을 본다. 대조하는 쪽은 정본을 봐야 한다.

### 2차 — 최종 목표에 닿는 지점

계획이 나오면 곧장 생성으로 가지 않고 승인을 기다린다. `approver` 속성이 예약인 이유가 여기다. 기록은 아래 [승인 기록](#승인-기록)에 남는다.

## 승인 기록

### 어디에 남기나 — 대상 저장소 안이다

```
<repo>/.code-agent/approvals/
  ├─ PROJ-1421.jsonl              승인 사건 원장 (append only)
  └─ PROJ-1421/
       ├─ app-settlement-1.plan.json   승인 시점 계획 스냅샷
       └─ app-settlement-2.plan.json   재승인 때 diff 의 기준이 된다
```

`out/` 이 아니라 **저장소 안**이다. 이유가 셋이다.

| 이유 | |
|---|---|
| `out/` 은 지워진다 | staging 디렉토리는 확인 후 지우는 것이 정상이다. 승인 이력이 거기 있으면 같이 사라진다 |
| 승인은 팀의 기록이다 | 버전 관리되어야 하고, PR 에서 읽혀야 하고, 다른 사람이 볼 수 있어야 한다 |
| 감사 추적의 정본 | 외부 툴에 미러링하더라도 **정본은 이 파일이다** |

> **"대상 저장소는 건드리지 않는다"의 예외다.** 그 약속은 *생성물*에 대한 것이고, 승인 기록은 생성물이 아니라 통제 기록이다. `--build`·`--test` 가 임시 worktree 로 예외를 두는 것과 같은 성격이며, 여기서는 예외를 두는 편이 목적에 맞다.

### 무엇을 남기나

한 줄이 승인 사건 하나다. append 만 하고 고치지 않는다.

```jsonl
{"id":"PROJ-1421","target":"app/settlement","kind":"refactor","orderHash":"sha256:7d10…","planHash":"sha256:9f2c…","decision":"approved","approver":"team-lead","at":"2026-08-21T10:14:02+09:00","comment":"보존 조건 확인함"}
{"id":"PROJ-1421","target":"app/common/tx","kind":"refactor","orderHash":"sha256:7d10…","planHash":"sha256:41ab…","decision":"rejected","approver":"team-lead","at":"2026-08-21T10:16:40+09:00","comment":"공통 모듈은 별도 지시서로"}
```

- **해시가 핵심이다.** 승인은 "이 작업"이 아니라 **"이 계획, 이 지시서"** 에 대한 것이다. 둘 중 하나가 바뀌면 해시가 달라지고 승인은 자동으로 무효가 된다. 이것이 없으면 *승인받고 다른 것을 만드는* 구멍이 열린다.
- `target` 이 있는 이유는 [대상마다 따로 돌기](#대상이-여럿일-때--대상마다-따로-돈다) 때문이다. 같은 `id` 아래 대상 수만큼 줄이 쌓인다.
- `rejected` 도 남긴다. 반려는 지워야 할 실패가 아니라 **가장 값진 기록**이다.
- JSONL 인 이유는 append 가 충돌 없이 병합되고, diff 에서 한 줄이 한 사건으로 읽히기 때문이다.

### 무효가 되는 것은 둘이다

계획만 잠그면 구멍이 남는다. **작업 지시서를 고치는 쪽이 더 위험하다** — `preserve` 한 줄을 지우면 3차 게이트가 그냥 통과한다.

| 무엇이 바뀌면 | 무효가 되는 것 | 어디부터 다시 |
|---|---|---|
| 계획 (`planHash`) | 그 대상의 승인 | **2차** — 재승인 |
| 작업 지시서 (`orderHash`) | 그 지시서의 **모든 대상** 승인 | **0차** — 속성 검사부터 |

지시서가 바뀌면 슬롯 충족 여부도, 경계도 다시 봐야 한다. 계획만 다시 승인받게 두면 **속성을 고쳐 통제를 우회하는 경로**가 그대로 열려 있다.

### 재승인 — 달라진 부분만 보여 준다

승인이 무효가 되면 계획 전체를 처음부터 다시 읽히지 않는다. **직전 승인본과의 차이만 제시한다.**

```
[승인됨] planHash: 9f2c…     ← 스냅샷이 남아 있다
[변경됨] planHash: 41ab…
─────────────────────────────
  파일   + facade/SettlementQueryFacade.java
         - handler/SettlementBatchHandler.java
  규칙   ~ "트랜잭션은 Handler 에서 연다"
           → "트랜잭션은 Facade 에서 연다"
```

| | |
|---|---|
| **스냅샷을 남긴다** | 해시만으로는 diff 를 만들 수 없다. 승인 시점의 계획 전문을 `.code-agent/approvals/<id>/<target>-<n>.plan.json` 에 남긴다 |
| **필드 단위로 비교한다** | 텍스트 diff 가 아니라 계획 구조(`files` · `conventions` · `conflicts`)의 항목 비교다. 문구만 바뀐 것과 파일이 늘어난 것이 같은 무게로 보이면 안 된다 |
| **승인 단위는 여전히 계획 전체다** | 제시만 diff 다. *바뀐 부분만 승인*으로 만들면 승인받지 않은 부분이 섞여 들어가는 구멍이 생긴다 |

> 이 흐름이 `planHash` 를 **계획 전체**로 잡아도 되게 해 준다. 판단 근거 문장 한 글자만 바뀌어도 승인은 무효가 되지만, 사람이 보는 것은 "문구 한 줄이 바뀌었다"는 diff 한 줄이라 승인 부담이 실제로는 늘지 않는다.

### 이 파일은 신원을 증명하지 않는다

`approver` 에 누가 적혔든, 로컬 도구는 그 사람이 실제로 승인했는지 알 수 없다. **자기가 자기를 승인할 수 있다.**

- 이 파일은 **기록**이지 인증이 아니다. 규격이 보장하는 것은 "승인 없이는 진행되지 않는다"까지다.
- 신원의 증명은 저장소 밖에 있다 — 커밋 서명, PR 승인, Jira 의 권한 모델. **미러링이 필요한 진짜 이유가 이것이다.**
- 그러므로 이 기록을 감사 증거로 쓰려면 커밋되어야 한다. 커밋되지 않은 승인 기록은 아무것도 증명하지 않는다.

### Jira 코멘트는 미러링이다

승인이 기록되면 어댑터가 그 줄을 읽어 해당 티켓에 코멘트를 남긴다.

```
승인 파일(정본)  →  어댑터  →  Jira 코멘트(사본)
```

- **코어는 파일까지만 한다.** 티켓에 어떻게 쓰는지는 코어가 모른다 — 작업 지시서가 "어디서 왔는지"를 담지 않는 것과 같은 이유다.
- 정본이 파일이므로 Jira 가 없거나 죽어 있어도 승인 절차는 그대로 돈다. 나중에 붙일 때 과거 기록을 밀어 넣을 수도 있다.
- 어댑터는 API 를 쓰므로 **지금 범위 밖이다.** 지금은 파일까지다.

## 레거시 도입 — 기본 문서는 어디서 오나

레거시에도 기본 문서가 있어야 한다. 다만 **사람이 백지에서 쓰는 것이 아니다. 코드가 정본이고, `adopt` 가 초안을 뽑아 사람이 확정한다.**

| 영역 | 레거시에서 어디서 오나 | 사람이 하는 일 |
|---|---|---|
| 스택 · 의존성 | `build.gradle` · `package.json` · lock 파일 | **정책만** 쓴다 ("새 의존성 추가 금지" 등) |
| 아키텍처 · 구조 | 실제 디렉토리 구조 + 참조 도메인 | 계층 이름과 의존 방향을 확정 |
| 코드 컨벤션 | 기존 코드에서 추출 | 추출된 규칙을 검토 · 확정 |
| 테스트 전략 | 테스트 디렉토리 · 프레임워크 · CI 설정 | 목킹 정책 등 코드에 안 드러나는 것 |
| 실행 환경 | `application.yml` · `docker-compose` · `.env.example` | 시크릿 주입 방식 확인 |
| 변경 금지 계약 | 공개 인터페이스 · 마이그레이션 파일 | **확정** — 여기가 가장 중요하다 |
| 보안 · 권한 | 기존 인증·인가 코드 | **확정** |

> **사람이 백지에 써야 하는 것은 "정책" 뿐이다.** 나머지는 전부 코드에 이미 있고, 추출은 결정론적으로 할 수 있는 부분이 많다. 의존성 목록을 사람이 쓰게 하면 반드시 실제와 어긋난다 — 빌드 파일을 코드가 읽어 프롬프트에 넣는 편이 정확하고 최신이다.

### 그래서 `adopt` 는 한 번 도는 작업이다

`adopt` 도 작업 지시서를 요구한다. `id`(티켓) · `target`(저장소) · `approver`(확정할 사람)가 필요하고, 산출물이 이후 모든 작업의 근거가 되므로 승인이 반드시 필요하다. 준비 과정이 아니라 **가장 중요한 한 건의 작업**이다.

## 외부 툴 연동

**속성 규격이 곧 필드 매핑표가 된다.**

| Jira | 작업 지시서 |
|---|---|
| 이슈 키 | `id` |
| 요약 | `title` |
| 이슈 타입 | `kind` (매핑 필요 — Story→`feature`, Bug→`fix` 등) |
| 컴포넌트 · 라벨 | `target` · 프로젝트 확장 속성 |
| 담당 검토자 | `approver` |
| **이슈 코멘트** | **승인 기록 한 줄** (반대 방향 — 파일에서 티켓으로) |

- 방향이 둘이다. **들어올 때**는 티켓이 머리말이 되고, **나갈 때**는 승인 기록이 코멘트가 된다.
- 지금은 사람이 머리말을 쓴다. 나중에 어댑터가 티켓에서 머리말을 **생성**한다.
- **코어는 한 줄도 바뀌지 않는다.** `turn.ts` 가 전송 방식을 담지 않게 쓰인 것과 같은 이유로, 작업 지시서도 "어디서 왔는지"를 담지 않는다.
- 역방향으로 `id` 가 필수라 **티켓 없는 작업이 시작되지 않고**, `out/` 의 모든 산출물이 티켓에 묶여 추적된다.

## 구현 순서

`kind` 5종을 한 번에 열지 않는다. `feature` 는 이미 도는 경로이고, 나머지는 계획 스키마를 갈라야 한다.

단계에 **글자**를 쓰는 것은 의도다. 게이트가 `0~3차` 이므로 구현 단계까지 숫자로 매기면 "1"이 두 가지를 가리킨다.

| | 무엇 | 검증 | 상태 |
|---|---|---|---|
| **A** | 머리말 파서 + **0차 게이트** · `--force` 제거 | 속성이 없으면 프롬프트 생성 자체가 실패한다. `kind: feature` 기존 경로는 그대로 통과한다 | **완료** |
| **B** | 입력 규격(`spec-schema.json`) + **1차 게이트** · 축약 주입 | `kind` 별 필수 슬롯 미충족 → 질문 N 건 + `blocked` | **완료** |
| **C** | **2차 승인 게이트** + 승인 원장 · 계획 스냅샷 · 재승인 diff | 미승인 상태에서 다음 프롬프트를 요청하면 "승인 대기"로 멈춘다. 계획이 바뀌면 재승인이 **달라진 항목만** 띄우고, 지시서가 바뀌면 0차부터 다시 돈다 | 남음 |
| **D** | 여러 대상 — 대상별 루프 | 대상 2개짜리 지시서가 `out/<id>/` 아래 두 갈래로 갈라져 각각 질문·승인을 받는다 | 남음 |
| **E** | `kind: refactor` — 계획 스키마 분기 + `preserve` 대조 | `preserve` 대상을 바꾸려는 시도가 반영 거부된다 | 남음 |
| **F** | `kind: fix` · `adopt` 보강 | 재현 테스트가 먼저 실패하고, 수정 후 통과한다 | 남음 |

A~C 는 `kind` 가 하나뿐이어도 값이 나온다. E 부터가 실제 확장이다. Jira 어댑터는 API 를 쓰므로 이 목록 밖이다.

> **A 가 곧 0차 게이트다.** 0차 없이 1차만 먼저 넣는 중간 상태는 만들지 않는다 — [층은 건너뛸 수 없다](#불변식--층은-건너뛸-수-없다)가 구현 순서에도 적용된다.

> **A 를 넣는 순간 기존 실행도 전부 `kind: feature` 를 명시해야 돌아간다.** 의도된 파괴적 변경이다 — "속성이 있을 때만 진행"이 목적이므로 예외를 두면 그 자리가 우회로가 된다.

---

## 정하지 않은 것

- **`id` 를 다시 쓸 때.** 같은 티켓으로 두 번 돌리면 `out/` 이 겹치고 원장에 두 회차가 섞인다. 회차를 나누나, 이어붙이나.
- **`preserve` 의 문장형 항목을 검수 단계가 얼마나 강하게 대조할 수 있나.** 경로형은 확실하지만 문장형은 모델 판단이다.
- **`kind` 를 프로젝트가 추가할 수 있게 할지.** 지금은 5종 고정이다. 추가를 허용하면 파이프라인 분기까지 선언 대상이 된다.
- **review-agent 를 승인 앞에 넣을지.** 2차 게이트가 생기면 "리뷰를 통과해야 승인 화면에 올라간다"는 자리가 생긴다. 지금은 범위 밖이다.

### 정해진 것 (이 판에서 닫힘)

| | |
|---|---|
| 승인 기록 위치 | 대상 저장소의 `.code-agent/approvals/` — `out/` 이 아니다 |
| Jira 연동 | 승인 파일이 정본, 티켓 코멘트는 미러링. 어댑터는 나중 |
| 여러 대상 | 대상마다 따로 돈다. `scope`·`preserve` 만 지시서 단위 |
| 게이트 건너뛰기 | 불가. `--force` 는 없앤다 |
| `planHash` 범위 | 계획 **전체**. 재승인 diff 가 부담을 흡수한다 |
| 재승인 | 달라진 항목만 제시. 단 **승인 단위는 계획 전체** |
| 지시서 변경 | `orderHash` 로 잠근다. 바뀌면 모든 대상의 승인이 무효, 0차부터 다시 |
| 신원 | 이 파일은 증명하지 않는다. 기록일 뿐이고, 증명은 커밋·PR·티켓에 있다 |
