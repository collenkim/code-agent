# 테스트 수정 창

얼어 있는 `kind: test` 파일의 **테스트 구현 오류**만 고치는 길이다. ⑦ 의 케이스·기대 결과와 AC 는 그대로 둔다.

쓰는 때 — 실패 로그가 테스트 자체의 결함을 가리킬 때다: 원인 없는 예외에 `getCause()` 를 단언함(null), `List.of(…, null)` 처럼 null 을 받지 않는 컬렉션, 결과에 TC 가 인식되지 않는 표기, 빈 디렉터리와 파일 존재를 가르지 못한 판정. 구현이 틀렸으면 구현을 고치고, 기대 결과를 바꿔야 통과하면 창이 아니라 질문·재계획이다.

1. Bash: `code-agent test-repair <TC-ID…> --cause <assertion|fixture|notation|filesystem> --reason "<실패 로그 줄·파일:줄과 테스트 구현 오류인 이유>"` — 원인 하나에 창 하나(TC 10개까지). 동결·마지막 실행에서 실패한 ⑦ TC·그 TC 가 있는 계획 테스트 파일·남은 회차는 코드가 본다.
2. 출력의 `전문`을 `ca-tester` 에게 맡긴다. 담당은 백그라운드로 끝날 수 있다 — 결과(호출 결과·인계 메시지·완료 알림 중 먼저 온 것)를 받은 그 턴에 다음 단계로 간다. 창의 파일은 그 담당만 쓸 수 있다(hook). 메인이 고치지 않는다.
3. 끝나면 `code-agent verify --json`. check 가 새 회차를 열며 창을 판정한다 — TC 토큰이 그대로이고, 창의 TC 가 인식되는 꼴로 있고, 건너뛰기 표지(`@Disabled`·`skip`·`assume` 등)가 늘지 않았으면 받아들여 동결 기준을 갱신한다. 아니면 거부 사유가 test 게이트에 뜨고 창은 열린 채다 — 같은 담당이 다시 고치거나 되돌린다.
4. 받아들인 창은 다음 리뷰 회차 context 에 원인·근거·단언 수 변화와 함께 실린다. 리뷰어가 AC·보안 요구를 약하게 했는지 본다.

창은 고쳐 쓰기 회차 안에서 돈다. 사람에게 물어야 하면 질문에 `[Kind]: test` 를 적는다 — 계획 문서(plan·critic)만 다시 돈다.
