# code-agent 프로세스와 사용성 검토 보고서

> 아래는 수정 전 커밋의 검토 기록이다. 사용자 요청에 따른 수정 결과는 [후속 보완 보고서](2026-10-01-process-improvements.md)를 참조한다. 기존 `process-probes.cjs`는 수정 전 반례를 검증하는 스크립트이며 수정 후 회귀 테스트가 아니다.

**종합 판정: 부분 충족.** 코드 작성·검증·리뷰를 나누고 승인된 범위를 지키는 기반은 구현돼 있다. 그러나 **요구사항만 주고 최소한의 선택으로 개발을 완료하는 초보자용 흐름**은 아직 충족하지 못한다. 문서 준비로 연결되지 않는 접수 흐름, 실제로 실행되지 않은 테스트의 통과 판정, 요구사항 누락을 놓치는 추적 범위를 우선 보완해야 한다.

이 보고서는 2026년 10월 1일 사용자가 제시한 목표와 현재 저장소를 대조한 결과다. 제품 소스와 스킬은 수정하지 않았다. 검토 보고서·재현 스크립트·결과만 추가했다.

| 항목 | 기준 |
|---|---|

| 환경 | Windows, Node `v24.19.0`, npm `11.17.0` |

| 충족 | 해당 범위의 구현과 검증 근거가 있음 |
| 부분 충족 | 기반은 있으나 요청한 흐름·강제·사용성 일부가 부족함 |
| 미충족 | 요청한 동작을 제공하지 않거나 반례가 재현됨 |
| 미검증 | 실제 사용 세션 등 판단에 필요한 실행 증거가 없음 |

**CLI가 강제하는 것과 스킬이 모델에게 지시하는 것을 구분했다.** 재현 스크립트의 승인 기록은 테스트용으로 작성했다. 실제 사용자 승인이나 Claude Code 서브에이전트 실행을 관측한 것으로 보지 않았다. AWS AI-DLC와의 시간·질문 수·품질 비교 실험은 수행하지 않았으므로 우열을 주장하지 않는다.

## 실행 결과

| 검증 | 결과 | 해석 |
|---|---|---|
| `npm test` | 522개 중 518 통과, 실패 0, 건너뜀 4, 약 255초 | 컴파일 및 기존 자동 테스트 통과 |
| 환경에 따른 건너뜀 | 대소문자 구분 관련 2개, Windows 파일 권한 관련 2개 | 제품이 검사하는 TC의 건너뜀 문제와 별개 |
| 추가 재현 | 11개 관찰 기록, 핵심 반례는 assertion으로 확인 | 아래 결함·한계를 재현했다는 뜻이며 제품 합격을 뜻하지 않음 |
| 실제 모델 완주 | 미실행 | 코드 생성 품질·질문 횟수·초보자 성공률은 미검증 |

최초 테스트 시도는 샌드박스의 자식 프로세스 생성 제한 `EPERM`으로 실행되지 않았다. 허용된 재실행에서 위 결과를 얻었다. 전체 로그 일부는 도구 출력에서 잘렸으며 [실행 요약](evidence/test-summary.json)은 최종 집계만 보존한다.

추가 재현은 [스크립트](evidence/process-probes.cjs)와 [관찰 결과](evidence/process-probes.json)에 보존했다. `npm run build` 후 `node doc/reviews/evidence/process-probes.cjs`로 다시 실행할 수 있다. 임시 저장소만 만들고 정리하며, 대상 제품 저장소에 작업 브랜치나 승인 기록을 만들지 않는다.

추가 재현의 build 명령은 통과만 반환하는 fixture이고, 테스트는 실제 `node:test`를 실행했다. 리뷰 결과도 fixture로 작성했다. 따라서 반영 전 자동 검사 통과는 검사 규칙의 반례이며, 실제 애플리케이션 빌드나 독립 모델 리뷰의 품질 검증 결과는 아니다.

U8의 충족은 **단계 분리 자체**에 대한 판정이다. 각 단계의 산출물 정확성까지 보증한다는 의미는 아니다. 실행 가능한 프로젝트 뼈대 생성은 문서 준비와 구분해야 한다. 공통 문서 단계에서 구조를 정하고, 실제 소스·설정 생성은 승인된 구현 Task로 관리하는 방식이 현재 승인 원칙과 맞는다.

## 현재 단계와 사용자 부담

현재 흐름은 다음과 같다. 내부 스테이지는 [layout.ts](../../src/agent/layout.ts) 20행, 전환 검사는 [commands.ts](../../src/agent/commands.ts) 481행에 정의돼 있다.

```text
별도 도입 및 공통 문서 준비 → POLICY 4종 각각 확정
요구사항 접수 → 요구사항 확정
분석 → 영향도 → 설계와 기능 명세 → 계획과 테스트 명세 → 계획 승인
구현 → 정적 검사 → 테스트 → 리뷰 → 통합 검증 → 최종 확인과 로컬 커밋
                            실패·수정 후 정적 검사부터 반복
```

| 단계 | 코드가 확인하는 것 | 사용자 편의와 남은 문제 |
|---|---|---|
| 도입·공통 문서 | 문서 파일·필수 절·확정 해시, 선언된 명령 이름 | 기존 문서 연결·역공학 있음. 접수에서 준비로 자동 연결되지 않음 |
| 요구사항 접수 | ID·종류·형식·원문 보관·확정 | 자연어·파일 입력 가능. ID와 fix/refactor의 경로·scope·preserve를 사용자가 알아야 하는 경우 발생 |
| 분석 | R 번호·근거 줄·가정 절 | 기술 세부를 가정으로 묶는 규칙은 유용. 원문 전량 반영은 확인하지 않음 |
| 영향도 | 모든 분석 R의 영향 표 포함, fix/refactor의 현행 근거 | 필요한 문서 틀 제공. 실제 의존·호출 영향은 모델의 조사 품질에 의존 |
| 설계·명세 | 설계 필수 절, R마다 AC 존재 | 개별 문서마다 사람 승인을 받지는 않음. 작은 수정도 같은 문서 종류를 거침 |
| 계획 | R→파일, AC→TC 연결, 보존 조건·경로 경계 | 문서를 묶어 승인하는 장점. 승인된 순서와 실행 순서가 다를 수 있음 |
| 구현 | 승인·현재 단계·계획 파일·보존 경계 | 단계별 새 컨텍스트, fix는 재현 우선. Task별 진행·완료 상태는 없음 |
| 정적 검사·테스트 | 선언 명령 실행, 반환 코드·해시·TC ID 존재 | 로그와 수정 루프 있음. 테스트별 skip·성공을 구분하지 않음 |
| 리뷰 | 회차·트리 해시·지적 상태·경로 범위 | 읽기 전용 reviewer 지시 있음. 실행 확인은 없고 동결 테스트 처리 지시가 코드와 충돌 |
| 통합·완료 | 별도 worktree의 build/test, 추적표, 최종 TTY 확인 | 완료 범위는 로컬 커밋. 사용자가 결과와 남은 검증 공백을 쉽게 읽는 요약은 보완 필요 |

결과 분석은 독립 스테이지가 아니라 검사·테스트 출력과 수정 루프 안에 있다. 이는 단계 누락으로 보지 않는다. `/ca-next`가 단계별 스킬을 이어 실행하므로 사용자가 매번 단계 명령을 외울 필요도 없다.

## 재현된 결함과 강제 범위의 한계

### F1 문서가 없는 접수를 열면 안내된 문서 준비도 막힌다

**우선순위 P1 · 실행 재현 P01·P02 · Task T1**

- 기대: 요구사항을 보존하고 문서·구조를 확인한 뒤, 빠진 것을 준비하고 분석으로 이어져야 한다.
- 실제: 설정이 없으면 접수부터 `/ca-adopt` 안내로 중단한다. 설정만 있고 POLICY가 없으면 접수는 열리지만 `start`가 `/ca-docs`를 안내하며 중단한다. 그 상태의 `docs begin`도 “접수 중”이라 거부된다.
- 영향: 사용자는 접수를 `abort`로 닫고 준비한 뒤 같은 ID로 다시 접수해야 한다. 작업 폴더와 원장은 남으므로 데이터 손실이나 영구 교착은 아니다.
- 근거: [request.ts](../../src/agent/request.ts) 374행, [commands.ts](../../src/agent/commands.ts) 261행, [docsCommands.ts](../../src/agent/docsCommands.ts) 131행.
- 보완: 접수한 내용이 남는 준비 상태를 두고, 그 상태에서 문서 작성→확정→분석으로 복귀하도록 연결한다.

### F2 실행을 건너뛴 테스트가 통과 증거로 인정된다

**우선순위 P1 · 실행 재현 P07·P10 · Task T5**

- 기대: 필수 TC가 실제 실행되어 성공해야 완료 검사에서 통과해야 한다.
- 실제: 함수가 `0`을 반환하고 AC는 `1`을 요구하는 상황에서 `test.skip('TC-1 returns 1', ...)`를 사용했다. 실제 `node --test` 출력에 `skipped 1`이 있어도 test와 integrate가 `passed`로 기록되고 반영 전 자동 검사도 문제 0건이었다. 최종 TTY 확인과 반영 커밋은 실행하지 않았다.
- 원인: 명령 반환 코드 0을 통과로 보고, 출력에 TC ID가 있거나 테스트 파일에 ID가 있으면 해당 TC가 확인됐다고 본다. 케이스별 성공 여부는 저장하지 않는다.
- 근거: [validate.ts](../../src/agent/validate.ts) 52·418행, [evidence.ts](../../src/agent/evidence.ts) 423·530행, [deliver.ts](../../src/agent/deliver.ts) 181행.
- 보완: 지원 테스트 도구의 구조화된 결과를 읽어 TC별 성공·실패·건너뜀·미실행을 저장한다. 알 수 없는 상태는 검증 완료로 표시하지 않는다.

[설계 문서](../design.md)의 “알고 남긴 한계”에도 파일의 TC ID만으로 확인하는 한계가 적혀 있다. 이번에는 **출력에 등장한 skipped TC도 통과하는 경로**를 확인했다. 명령 자체의 `not-run`·`error` 차단과 테스트 내부 케이스의 skip 차단은 서로 다른 문제다.

### F3 원 요구사항이 분석에서 빠져도 뒤의 추적표는 완성될 수 있다

**우선순위 P1 · 실행 재현 P03·P11 · Task T3**

- 기대: 접수·확정한 각 요구가 분석과 작업으로 이어지고, 제외한 항목은 명시적으로 보여야 한다.
- 실제: 확정 지시서의 두 문장 중 “입력 오류는 거부한다”를 분석 R에서 제외해도, 남은 R의 AC·파일·TC를 채우면 반영 전 자동 검사까지 통과했다. `근거:` 값이 비어 있어도 분석 파서가 받아들였다.
- 원인: 후속 대조의 출발점은 원문 전체가 아니라 모델이 작성한 `01-requirements.md`의 R 목록이다. 근거 검사는 줄 존재 검사이며 인용 내용과 원문을 대조하지 않는다.
- 영향: “모든 분석된 R이 파일에 연결됨”은 보장하지만 “사용자가 준 모든 요구에 작업이 있음”까지 보장하지 않는다. 실제 모델이 항상 누락한다는 주장은 아니다.
- 근거: [workDocs.ts](../../src/agent/workDocs.ts) 74·88행, [commands.ts](../../src/agent/commands.ts) 216행, [deliver.ts](../../src/agent/deliver.ts) 65행.
- 보완: 접수 요구 항목에 안정적인 ID를 주고 각 ID가 R 또는 명시적 제외 사유에 연결되는지 검사한다. 근거의 빈값과 원문에 없는 인용을 거부하고, 사람에게 원문 대비 반영 목록을 보여 준다.

### F4 승인한 구현 순서가 실제 실행 순서를 정하지 않는다

**우선순위 P2 · 실행 재현 P05·P06 · Task T4**

- 기대: 계획의 작업 순서와 실행이 일치하거나, 불가능한 순서를 제출 전에 거부해야 한다.
- 실제: feature 계획의 `sequence`를 `test → code`로 승인해도 커서는 매니페스트 순서의 `code`에서 시작했다. 파일·단계와 무관한 `step: not-a-real-task`, 빈 `why`도 제출됐다.
- 원인: `plannedStages`는 매니페스트 순서를 따른다. fix에서만 테스트 단계를 앞으로 옮기며, 일반 sequence의 실행 연결은 없다.
- 근거: [plan.ts](../../src/core/plan.ts) 14행, [commands.ts](../../src/agent/commands.ts) 239·1124·1155행, [ca-plan](../../template/claude/skills/ca-plan/SKILL.md)의 Risk 기반 작업 순서 지시.
- 보완: 실행 Task와 순서를 하나의 데이터로 관리한다. 매니페스트의 의존 규칙과 충돌하면 승인 전에 오류를 표시한다.

### F5 동결된 테스트에 대한 리뷰 지시와 범위 판정이 충돌한다

**우선순위 P2 · 파서 재현 P09와 지시문 대조 · Task T6**

- 기대: 리뷰어가 규칙대로 낸 지적을 메인이 그대로 옮기면 일관된 처리 경로로 이어져야 한다.
- 실제: reviewer는 동결 테스트 오류를 `계획 밖`으로 보고하라고 지시받는다. 하지만 그 테스트가 계획 파일이면 파서는 `계획 안`으로 판정하고 `reviewProblems`는 범위 불일치를 거부한다. 메인은 재분류하지 말라는 지시도 받는다.
- 추가 불일치: 코드에는 리뷰 지적으로 동결을 푸는 `findingOpensFile`이 있으나 스킬은 동결 테스트를 고치지 말라고 한다.
- 근거: [ca-reviewer](../../template/claude/agents/ca-reviewer.md) 14행, [ca-review](../../template/claude/skills/ca-review/SKILL.md) 21행, [review.ts](../../src/agent/review.ts) 112·304·344행, [ca-check](../../template/claude/skills/ca-check/SKILL.md)의 수정 루프.
- 보완: 파일이 계획 안인지와 사람의 판단이 필요한지를 별개 값으로 표현하고, 테스트 수정·재승인 규칙을 코드와 스킬에 동일하게 적용한다.

### F6 리뷰 회차 통과는 실제 리뷰어 실행을 증명하지 않는다

**강제 범위 한계 · 실행 재현 P08 · Task T7**

- 실제: 코드로 리뷰 회차를 연 뒤 지적 절에 `- 없음`을 쓰면, reviewer를 호출하지 않은 재현에서도 리뷰 검사가 통과했다.
- 해석: 현재 CLI는 리뷰 기록의 일관성을 검사한다. 독립 리뷰의 실제 수행 여부·판단 품질은 스킬 준수에 의존한다. 스킬에 reviewer 호출 지시는 존재하므로 “리뷰 기능이 없다”는 판정은 아니다.
- 근거: [ca-review](../../template/claude/skills/ca-review/SKILL.md) 19행, [review.ts](../../src/agent/review.ts) 344행.
- 보완: 관측 가능한 reviewer 실행·결과를 회차와 연결한다. 지원 환경에서 관측할 수 없다면 보고서에 “리뷰 결과 문서 확인”과 “독립 리뷰 실행 확인”을 구분한다.

## 초보자 사용성에서 부족한 부분

### 언어와 구조 선택은 있지만 목적에 맞는 추천 흐름은 부족하다

[schemas.ts](../../src/agent/schemas.ts)에는 언어·프레임워크·디렉토리 구조·계층 선택지가 있다. 그러나 신규 저장소의 [ca-adopt](../../template/claude/skills/ca-adopt/SKILL.md) 21행은 `domainBase`, `outputDirs`, 단계 종류, build/test/prepare, 기준 브랜치까지 사용자에게 묻도록 한다. 프로젝트 용도와 경험 수준으로 추천 조합을 만들고 나머지 설정을 채우는 절차는 확인되지 않았다.

POLICY 인터뷰 질문 목록은 **아키텍처 15, 컨벤션 8, 테스트 전략 9, 품질 8로 총 40개**다(P04). 이는 실제 한 세션의 질문 수가 아니다. 기존 코드·사용자 답에 따라 줄일 수 있고, 한 번에 4개까지만 묻는 규칙도 있다. 다만 질문 총량의 상한이나 초보자용 간단 모드는 없다.

[ca-docs](../../template/claude/skills/ca-docs/SKILL.md) 73행은 사용자가 모르면 POLICY를 `확인 필요`로 남기도록 한다. 필수 절에 이 표시만 남으면 문서 검사를 통과하지 못한다. 따라서 “잘 모르니 추천대로 진행”할 수 있는 명시적 경로가 필요하다. **Task T2.**

### 요구사항을 다시 입력하지 않아도 되는 흐름과 확인 묶음이 필요하다

초기 POLICY 확정은 별도 터미널 명령 4회다. 이후 각 작업은 요구사항 확정·계획 승인·반영 확인 3회를 요구한다. **첫 도입과 첫 작업을 합하면 기본 확인 명령 7회**이며, 문서 생성 방식 선택·질문 답변·KNOWLEDGE 반영 선택은 별도다. 이 수치는 터미널 전환 횟수나 전체 질문 횟수를 뜻하지 않는다.

`/ca-next`의 자동 진행, 기술 가정을 계획에 묶는 규칙, 문서 변경 시 재승인 요구는 유지할 가치가 있다. 줄여야 하는 것은 사용자가 기억할 명령과 반복 선택이다. 무조건 모든 확인을 없애는 방식은 필요하지 않다. **Task T1·T8.**

### 파일 목록은 작업 분해의 기반이지만 Task 관리까지는 아니다

현재 `plan.files`에 파일·목적·R이 있고 `sequence`에 순서·이유가 있다. 따라서 작업 계획이 전혀 없다고 볼 수는 없다. 다만 [types.ts](../../src/core/types.ts)와 [plan.ts](../../src/core/plan.ts)에는 Task ID, 연결 요구, 완료 기준, 의존 작업, 진행 상태를 함께 다루는 모델이 없다. 상태 화면도 전체 스테이지·구현 단계 중심이다.

Task를 별도 문서 여러 장으로 늘릴 필요는 없다. 기존 `plan.json` 안에 간단한 Task를 두고 R·파일·TC·상태를 연결하면 사용자 목표에 맞는다. **Task T3·T4.**

### 실제 완주 결과가 더 필요하다

[설계 문서](../design.md)의 남은 작업에도 직접 완주와 TC 수준 출력 파싱이 명시돼 있다. 이번 기존 테스트는 준비된 fixture와 테스트용 승인 기록을 사용하는 부분이 많다. 이 결과만으로 자연어 요구를 모델이 정확하게 구현하거나 초보자가 혼자 완료한다고 판단할 수 없다.

특히 신규는 `/ca-adopt`가 문서·설정까지만 작성하며, 기준 커밋이 없는 저장소는 `start`가 진행하지 못한다. 실제 프로젝트 뼈대 생성, 초기 Git 준비, 의존성 준비까지 포함한 신규 사용 시나리오를 검증해야 한다. **Task T2·T9.**

## 권장하는 간단한 사용자 흐름

아래는 **개선 제안이며 현재 구현된 기능이 아니다.** 내부 검증 단계는 유지하고, 사용자에게는 다섯 구간으로 보여 주는 편이 적절하다.

| 사용자에게 보일 단계 | 자동으로 처리할 일 | 사용자가 결정할 것 |
|---|---|---|
| 1 요구사항 받기 | 원문 보존, 작업 ID 제안, 신규·개선·수정·리팩토링 분류 | 의도가 모호할 때만 종류 확인 |
| 2 프로젝트 준비 | 문서·구조·환경 점검, 기존 설정 재사용, 빠진 문서 생성 | 최초에 추천 구성 / 직접 선택, 필요한 제품 제약 |
| 3 할 일 확인 | 요구→영향→설계→Task→테스트 연결, 빠진 요구 표시 | 이해한 요구와 작업 계획을 한 묶음으로 확인 |
| 4 개발과 검증 | 코드 작성, 빌드·테스트, 독립 리뷰, 범위 안 수정 | 의미·범위 변경 또는 해결 불가 문제만 질문 |
| 5 결과 확인 | Task 완료, 실제 TC 결과, 리뷰 상태, 변경 요약 제공 | 최종 반영 확인 |

초기 질문 수는 실제 사용자 실험 후 정하되, “추천대로”를 선택했을 때 기술 내부값을 추가로 결정하게 해서는 안 된다. 이후 일반 작업의 기본 확인은 작업 계획과 최종 결과 두 묶음으로 줄이는 방안을 제안한다. 요구사항을 별도 확정해야 하는 운영 환경에서는 현재 방식을 선택할 수 있게 한다.

## 재검토 리포트 형식

다음 검토에서도 아래 항목을 같은 순서로 기록하면 구현 진척과 사용자 목표 달성을 혼동하지 않고 비교할 수 있다.

| 보고 항목 | 반드시 포함할 내용 |
|---|---|
| 종합 판정 | 충족/부분 충족/미충족/미검증, 가장 중요한 이유 |
| 검토 기준 | 커밋·환경·사용자 요구 ID·검증 범위 |
| 요구사항 추적 | 원 요구→R→Task→변경 파일→TC 결과 |
| 단계별 결과 | 진입 조건·산출물·완료 조건·사용자 선택 |
| 발견 사항 | 기대 동작·실제 동작·재현·코드 위치·사용자 영향 |
| 실행 결과 | 통과·실패·건너뜀·미실행을 분리, 실제 모델 실행 여부 |
| 사용성 | 질문 수·확인 명령 수·중단/복구 횟수·수동 개입 이유 |
| 후속 Task | 연결 요구·우선순위·담당 범위·완료 기준·상태 |

현재는 **기존 검사를 통과한다는 사실**과 **사용자가 요청한 모든 동작을 개발·검증했다는 사실** 사이에 간격이 있다. 우선 접수와 준비를 연결하고, 원 요구부터 Task를 추적하며, 실제 TC 성공을 완료 조건으로 삼은 뒤 실제 모델 완주를 확인해야 한다.
