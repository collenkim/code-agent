# ca-answer 참고 — 필요할 때만 읽는다

## 5개 이상 선택지

전체 후보의 이름과 한 줄 설명을 먼저 짧은 표로 보여 주고, 선택은 도구로 받는다. 추천을 첫 번째로 정렬하고 고유한 후보 이름은 페이지 사이에 바꾸지 않는다.

- 첫 화면: 후보 3개 + `다른 선택지`(설명에 남은 후보 이름).
- 중간 화면: `앞 선택지` + 다음 후보 2개 + `다른 선택지`.
- 마지막 화면: `앞 선택지` + 남은 후보 최대 3개. 따라서 모든 화면은 2~4개 옵션이고 어떤 후보든 선택할 수 있다.
- 5개 후보 예: 첫 화면 A·B·C·다른 선택지 → 마지막 화면 앞 선택지·D·E. 7개 후보 예: A·B·C·다른 선택지 → 앞 선택지·D·E·다른 선택지 → 앞 선택지·F·G.
- 페이지 이동은 답으로 저장하지 않는다. 후보를 고르면 그 결정은 끝내고 다른 페이지를 강제로 질문하지 않는다. 내장 직접 입력으로 다른 페이지의 후보를 명시해도 그 선택을 기록한다.
- 5개 이상을 복수 선택해야 하면 먼저 3개 이하의 의미 있는 그룹을 도구로 선택하게 하고, 선택한 각 그룹의 후보를 최대 4개씩 복수 선택으로 받는다. 이동·그룹 이름을 최종 선택으로 간주하지 않고, 실제 선택한 후보들을 합쳐 기록한다.

## 작업 JSON 필드

자유 문구가 없는 동작은 파일 대신 `code-agent consent prepare --action <동작> [--id] [--kind] [--spec] --for claude`로 준비한다. 표의 필드 형식은 파일로 준비할 때 쓴다.

| 필드 | 형식과 용도 |
|---|---|
| `action` | 필수 문자열: `setup`, `docs`, `baseline`, `request`, `plan`, `deliver`, `knowledge-prune`, `model`, `abort`, `plugin-add`, `plugin-remove`, `update`, `repro-log`, `judgment` 중 하나 |
| `kind` | 선택 문자열: 문서 종류 또는 `all`. `judgment`에서는 `retry-grant`·`waive-finding`·`cross-stop` |
| `id` | 선택 문자열: 요구사항의 작업 ID. `prepare`가 반환하는 동의 UUID와 구분한다. `judgment`에서는 지적 번호(F1·X1·C1)(waive-finding), 또는 계획 배정 한도(`taskTotal`·`sameInput`)의 계획 작업 ID(retry-grant). 그 밖의 카운터에는 넣지 않는다 — 회차·트리·critic 지점은 코드가 현재 단계에서 정한다 |
| `spec` | 선택 문자열: 사람이 작성한 지시서 경로 |
| `decision` | 선택 문자열: `accept` 또는 `reject`. 실행할 확정·반려 동작이며 실제 동의 응답을 대신하지 않는다 |
| `comment` | 선택 문자열: 사용자가 제시한 반려·판단 사유 (`judgment`는 필수) |
| `"agent"`, `"model"` | 선택 문자열: 바꿀 역할(`all`은 모든 역할)과 모델. `model:"default"`는 그 역할의 모델·추론 강도를 제품 기본값으로 되돌린다 |
| `host` | 선택 문자열: `claude` 또는 `codex`. 두 호스트를 함께 설치했으면 반드시 넣는다 |
| `reasoning` | 선택 문자열: 추론 강도. Claude는 `low`·`medium`·`high`·`xhigh`·`max`(haiku는 강도를 받지 않으니 넣지 않는다), Codex는 여기에 `ultra`까지. 생략하면 그 역할의 지금 강도를 유지한다. `default` 복원에는 넣지 않는다 |
| `name`, `command`, `slots` | 선택 문자열: 플러그인 이름·실행 명령·슬롯. `judgment`의 `name`은 카운터 이름(retry-grant) 또는 교차 지점 `review`·`planning`(cross-stop) |
| `sendsCode` | 선택 불리언: 플러그인의 코드 전송 여부 |
| `secretEnv` | 선택 문자열: **이미 설정된 환경변수 이름만** 참조한다. 키 값은 넣지 않는다 |

## 상황별 예시

| 상황 | 작업 JSON 예시 |
|---|---|
| 최초 준비 | `{"action":"setup"}` — POLICY 전체 확정(`confirm doc all`)과 필요한 준비 커밋(`setup baseline`: 최초 커밋 또는 기존 저장소의 도입 파일 반영)을 **사용자 질문 하나**로 묶는다 |
| 준비 이후 문서 확정 | `{"action":"docs","kind":"all"}` — 특정 문서만이면 해당 종류를 쓴다 |
| 기준 커밋만 별도 준비 | `{"action":"baseline"}` |
| 접수 요구사항 확정 | `{"action":"request","id":"<작업 ID>"}` — 수기 지시서는 필요하면 `spec`을 포함한다 |
| 계획 승인 | `{"action":"plan"}` |
| 요구사항·계획 반려 기록 | 해당 `request` 또는 `plan`에 `"decision":"reject","comment":"<사용자 사유>"`를 포함한다. 이 동작도 별도 동의 후 적용한다 |
| 검증 결과 반영 | `{"action":"deliver"}` |
| 오래된 지식 항목 정리 | `{"action":"knowledge-prune"}` |
| 모델·추론 강도 변경 | 먼저 `code-agent model --host claude`로 지금 값을 조회한다. `{"action":"model","host":"claude","agent":"<역할|all>","model":"<opus|sonnet|haiku|fable|claude-…|default>","reasoning":"<low|medium|high|xhigh|max>"}` — `reasoning`은 바꿀 때만 넣는다. 사용자가 고른 값만 넣고 임의로 다른 모델로 바꾸지 않는다. 진행 중인 작업이 있으면 준비가 거부된다 — 작업을 반영하거나 종료한 뒤 요청하게 한다 |
| 접수·작업 종료 | `{"action":"abort"}` |
| 플러그인 추가 | `{"action":"plugin-add","name":"<이름>","command":"<명령>","slots":"<슬롯>","sendsCode":false}` — 인증이 필요하면 `secretEnv`로 기존 환경변수 이름만 참조한다 |
| 플러그인 제거 | `{"action":"plugin-remove","name":"<이름>"}` |
| 사용자가 code-agent 업데이트를 요청함 | `{"action":"update"}` — 소스 갱신의 Git pull·빌드·설치 적용 범위를 확인받는다 |
| fix 의 로컬 재현 실패 뒤 오류 로그 근거로 진행 | `{"action":"repro-log"}` — `code-agent repro` 가 전환을 안내했을 때만. 확인 화면은 CLI 가 재현 시도 결과와 오류 로그 앞부분으로 만든다 |
| CLI 결과가 `limit-exceeded`이고 사용자가 같은 계획으로 한 번 더를 골랐음 | `{"action":"judgment","kind":"retry-grant","name":"fix","comment":"<사용자 사유>"}` — `name`은 결과의 `failure.counter.key` |
| 계획 작업 배정 한도가 소진됐고 사용자가 한 번 더를 골랐음 | `{"action":"judgment","kind":"retry-grant","name":"taskTotal","id":"<계획 작업 ID>","comment":"<사용자 사유>"}` |
| 리뷰 지적을 사용자가 기각함 | `{"action":"judgment","kind":"waive-finding","id":"F1","comment":"<사용자 사유>"}` — review 단계는 F·X 번호, plan 단계는 교차 계획 검토의 차단 지적 id. 표의 줄은 남고 게이트만 그 회차에서 그 지적을 세지 않는다(다음 회차는 지적 내용이 같을 때만 이어진다) |
| 교차 검증이 설정 오류·형식 실패로 막혔고 사용자가 중지를 결정함 | `{"action":"judgment","kind":"cross-stop","name":"review","comment":"<사용자 사유>"}` — 샌드박스 권한 상승을 사용자가 거절했거나, 권한 상승 뒤에도 네트워크 오류가 되풀이돼 사용자가 진행을 정한 경우도 같다. 계획 검토는 "name":"planning" |

judgment 는 사용자가 업무 질문에서 그 선택을 고른 뒤에만 준비한다. 모델이 스스로 한도를 늘리거나 지적을 기각하지 않는다.

## 대상 변경 안내

대상 변경 오류에는 `변경 대상:`으로 경로와 Git 상태가 표시된다. 표시된 변경을 검토한 뒤 새 동의를 준비한다. 경로별 해시가 없는 이전 기록은 재준비 안내만 나올 수 있다. Git에서 무시된 외부 세션·캐시는 기본 스냅샷에서 제외되지만 명시된 제어·문서 경로와 추적 파일은 계속 검사한다. 동의 통과를 위해 hook을 지우거나 감사 파일을 임의로 무시하지 않는다. 접수 중에도 `code-agent help`·`code-agent --help`로 명령을 조회할 수 있다. 대상 변경·응답 거부·보류·수정 요청·적용 실패는 동의 기록에 `failure`(`class`·`kind`·`guide`)로 남고 그 동의는 다시 쓸 수 없다. 다음 행동은 `guide`를 따른다 — 보류·명시적 선택 없음은 다시 묻지 않는다. 같은 동작이 연속 두 번 대상 변경으로 폐기되면 준비 결과에 `warning`이 붙는다 — 외부 hook·편집기·빌드가 대상을 바꾸는지 사용자에게 확인받는다.

## 수동 대체 경로

독립 TTY CLI는 사용자가 직접 선택하는 **수동 대체 경로**다. 같은 세션의 도구·hook을 사용할 수 없으면 미승인 상태와 사유를 알리고 이 경로를 안내할 수 있다. `code-agent confirm doc all`, `code-agent setup baseline`, `code-agent confirm request <ID> [<지시서>]`, `code-agent approve`, `code-agent deliver` 등은 사용자가 직접 실행할 때만 사용하며 필수 절차로 요구하지 않는다. 에이전트가 TTY 입력을 대신하거나 다른 명령으로 동의를 우회하지 않는다. 수동 처리 뒤에는 현재 상태를 확인하고 중단된 흐름을 재개한다.
## 차단 복구

CLI·hook 거부는 그 동작을 중지한다는 뜻이다. 메인은 사유를 설명하고 아래 선택 절차를 이어간다. 담당 에이전트는 거부를 메인에 보고하며 직접 동의를 받거나 우회하지 않는다.

1. 거부 원문과 직전 상태를 확인한다. 상태가 불명확하면 읽기 전용 `code-agent status`·`doctor`로 확인한다. 같은 실패 명령을 반복하거나 다른 도구로 우회하지 않는다. 사용자 취소·보류·승인 거절은 복구 질문으로 되묻지 않고 존중한다.
2. 현재 가능한 행동 2~3개만 공통 질문 절차로 실제 제시한다. 사유·영향을 설명하고 보류를 포함한다. 근거가 있는 복구를 첫 항목에 추천하되 응답 전 실행하지 않는다. 다음 표의 후보를 상태에 맞게 고르며 불가능한 행동을 선택지로 넣지 않는다.

| 원인 | 선택 후보·연결 |
|---|---|
| 공통 문서·설정 누락 | 코드·기존 자료로 준비 / 기존 문서 경로를 받아 연결 / 보류. 설정은 ca-adopt, 문서는 ca-docs. 내용이 있으나 미확정이면 작성 대신 문서 확정 절차로 연결 |
| 작업 중 공통 문서 보완 필요 | 작업 보존 후 문서 보완 / 보류. 아래 작업 중 보완 순서를 설명하고 확인 |
| 요구·계획 미확정 또는 승인 무효 | 현재 안 확인·승인 절차 / 내용 수정·재계획 / 보류. 확정되지 않은 상태로 실행하는 선택지는 없음 |
| 계획 범위 밖·다른 단계의 쓰기 | 현재 범위 내 해결(가능할 때만) / 범위 변경·재계획 / 보류. 단계 이동·재계획에 필요한 사용자 지시와 재승인을 따로 받음 |
| 테스트 실패·재시도 한도 | 출력이 허용하는 수정·진단 / 출력에 실제 있는 사람 판단·추가 허용 / 보류. 허용 횟수·테스트 동결·검증 생략 규칙은 바꾸지 않음 |
| 다른 세션·외부 절차와 충돌 | 기존 세션에서 계속 / 종료 확인 후 정식 인계 / 보류. 실행 중인 다른 작업을 임의 종료하지 않음 |
| 호스트 권한·설치·외부 hook 또는 원인 불명 | 읽기 전용 원인 점검 / 사용자가 권한·설정을 확인한 뒤 재개 / 보류. 외부 거부를 code-agent 승인으로 해제할 수 있다고 안내하지 않음 |

3. 선택은 복구 방향에 대한 답이다. abort·docs·setup·plan 등의 동의가 필요한 실행은 각각의 기존 동의 절차를 거친다. 권한 변경·문서 확정·승인을 일반 답변으로 대체하지 않는다. 질문 기록이 허용되지 않으면 파일을 만들지 않고 현재 대화에서 질문한다.
4. 작업 ID·종류·원문·현재 단계를 유지한다. 접수 중 문서 준비는 같은 접수로 돌아온다. **이미 시작한 작업**은 docs begin이 거부되므로 허용된 작업 폴더에 작업 ID·지시서 경로·대상·기준 브랜치·멈춘 단계를 보존하고, abort 동의를 받아 커서만 닫은 후 문서를 보완·확정한다. 기존 지시서로 start하여 분석부터 필요한 근거·계획·승인을 다시 검증한다. 원래 단계로 무조건 건너뛰거나 새 작업 ID·원문 재입력을 요구하지 않는다.
5. 선택한 복구가 끝나면 상태를 다시 확인하고 기존 작업을 자동으로 이어간다. 사용자가 ca-request·ca-fix·ca-next를 다시 입력하게 하지 않는다. 새로운 차단은 달라진 원인을 설명하고 다시 선택받는다. 같은 원인·같은 미응답에는 반복 질문하지 않는다.
