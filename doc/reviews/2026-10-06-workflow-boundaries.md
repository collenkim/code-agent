# 도입·반영·도메인 경계 결함 수정

기준일: 2026-10-06. 수정 전 기준 커밋: `9bd628a`. 현재 사용 계약은 [사용 가이드](../usage.md), [설치](../install.md), [설계](../design.md), [요구사항](../requirement.md)을 따른다.

## 확인한 결함과 수정

| 항목 | 발생 조건 | 수정된 동작 |
|---|---|---|
| H1 · start → check | 기존 저장소의 도입 파일이 미커밋이거나, 도입 커밋이 시작 기준 브랜치에 없음 | `setup baseline`이 기존 저장소의 준비 커밋도 지원한다. `start`는 미커밋 도입 파일과 기준·전환 대상의 불일치를 전환 전에 안내한다. 파일과 브랜치를 보존하며 도입 파일을 영구 예외로 허용하지 않는다. |
| H2 · deliver | `doc/` 또는 지식·증거 경로가 Git에서 무시됨 | 확인한 반영 경로만 literal pathspec과 강제 추가로 올리고 같은 경로로 커밋한다. `add` 오류도 `Stop`으로 안내하며 작업 커서를 유지한다. 다른 작업과 미선택 지식, 무관한 스테이징 파일은 포함하지 않는다. |
| H3 · plan submit | fix/refactor에 domain 범위와 제한된 outputDirs를 사용 | 각 파일의 단계 base → 선언된 분류 → 도메인 → 계층을 해석한다. 분류를 계층으로 오판하지 않으며 scope·preserve·계층 제한과 기존 테스트 보존 규칙은 유지한다. |

`init`은 호스트 파일을 설치하며 `code-agent.json`은 adopt/setup에서 준비한다. H1은 이 준비 파일 묶음의 기준 관리 결함이다. 도입 커밋이 다른 브랜치에만 있을 때 Git 전환으로 작업 트리에서 파일이 사라지던 것이며, 원래 도입 커밋 자체가 지워지는 문제는 아니었다. H2도 모든 저장소에서 실패하는 문제가 아니라 해당 문서가 무시되는 조건에서 재현됐다.

## 검증 범위

- `adoption.test.ts`: 기존 Git 이력에서 Claude·Codex 설치와 준비 커밋, 미커밋 시작 차단, 기준/기존 작업 브랜치 불일치 시 파일 보존, 명시한 도입 브랜치에서 정상 시작, 시작 후 설치 파일 변경 검출, 확인 중 브랜치 변경 거부.
- `consent.test.ts`: 기존 커밋이 있어도 setup 확인에 준비 커밋이 포함되고 실제 관찰·적용 뒤에만 반영됨.
- `gate.test.ts`: fix/refactor × admin/application, 단계별 테스트 base, 분류 없는 배치, 잘못된 분류·계층·scope·preserve 거부.
- `p6.test.ts`: 실제 실패 테스트를 재현한 fix와 기존 테스트를 보존한 refactor가 계획 제출·승인·구현·검증·리뷰·통합·로컬 반영까지 완료. 무시된 문서·증거·선택한 지식만 커밋하고 기존의 무관한 index는 보존. index 잠금으로 add가 실패하면 안내와 작업 상태 유지.
- `process.test.ts`: 기존 저장소에서 두 호스트 설치 → 준비 커밋 → 접수 → 분석·계획 → 구현 → 실제 테스트 → 리뷰 → 깨끗한 작업 트리의 통합 검증 → 무시된 작업 문서를 포함한 반영. 완료 뒤 작업 커서와 Git 작업 트리도 확인.

승인과 리뷰 관찰은 명시적인 자동 테스트 fixture다. 검증 명령, Git 커밋, 임시 저장소와 worktree는 실제로 실행한다. 이 결과를 실계정 모델 실행이나 실제 사용자 승인 실측으로 해석하지 않는다. 이전 모델 실행 기록은 해당 날짜의 보고서에 보존한다.

## 최종 결과

최종 고유 확인 범위는 **740개 중 736개 통과 · 미해결 실패 0개 · 생략 4개**다. [실행별 요약 근거](evidence/workflow-boundaries-2026-10-06.json)에 명령·결과·로그 SHA-256을 보관한다.

| 실행 | 결과 | 로컬 로그 |
|---|---|---|
| 전체 `npm test` | 740개 중 730개 통과 · 6개 실패 · 4개 생략 | `dist/final-regression.log` |
| 준비 절차를 보완한 실패 사례 전체 재검증 | 동일한 6개 모두 통과 | `dist/adoption-fixture-regression.log` |
| H1~H3 및 기능 추가 전체 흐름 집중 검사 | 12개 통과 | `dist/workflow-defects-focused.log` |
| 도입·동의·경계·초기 준비 검사 | 80개 통과 | `dist/adoption-focused.log` |

전체 실행과 수정된 실패 사례 재검증을 결합한 범위이며, 단일 전체 재실행이 모두 통과했다고 표시하지 않는다. 집중 검사의 중복 범위를 더하지 않는다. 생략 4개는 Windows의 대소문자 구분 없는 파일시스템 2개와 POSIX 권한 검사 2개다. TypeScript 빌드와 `git diff --check`도 통과했다.

첫 전체 검사에서 기존 테스트 6개가 설정·공통 문서를 미커밋으로 바꾸고 바로 시작하던 준비 방식 때문에 차단됐다. 제품의 시작 검사를 완화하지 않고 테스트 기준 브랜치에 준비 내용을 먼저 커밋하도록 보완했다. 전체 실행의 실패 이름과 재검증의 통과 이름이 모두 일치하는지도 확인했다.

## 문서 정리

README, 사용·설치·설계·요구사항 정본과 설치 스킬의 최초 커밋 전용 안내를 기존 저장소의 도입 커밋까지 포함하도록 맞췄다. 검증 이력 색인과 요약 근거에서 최신 결과를 가리키며 과거 결과와 실패 기록은 보존한다. `dist/`의 실행 로그와 재현 저장소는 재생성 가능한 로컬 산출물로 커밋하지 않는다.
