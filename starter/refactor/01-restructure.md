# [refactor 01] 구조 정리

> **산출물**: 구조만 달라진 코드 · **다음**: [02] 기존 테스트 통과 확인
> **근거**: 스펙(무엇을 왜 고치는가) · 대상의 현재 코드 · 지시서의 `scope`·`preserve` · 계획의 보존 방식

## 0. 사용법

동작을 바꾸지 않고 구조를 고친다. "동작"의 정의는 지시서의 `preserve` 와 기존 테스트다.
**무엇을 고치는지보다 무엇을 지키는지가 먼저다** — 계획의 `preserve` 항목마다 적힌 "어떻게 지키는지"가 이 단계의 규칙이다.

**do-not-touch**: `preserve` 에 적힌 경로는 코드가 막는다. 문장형(`공개 시그니처를 유지한다` 등)은 여기서 지킨다. `scope` 밖은 만들지도 고치지도 않는다.

## 1. 입력 게이트

- [ ] 스펙에 **왜** 고치는지가 있다 — 이유 없는 구조 변경은 취향이다. 없으면 `ask`
- [ ] 「대상의 현재 파일」에 고칠 코드가 실려 있다
- [ ] 계획에 `preserve` 항목마다 보존 방식이 적혀 있다 (없으면 계획이 저장되지 않았을 것이다)
- [ ] 기존 테스트가 있다. 없으면 이 작업은 검증할 수 없다 — `ask` 로 사람에게 알린다

## 2. 규칙 게이트

| 규칙 | 근거 | 위반 시 |
|---|---|---|
| 계획에 적힌 보존 방식을 그대로 지킨다 | 계획 `preserve` | 무효 |
| 공개 인터페이스(호출되는 이름·시그니처·반환)를 바꾸지 않는다 — `preserve` 에 없어도 기본이다 | 동작 보존 | 무효 |
| 고치는 파일은 계획의 목록뿐이다. 그 김에 다른 곳을 정리하지 않는다 | 경계 | 무효 |
| 기존 파일은 `edit` 으로 고친다. `write` 로 통째로 다시 쓰면 나머지가 조용히 사라진다 | — | 무효 |
| 테스트를 고치지 않는다. 테스트가 구조에 묶여 있어 깨진다면 `note` 로 남기고 멈춘다 | 경계 | 무효 |
| 판단이 필요했던 지점(이 이름을 바꿔야 했나 등)은 `note` 로 남긴다 | — | 무효 |

## 3. 작업

1. 계획의 파일 목록과 `preserve` 보존 방식을 나란히 놓는다. 각 파일에서 **바꿀 것과 지킬 것**을 먼저 가른다
2. 지킬 것(공개 시그니처·이름·반환)을 표로 적어 둔다 — 이것이 [4] 의 대조표다
3. 파일마다 `edit` 으로 고친다. 한 파일에 여러 곳이면 `edit` 을 여러 번 — find 는 한 곳에만 걸려야 한다
4. 이동·이름 변경이 있으면 **부르는 쪽**도 계획에 있는지 확인한다. 없으면 만들지 말고 `note`
5. `### done`

## 4. 자가검증 체크리스트

- [ ] 고친 파일이 계획의 목록과 정확히 같은가
- [ ] [3]-2 의 표에 적은 것이 전부 그대로 남아 있는가
- [ ] `preserve` 의 각 항목이 계획에 적힌 방식대로 지켜졌는가 — 항목마다 확인했는가
- [ ] `write` 로 다시 쓴 기존 파일이 없는가
- [ ] 테스트를 고치지 않았는가

## 5. 산출물 → 다음 단계 입력

- **산출물**: 구조만 달라진 코드
- **[02] 입력**: 없음 — [02] 는 기존 테스트를 **돌린다**. 통과하지 않으면 동작이 바뀐 것이다
