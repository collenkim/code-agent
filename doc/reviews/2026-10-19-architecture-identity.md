# 2026-10-19 실행 구조 검토와 접수 식별 보존

## 범위

code-agent와 master-agent의 실행 그래프, 저장소, 접수, 제어 계약, 호스트 실행, 대시보드 접수 경로를 확인했다. 코드 변경은 최초 접수 종류·작업 ID 보존과 프로젝트별 업무 번호 중복 방지다. 현재 CLI·호스트 실행 방식을 유지하며 API 전환은 범위에 포함하지 않는다.

변경 커밋은 code-agent `54f443c`, master-agent `9495916`이다.

## 구조 판정

두 저장소 모두 LangGraph JS 1.5.0과 공식 SqliteSaver 1.1.0을 실제 실행 경로에서 사용한다. master는 Mission·Task·Attempt와 프로젝트 간 의존성을, code-agent는 프로젝트 내부 접수·계획·구현·검증·반영을 담당한다. `code-agent.master` v1의 JSON CLI 계약이 두 실행기를 연결한다.

- master `packages/orchestrator/drive.mjs`: 작업 선택, 접수, 관측, 위임 판단, 검증, 복구, 재계획을 별도 노드로 분리한다. 독립 프로젝트의 외부 호스트 실행은 겹치며 같은 프로젝트는 도메인 잠금으로 보호한다.
- code-agent `src/agent/graph/`: lifecycle·planning·transition·operation 그래프가 도메인 서비스를 호출한다. `src/core/workflow.ts`는 검증의 program·agent·human 분기를 구성한다.
- 양쪽 모두 도메인 기록이 권한·완료의 근거다. 체크포인트 자체나 단순 resume 신호로 승인하지 않는다. master의 요청 ID·소유 세대, 기대 상태, 독립 검증과 code-agent 승인·증거 대조를 유지하는 점이 적절하다.
- 정상 wait는 master에서 Command.resume으로 깨운다. code-agent 운영 흐름과 비정상 종료 복구는 START에서 최신 도메인 상태를 다시 관측한다. 이는 의도적인 재관측 설계다. 체크포인트가 중간 모델 호출·외부 실행의 정확히 한 번 수행을 보장하는 구조는 아니다.

[LangGraph interrupt 문서](https://docs.langchain.com/oss/javascript/langgraph/interrupts)는 재개 시 노드 처음부터 코드가 다시 실행됨을 명시한다. 현재 구조에서 외부 효과 노드를 무조건 재생하지 않는 선택은 타당하다. 일반 명령을 한 노드 또는 observe/apply/reconcile로 감싼 부분은 그래프의 분기·복구 이점이 작으므로 복잡한 흐름과 같은 수준의 내구성을 갖췄다고 해석해서는 안 된다.

## 개선 우선순위

| 우선순위 | 관측 | 제안 |
|---|---|---|
| 높음 | master HTTP 접수 저장과 worker 시작이 분리돼 있다. 접수 후 launch 직전에 오류를 주입하면 첫 POST는 500, 같은 키의 재전송은 queued로 202를 반환하지만 worker 시작은 재시도하지 않는다 | 영속 실행 대기열과 시작되지 않은 요청의 재조정. 기존 request continue 수동 복구와 멱등 키는 유지 |
| 높음 | 프로젝트별 잠금은 있으나 Mission·전체 실행의 동시 호스트 수·모델 비용 상한은 자동 배정에 없다 | 배정 전 자원 예약, 실행 수·토큰·시간 예산, 공정한 대기열 |
| 중간 | master는 기본 2초 간격 관측을 그래프 노드 반복으로 처리하고 매 단계 동기 체크포인트를 저장한다. 결과·원격 상태도 저장 대상이다. 자동 보존 기간 정리는 없다 | 완료 이벤트로 깨우기, 변화 없는 관측 축소, 큰 결과의 참조 저장, 체크포인트 보존·압축·삭제 정책 |
| 중간 | 단일 노드 명령 그래프는 새 UUID thread를 만들고 결과 전체를 저장한다. code-agent 일부 결과는 클로저에만 있어 체크포인트 재생용 상태가 아니다 | 도메인 트랜잭션과 그래프 상태의 책임 명시, 복구가 필요한 노드만 결과를 직렬화. 무조건 resume 전환은 금지 |
| 중간 | master Store는 JSON records를 전체 목록으로 읽고 mission/events를 반복 투영한다 | 프로젝트·업무 번호·Mission·이벤트 순번 인덱스, 페이지 조회와 증분 상태 전달 |

조회 주기·체크포인트 증가의 실제 운영 비용은 부하 측정하지 않았다. 성능 항목은 코드 경로에서 도출한 개선 제안이다. DB 저장 실패·worker 유실·오래된 승인·같은 프로젝트 동시 접수의 장애 주입 시험을 추가할 수 있다. 위 개선 제안은 이번 코드 변경에 포함하지 않는다.

## 접수 식별 보존

1. code-agent는 접수 시 ID·종류를 로컬 식별 기록에 보존한다. 초안 작성 전 접수를 닫아도 feature를 같은 ID의 fix로 바꿀 수 없다. 자동 발급은 보존된 ID를 건너뛴다.
2. 다른 브랜치에 보관된 동일 ID의 request begin·start를 거부한다. 기존 브랜치의 커서·승인·증거를 보존하고 그 자리에서 이어간다.
3. 재제출 시 계획 파일 읽기 실패를 이유로 종류 검사를 생략하던 경로를 제거한다. 후속 수정은 최초 종류로 처리하도록 Claude·Codex 변환 원문을 맞춘다.
4. master는 접수 트랜잭션 안에서 `(projectId, taskNumber)` 중복을 확인한다. 서로 다른 프로젝트에 같은 번호를 사용하는 것은 허용한다. 새 요청 키·그룹과 단일 요청의 중첩·완료 후 재접수는 기존 목표를 안내하고 거부한다. 같은 키·같은 내용의 재전송은 기존 목표를 반환한다. 내부 Task·Attempt ID는 업무 번호와 별도로 유지한다.
5. 프로젝트 상태 형식 세대는 6이다. 식별 기록은 checkout 단위이며 여러 PC의 전역 예약을 제공하지 않는다. master의 업무 번호 중복 판정은 해당 master DB 안의 프로젝트 기준이다.
