입력: `code-agent context` 출력(그대로), `07-test-spec.md`(테스트 명세), `04-functional.md`(AC), 테스트 전략·컨벤션 경로.

- **`07-test-spec.md` 의 TC 를 그대로 구현한다.** 표의 케이스마다 테스트 하나 — 빼지도, 새로 발명하지도 않는다.
  명세가 모자라 보이면 테스트를 늘리지 말고 보고한다 (⑦ 은 승인에 묶여 있어 지금 고칠 수 없다).
- 각 TC 의 **수준**(Unit/Integration/E2E)과 **기대 결과**를 그대로 따른다.
- **⑦ 의 `## 재현` 이 가리킨 TC**(`fix` 에서만 있다)는 **지금 코드에서 실패해야 맞는 것**이다 — 결함이 드러나게 쓴다.
  통과하도록 손보지 않는다. 메인이 `code-agent repro` 로 그 실패를 확인해야 고칠 파일을 쓸 수 있고, 확인된 순간 이 파일들은 언다.
  그 확인은 **실패한 실행의 출력에 그 TC id 가 찍혀야** 성립한다 — 재현 TC 는 특히 **테스트 이름**에 id 를 넣는다 (주석만으로는 세지 않는다).
- **`refactor` 에서는 기준 커밋에 이미 있던 테스트 파일을 고치지도 지우지도 않는다** — 동작이 보존되는지 보는 것이 그 테스트다. hook 이 거부한다.
- 테스트는 **AC 에서** 출발한다. 구현 코드가 하는 일을 그대로 단언하지 않는다 — 그러면 결함도 통과한다.
- **TC id를 실행 결과에 나오는 테스트 이름에 남긴다.** 주석만으로는 실제 통과를 증명하지 못한다. TAP · Node spec · unittest -v · pytest -v · go test -json 또는 code-agent-test JSONL 결과를 사용한다.
- 참조 표준 테스트의 구조·명명·픽스처 방식, 테스트 전략의 데이터·격리 방식을 따른다.
- **테스트는 `code-agent test` 가 처음 돌기 전에 다 써 둔다.** 한 번 돌면 동결되며, review 단계에서 기록된 독립 리뷰 지적이 해당 계획 파일을 가리킬 때만 수정할 수 있다. refactor의 기준 커밋 테스트는 계속 보호한다.
  실패를 고치려고 **단언을 지우거나 약하게 바꾸는 일은 없다.** 구현이 틀렸으면 구현을 고치는 것이고, 테스트가 틀렸다고 보이면 근거와 함께 보고한다.
- 만들 파일 목록 밖은 쓰지 않는다. 거부되면 보고하고 멈춘다.
