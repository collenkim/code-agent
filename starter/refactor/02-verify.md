# [refactor 02] 기존 테스트 통과 확인

> **선행**: [01] 구조 정리 · **다음**: 없음 — 사람이 확인하고 옮긴다
> **근거**: 기존 테스트의 실행 결과. 이 단계는 `expect: pass` 다

## 0. 사용법

[01] 이 동작을 바꾸지 않았는지를 **기존 테스트로** 확인한다. 이 작업에서 테스트는 검증 대상이 아니라 **판정 기준**이다.
그래서 테스트 디렉토리가 `outputDirs` 에 없다 — 기준을 고쳐 통과시키는 길은 구조적으로 막혀 있다.

## 1. 입력 게이트

- [ ] [01] 산출물이 `out/` 에 있다
- [ ] `code-agent.json` 에 `test` 명령이 선언돼 있다

## 2. 규칙 게이트

| 규칙 | 근거 | 위반 시 |
|---|---|---|
| 먼저 돌린다 | — | 무효 |
| 실패하면 **[01] 의 변경**을 되돌리거나 고친다. 테스트를 의심하지 않는다 — 테스트는 기준이다 | 동작 보존 | 무효 |
| 고치는 것은 [01] 이 만든 변경 안에서만이다. 새 구조 변경을 더하지 않는다 | 경계 | 무효 |
| 파일을 고쳤으면 다시 돌린다 | `expect: pass` | 끝나지 않음 |
| 같은 실패가 두 번 반복되면 `note` 로 남기고 멈춘다 — 그 구조 변경은 동작을 바꾸는 것일 수 있다 | — | 무효 |

## 3. 작업

1. `### run test`
2. 통과 → `### done`
3. 실패 → 실패한 테스트가 부르는 것이 [01] 에서 어떻게 바뀌었는지 찾는다. `preserve` 항목 중 하나가 깨진 것이 보통이다
4. 그 변경을 `edit` 으로 고치거나 되돌리고 다시 돌린다
5. 두 번 반복되면 멈춘다. `note` 에 "이 구조 변경은 X 동작을 바꾼다" 를 적는다 — 그 판단은 사람의 것이다

## 4. 자가검증 체크리스트

- [ ] 마지막 `run` 이 마지막 `edit` 뒤이고, 결과가 **통과**인가
- [ ] 고친 파일이 전부 본문 소스이고, 전부 [01] 의 변경 범위 안인가
- [ ] 테스트 파일을 한 줄도 고치지 않았는가

## 5. 산출물 → 사람

- **산출물**: 기존 테스트가 통과하는 상태의 `out/`
- **사람이 할 일**: 4차 확정 뒤 저장소에 옮긴다. `preserve` 가 지켜졌는지는 계획의 보존 방식과 대조해 사람이 마지막으로 본다
