# code-agent 설계 — Claude Code 위에서 도는 코드 작성 에이전트

> 상태: **초안** (2026-09-28). 합의되면 이 문서가 정본이 되고, README 는 여기를 가리킨다.
> 붙여넣기 왕복·서버 모드는 이 설계로 대체된다.

## 1. 역할

**code-agent 는 요구사항을 받아 코드를 쓰는 에이전트다.** 그 밖의 일은 하지 않는다.

| 한다 | 하지 않는다 |
|---|---|
| 요구사항 분석, 모호한 점 질문 | 아이디어 발굴·시장 조사 (AI-DLC Ideation) |
| 필요한 문서 확인, 없으면 작성 유도 | 배포·인프라·관측 (AI-DLC Operation) |
| 개발 계획, 문서와 참조 코드를 읽고 코드·테스트 작성 | 유료 도구를 등록 없이 쓰는 것 |
| 검증하고 더 나은 방향으로 고쳐 쓰기 | 사람 대신 승인하는 것 |

실행 틀은 AI-DLC 와 같다 — **Claude Code 안에서 모델이 도구를 직접 쓰고**, 규칙은 스킬·에이전트 정의로,
강제는 hook 과 CLI 로 한다. 다른 점은 AI-DLC 가 사후에 대조하는 것을 **쓰기 전에** 막는다는 것,
그리고 읽을 참조 코드를 **코드가** 고른다는 것이다.

## 2. 문서 — 무엇이 반드시 있어야 하고 무엇이 유동적인가

문서가 근거다. 없는 문서는 모델이 지어내는 자리가 된다. 그렇다고 모든 문서를 미리 요구하면 레거시에서는
시작조차 못 한다. 그래서 둘로 나눈다.

### 2.1 프로젝트 필수 문서 — 없으면 무조건 막는다

| 문서 | 필수 섹션 (코드가 검사) |
|---|---|
| **아키텍처 (뼈대 구조)** | 기술 스택 · 모듈/패키지 구조 · 계층과 책임 · 의존 방향 · 공통 모듈 · 주요 결정(식별자·트랜잭션·예외·인증 등) |
| **코드 컨벤션** | 명명 · 계층별 규칙 · 예외 처리 · 테스트 규칙 |

통과 조건 — 둘 다 셋을 만족해야 어떤 작업도 요구사항 분석 이후로 가지 않는다.

1. 파일이 있다 (`code-agent.json` 의 `docs` 에 등록된 경로)
2. 필수 섹션이 있고 비어 있지 않다 — 섹션 목록은 문서 종류별 스키마(`doc-schemas/*.json`)가 정한다
3. **사람이 확정했다** — `code-agent confirm doc <종류>` 가 문서 해시를 원장에 남긴다. 확정 뒤 바뀌면 다시 확정한다

### 2.2 작업 문서 — 요구사항에 따라 유동적

| 문서 | 언제 필요한가 | 없을 때 |
|---|---|---|
| **요구사항 (작업 지시서)** | 모든 작업 — 작업의 입력 자체 | 머리말(kind·id·title·target)만 있으면 시작한다. 내용이 얇으면 분석 스테이지가 질문으로 채운다 |
| 데이터 정의 | 요구사항이 데이터를 만들거나 바꿀 때 | **요구사항 범위만** 자동 생성 — 요구사항 + 관련 코드 역공학으로 초안, 빈칸은 질문 |
| API·화면 정의 | 요구사항이 외부 접점을 만들거나 바꿀 때 | 같음 |
| 현행 분석 | 레거시를 고칠 때 (fix·refactor·기존 도메인 확장) | 요구사항 범위 역공학으로 자동 생성 |
| 업무 개요 · 컴포넌트 목록 · API 목록 · 의존성 | 계획이 참고할 때 | 있으면 읽는다. 없어도 막지 않는다 |

**무엇이 필요한지는 분석 스테이지가 정한다** — analyst 가 요구사항 항목마다 "데이터를 건드리는가, 접점을 건드리는가"를
판정하고, 필요한 작업 문서 목록을 낸다. 이미 있는 프로젝트 문서(예: 전체 데이터 사전)가 그 범위를 덮으면 새로 만들지 않고 인용한다.

작업 문서는 따로 확정받지 않는다. **계획과 한 묶음으로 승인된다** — 계획 승인 해시에 프로젝트 필수 문서 해시와
작업 문서 해시가 함께 들어간다. 승인은 "이 문서들을 근거로 한 이 계획"에 대한 것이다.

### 2.3 문서를 만드는 세 경로

| 경로 | 언제 | 어떻게 |
|---|---|---|
| **리버스엔지니어링** | 코드가 있을 때 | 서브에이전트가 코드를 분석해 초안. 모든 서술에 근거 경로. 코드로 알 수 없는 것(의도·이유)은 빈칸 → 질문 |
| **사용자 입력** | 코드가 없을 때(신규), 의도·결정·새 요구처럼 코드에 없는 내용 | 스키마 빈칸을 코드가 찾아(`findGaps`) 선택지 질문으로 묻고 답을 문서로 옮긴다. 결정은 선택지와 트레이드오프를 보여 주고 사람이 고른다 |
| **기존 문서 연결** | 다른 곳에 이미 있을 때 | 경로만 등록. 필수 섹션 검사는 똑같이 받고, 모자란 섹션만 위 두 경로로 채운다 |

보통은 섞인다 — **역공학 초안 → 남은 빈칸은 사용자 입력.** 신규 프로젝트의 아키텍처는 전부 사용자 입력이다.

### 2.4 리버스엔지니어링은 두 층이다

| 층 | 범위 | 언제 | 산출물 |
|---|---|---|---|
| **뼈대 역공학** | 프로젝트 전체를 **얕게** — 빌드 파일, 디렉토리 구조, 계층별 표본 몇 개 | 필수 문서가 없을 때 한 번 | 아키텍처 · 코드 컨벤션 초안 |
| **요구사항 범위 역공학** | 요구사항이 닿는 코드만 **깊게** — 관련 파일, 호출 경로, 현행 데이터·API | 작업마다 | 현행 분석 · 데이터 정의 · API 정의 (그 범위만) |
| (선택) 전체 역공학 | 프로젝트 전체를 깊게 | 사람이 원할 때 (`/ca-docs --full`) | 업무 개요 · 컴포넌트 목록 · API 목록 · 의존성 |

레거시에 처음 들어갈 때 전체를 깊게 분석할 필요가 없다. **뼈대만 얕게 → 작업마다 필요한 곳만 깊게.**
큰 저장소일수록 이 차이가 토큰 비용을 가른다.

## 3. 스테이지

| # | 스테이지 | 하는 일 | 누가 | 게이트 |
|---|---|---|---|---|
| 0 | 준비 | `init` 설치, 워크스페이스 감지 (신규/레거시, 필수 문서 유무) | CLI | — |
| 1 | 프로젝트 문서 | 아키텍처·코드 컨벤션 점검. 없으면 뼈대 역공학 또는 사용자 입력으로 작성 | CLI 점검 + surveyor·writer | **둘 다 확정돼야 2 이후 진행** |
| 2 | 요구사항 분석 | 요구 항목화, 모호·누락·충돌을 질문으로, **필요한 작업 문서와 조사 범위 판정** | 메인 + analyst | 질문에 답해야 진행 |
| 3 | 범위 조사·작업 문서 | 요구사항 범위 역공학(항목별 병렬), 필요한 작업 문서 초안(데이터·API·현행), 빈칸 질문 | 메인 + explorer·writer | 질문에 답해야 진행 |
| 4 | 개발 계획 | 작업 단위 · 파일 · 적용 컨벤션 · 테스트 전략 · 위험 | 메인 → critic | **사람 승인 (터미널)** — 작업 문서 포함 |
| 5 | 구현 | 작업 단위마다 새 컨텍스트에서 코드와 테스트 | implementer · tester | hook — 계획 밖 쓰기 거부 |
| 6 | 검증·개선 | build/test/lint, 리뷰, 고쳐 쓰기 (최대 2회) | CLI + reviewer → implementer | 코드 — 기대 결과 대조 |
| 7 | 인계 | 요구사항 → 파일 → 테스트 추적표, 변경 요약, 로컬 커밋 | 메인 + CLI | 사람 확인 |

**작업 종류**는 어떤 스테이지를 도는지로 갈린다.

| 종류 | 스테이지 |
|---|---|
| `adopt` | 0 → 1 (프로젝트 필수 문서를 처음 갖춘다) |
| `feature` | 1 (점검) → 2 → 3 → 4 → 5 → 6 → 7 |
| `fix` | 1 (점검) → 2 → 3 (현행 분석 필수) → 4 (재현 테스트 먼저) → 5 → 6 → 7 |
| `refactor` | 1 (점검) → 2 → 3 (현행 분석 필수) → 4 (preserve 필수) → 5 → 6 → 7 |

어느 작업이든 1 의 점검을 먼저 지난다. 필수 문서가 없으면 거기서 멈추고 작성으로 안내한다 —
`/ca-feature` 를 불렀더라도 `/ca-docs` 로 돌려보낸다.

### 질문은 어느 스테이지에서든 던진다

애매하거나 모호하면 지어내지 않고 묻는다. 질문은 작업 폴더의 `questions.md` 에 쌓이고, **답이 없는 질문이
있으면 다음 스테이지로 넘어가지 않는다** (Stop hook 과 `code-agent next` 가 확인).

```
## Q3 · 요구사항 분석
주문 취소 후 재주문이 가능한가?
A. 가능 — 새 주문번호
B. 불가
X. 기타:
[Answer]:
```

답은 채팅으로 해도 된다 — 메인 에이전트가 파일에 옮긴다. 질문의 답은 승인이 아니므로 터미널을 요구하지 않는다.
**승인·확정만 터미널**이다 (모델 세션 안의 승인은 모델이 한 것과 구분되지 않는다).

### 검증·개선 루프

```
구현 → verify(build·test·lint, worktree) → reviewer(컨벤션·요구사항 충족·참조 코드와의 차이)
     → 고칠 것이 계획 안이면 implementer 가 고쳐 쓴다 (최대 2회)
     → 계획 밖이면 질문 또는 재계획 (재승인)
     → 2회 뒤에도 실패면 덮지 않고 보고한다 — 테스트 단언을 지워 통과시키는 길은 hook 이 막는다
```

## 4. 메인 에이전트와 서브에이전트

**메인 에이전트**는 사용자와 대화하는 Claude Code 세션 자체다. 스킬(`/ca-*`)을 따라 순서를 진행하고,
서브에이전트를 부르고, 결과를 합친다. 코드를 직접 많이 쓰지 않는다 — 메인 컨텍스트가 작아야 긴 작업이 버틴다.

| 서브에이전트 | 스테이지 | 도구 | 하는 일 |
|---|---|---|---|
| `ca-surveyor` | 1 | 읽기 전용 | 뼈대 역공학 — 영역 하나(빌드·구조·계층 표본)를 맡아 근거 경로가 달린 분석. 여럿 병렬 |
| `ca-analyst` | 2 | 읽기 전용 | 요구 항목화, 모호·누락·충돌을 질문 후보로, 항목별 "데이터·접점을 건드리는가" 판정 |
| `ca-explorer` | 3 | 읽기 전용 | 요구사항 범위 역공학 — 항목 하나의 관련 파일·호출 경로·현행 데이터·API. 항목마다 병렬 |
| `ca-writer` | 1, 3 | 쓰기 (문서 경로만) | 분석 결과·사용자 답을 문서 스키마 섹션에 맞춰 문서로 |
| `ca-critic` | 4 | 읽기 전용 | 계획 반박 검토 — 빠진 요구 항목, 계획 밖 파일 필요성, 테스트 공백, 작업 문서와의 불일치 |
| `ca-implementer` | 5, 6 | 쓰기 (hook 강제) | 작업 단위 하나. `code-agent context` 로 받은 것만 읽고 시작 |
| `ca-tester` | 5 | 쓰기 (테스트 경로만) | 테스트 작성. 구현과 다른 컨텍스트라 구현을 베끼지 않는다 |
| `ca-reviewer` | 6 | 읽기 전용 | 컨벤션·요구사항 충족·참조 코드와의 차이. 고칠 목록만 낸다 |

**2~4 스테이지의 흐름** — 서브에이전트를 가장 적극적으로 쓰는 곳이다.

```
메인 + ca-analyst: 요구 항목 N개, 질문, 필요한 작업 문서(데이터·API·현행), 조사 범위
  ↓ 질문 답변
  ├─ ca-explorer × N (병렬) ── 항목별 관련 코드·현행 데이터·API (요구사항 범위 역공학)
  ├─ code-agent context ───── 참조 코드·컨벤션 (결정론적)
  └─ (등록됐으면) 플러그인 판정 ── 후보 파일 순위 등
메인 + ca-writer: 작업 문서 초안 → 빈칸 질문 → 답변 반영
메인: 계획 초안 (작업 단위·파일·컨벤션·테스트·위험)
  └─ ca-critic ── 반박 → 메인이 반영하거나 질문으로
code-agent plan submit ── 문서 게이트·스키마·preserve 검사, 저장
사람: code-agent approve (터미널) ── 계획 + 작업 문서 한 묶음
```

**작업 단위 병렬** — 계획이 서로 파일을 공유하지 않는 작업 단위를 표시하면, 메인이 implementer 를 병렬로 부른다.

각 에이전트의 모델은 `code-agent.json` 의 `agents` 에서 고른다. 기본은 역공학·탐색은 가벼운 모델, 계획·구현은 상위 모델이다.

## 5. 강제 — 모델이 어겨도 막히는 것

| 무엇 | 어디서 | 시점 |
|---|---|---|
| 프로젝트 필수 문서(아키텍처·컨벤션)가 없거나 미확정이면 분석 이후 진행 거부 | `code-agent next` · `plan submit` | 스테이지 전환 |
| 작업 문서가 분석 결과에 필요하다고 나왔는데 없으면 계획 제출 거부 | `code-agent plan submit` | 계획 전 |
| 문서 스테이지(1·3)에는 문서 경로 밖 쓰기 금지 | PreToolUse hook | 쓰기 전 |
| 계획 승인 전 코드 쓰기 금지 | PreToolUse hook → `code-agent hook` | 쓰기 전 |
| 계획에 없는 파일, scope 밖, preserve, 계층 경계 | 같음 (코어 `checkPaths`·`unplannedFiles`) | 쓰기 전 |
| `.code-agent/` 상태·원장 변조 | 같음 | 쓰기 전 |
| Bash 는 허용 목록만 (`code-agent *`, 선언된 명령, 읽기용 git) | 같음 | 실행 전 |
| 답 없는 질문이 있으면 진행 금지 | Stop hook · `code-agent next` | 턴 끝 |
| 단계 종료 시 실제 변경과 계획 대조 (`git diff`) | Stop hook | 턴 끝 |
| 승인·확정은 사람만 | `approve` · `confirm` 의 TTY 검사 | 승인 시 |
| 승인은 무엇에 대한 것인가 | 원장 해시 사슬 — 지시서·계획·매니페스트·문서 | 매 쓰기 |

경로는 실제 경로로 풀어 비교한다 (Windows 8.3 이름·junction — 스파이크에서 확인).
hook 은 사고 방지 장치이지 보안 경계가 아니다 — 개발자는 로컬 설정으로 끌 수 있다.

## 6. 플러그인과 도구

**원칙: 무료로 되는 것은 등록 없이 쓰고, 유료는 사용자가 등록해야만 쓴다. 아무것도 없어도 전 과정이 돈다.**

### 자리(slot) — 플러그인이 끼는 곳

code-agent 코어가 자리를 정의하고, 자리마다 **기본 구현**이 있다. 플러그인은 자리를 대신 채울 뿐이다.

| 자리 | 쓰이는 곳 | 기본 구현 (등록 없이) | 예: 채울 수 있는 플러그인 |
|---|---|---|---|
| `survey.classify` | 1 뼈대 역공학 — 파일을 계층·컴포넌트로 분류 | 경로 규칙 + surveyor | Jev |
| `candidates.rank` | 3 범위 조사, fix — 요구 항목과 관련된 파일 순위 | ripgrep + explorer | Jev, 코드 검색 서비스 |
| `review.prefilter` | 6 검증 — 규칙 위반 의심 항목 | reviewer 가 전부 봄 | Jev |
| `context.docs` | 3~5 — 컨벤션·외부 문서에서 필요한 섹션 | 제목 매칭 | Jev, 문서 MCP |
| `code.index` | 1·3 — 심볼·호출 관계 | ripgrep | LSP 플러그인, 코드 인덱스 MCP |
| `verify.extra` | 6 — build/test 외 검사 | 매니페스트의 lint 명령 | 정적 분석 도구 |

### 등록

```
code-agent plugin list                  # 자리, 기본 구현, 감지된 무료 도구, 등록된 플러그인
code-agent plugin add jev               # 터미널에서 키 입력 → 사용자 설정(저장소 밖)에 저장
code-agent plugin remove jev
```

- **무료 도구**(ripgrep, LSP, 매니페스트에 선언한 linter)는 설치돼 있으면 자동으로 쓴다.
- **유료 도구**는 `plugin add` 로 키를 등록해야만 켜진다. 키는 `~/.code-agent/credentials.json` 에만 있고
  저장소에는 "어떤 플러그인을 쓰는 프로젝트인가"만 남는다. 외부로 코드를 보내는 플러그인은 등록 시 그 사실을 경고한다.
- 플러그인은 **명령 어댑터**다 — JSON 을 stdin 으로 받아 JSON 을 stdout 으로 낸다 (hook 과 같은 규약, 언어 무관).
  모델이 직접 써야 하는 도구(문서 조회 등)는 MCP 서버로 등록해 `.mcp.json` 에 넣는다.
- 판정 플러그인은 **CLI 가 부른다**, 모델이 아니라. 쓸지 말지를 모델이 정하면 그 판단에 토큰이 들고 결과가 흔들린다.
- 플러그인의 판정은 입력 요약·결과·임계값과 함께 `.code-agent/log/` 에 남는다. 실패하면 기본 구현으로 떨어지고 알린다.

## 8. 배포와 대상 저장소

```
npm install -g <사내 저장소>/code-agent     # 한 번
cd <프로젝트> && code-agent init             # 프로젝트마다 — .claude/ 설치, 버전 고정
claude  →  /ca-docs  →  (터미널) code-agent confirm doc architecture · conventions
        →  /ca-feature doc/work/ORD-1.md  →  (터미널) code-agent approve  →  /ca-next …
```

| 대상 저장소에 생기는 것 | 커밋 |
|---|---|
| `CLAUDE.md` 의 code-agent 블록, `.claude/skills/ca-*`, `.claude/agents/ca-*`, `.claude/settings.json` hook | O |
| `code-agent.json` (`docs` 에 문서 종류 → 경로 등록) | O |
| `doc/architecture.md`, `doc/conventions/` — 프로젝트 필수 문서 | O |
| `doc/knowledge/` — 전체 역공학 참고 문서 (선택) | O |
| `doc/work/<ID>.md` — 작업 지시서·요구사항 | O |
| `doc/work/<ID>/` — 작업 폴더: 분석, 질문, 작업 문서(데이터·API·현행), 계획 초안, 추적표. **모델과 사람이 쓴다** | O |
| `.code-agent/work/<ID>/<대상>.plan.json` — 제출된 계획. `plan submit` 만 쓴다 | O |
| `.code-agent/approvals/` — 승인·확정 원장 | O (증거) |
| `.code-agent/active.json`, `.code-agent/log/` | X |

`.code-agent/` 는 **코드만** 쓴다 — hook 이 모든 도구 쓰기를 막는다. 모델이 쓸 것은 전부 작업 폴더에 있다.

### 작업 브랜치

`start` 가 `<종류>/<ID>`(예: `feature/ORD-1`, `fix/BUG-3`) 를 기준 브랜치에서 따서 옮긴다. 이미 있으면 전환만 한다.
기준 브랜치는 **사용자 입력(`--base`) > `code-agent.json` 의 `git.base` > `master`** 순이다.
모델은 브랜치를 바꿀 수 없다 — hook 이 읽기용 git(status·diff·log·show·branch)만 허용한다.

작업 문서 중 오래 쓸 가치가 있는 것(새 도메인의 데이터 정의 등)은 인계 스테이지에서 `doc/` 로 올릴지 묻는다.
레거시에 문서가 조금씩 쌓이는 길이 이것이다.

## 9. 명령

| Claude Code 안 | 하는 일 |
|---|---|
| `/ca-docs` | 프로젝트 필수 문서 점검·작성 — 빠진 문서마다 역공학 / 사용자 입력 / 기존 문서 연결 중 고르게 한다. `--full` 은 전체 역공학 |

| `/ca-answer` | 남은 질문을 하나씩 묻고 기록 |

|---|---|
| `code-agent docs` | 문서 게이트 상태 — 종류별 있음·섹션·확정 여부 |
| `code-agent confirm doc <종류>` | 프로젝트 필수 문서 확정 (해시를 원장에) |
| `code-agent approve` · `reject` | 계획 + 작업 문서 판정 (diff 표시, 반려 사유 필수) |
| `code-agent status` · `abort` · `usage` | 상태 · 중단 · 토큰 집계 |
| `code-agent init` · `update` · `plugin ...` | 설치 · 갱신 · 플러그인 |

## 11. 구현 순서

| 단계 | 내용 | 완료 기준 |
|---|---|---|
| P1 뼈대 | CLI(`init` `hook` `context` `plan submit` `approve` `status` `next`), `.claude/` 템플릿(CLAUDE.md 블록·hook·스킬·에이전트 정의), 작업 폴더 구조, `docs` 등록 | 스파이크 판정 13개를 테스트로 이관해 통과, 테스트 저장소에서 `init` → `/ca-status` |
| P2 프로젝트 문서 | 문서 스키마(아키텍처·컨벤션), `code-agent docs`·`confirm doc`, `/ca-docs` 의 세 경로, 뼈대 역공학, `/ca-adopt` | 필수 문서 없는 저장소에서 진행이 거부되고, 레거시 1개는 뼈대 역공학으로·빈 저장소 1개는 인터뷰로 두 문서가 만들어져 게이트 통과 |
| P3 분석·범위 조사·계획 | analyst(작업 문서 판정), explorer(범위 역공학), writer(작업 문서), critic, 질문 루프 | 레거시 저장소에서 데이터 정의 없이 시작해 요구사항 범위 작업 문서가 생기고 승인 가능한 계획까지, 토큰 기준치 기록 |
| P4 구현·검증·인계 | implementer·tester·reviewer, 개선 루프, worktree verify, 추적표·로컬 커밋 | 실제 프로젝트에서 feature 한 건 완주 (첫 실측) |
| P5 fix·refactor | 현행 분석 필수, 재현 테스트 먼저, preserve 강제 | 각 한 건 완주 |
| P6 플러그인 | 자리 정의, `plugin add/list/remove`, 무료 도구 감지, Jev 어댑터 | Jev 켜고/끄고 같은 저장소 A/B 토큰 비교 |
| P7 정리 | 옛 코드 삭제, 문서 세트, `usage`, 다른 PC 설치 검증 | 다른 개발자가 혼자 설치부터 feature 까지 |
