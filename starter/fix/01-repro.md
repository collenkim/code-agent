# [fix 01] 재현 테스트

> **산출물**: 지금 코드에서 **실패하는** 테스트 하나 · **다음**: [02] 수정
> **근거**: 스펙의 결함 서술(무엇을 넣었을 때 무엇이 나와야 하는데 무엇이 나오나) · 대상의 현재 코드
> 이 단계는 `expect: fail` 이다 — 테스트를 돌려 **실패를 확인**해야 끝난다. 통과하면 재현하지 못한 것이다.

## 0. 사용법

고치기 전에 결함을 **테스트로 고정**한다. 이 테스트가 없으면 [02] 의 "고쳤다"는 확인할 수 없는 말이다.

**do-not-touch**: 이 단계의 `outputDirs` 는 테스트 디렉토리만이다. **본문 소스를 고치지 않는다** — 고치고 싶은 것을 발견해도 `note` 에 적고 넘어간다. 그것이 [02] 의 입력이 된다.

## 1. 입력 게이트

- [ ] 스펙에 결함 서술이 있다 — 입력 · 기대 결과 · 실제 결과. 셋 중 하나라도 없으면 `ask`
- [ ] 지시서의 `scope` 안에 결함이 있는 코드가 있다. 없으면 지시서가 틀린 것이다 — `ask`
- [ ] 「대상의 현재 파일」에 기존 테스트가 실려 있다 — 테스트의 모양은 여기서 배운다

## 2. 규칙 게이트

| 규칙 | 근거 | 위반 시 |
|---|---|---|
| 기존 테스트와 같은 위치·명명·픽스처 방식을 쓴다 | 대상의 현재 테스트 | 무효 |
| 테스트는 **스펙의 결함 서술 그대로**를 검증한다 — 입력을 넣고 기대 결과를 단언한다 | 스펙 | 무효 |
| 결함과 무관한 검증을 끼워 넣지 않는다. 테스트 하나, 단언은 결함에 대한 것만 | — | 무효 |
| 본문 소스를 고치지 않는다 | 경계 | 무효 |
| `### run test` 로 돌려 **실패**를 확인한다. 통과하면 테스트가 틀린 것이다 — 고쳐서 다시 돌린다 | `expect: fail` | 끝나지 않음 |

## 3. 작업

1. 기존 테스트 하나를 골라 골격(위치·기반·픽스처)을 가져온다
2. 스펙의 결함 서술을 그대로 옮긴다 — 입력 준비 → 실행 → **기대 결과** 단언. 실제 결과가 아니라 기대 결과를 단언한다
3. `### run test` (또는 `commands` 에 선언된 필터)로 돌린다
4. 실패했으면 `### done`. 통과했으면 재현이 안 된 것이다 — 입력·단언을 스펙과 다시 대조하고 고쳐서 다시 돌린다
5. 결함을 재현할 수 없다고 판단되면 그 근거를 `note` 에 적고 `### done` 없이 멈춘다

## 4. 자가검증 체크리스트

- [ ] 만든 파일이 계획의 목록과 같고, 전부 테스트 디렉토리 아래인가
- [ ] 단언이 스펙의 **기대 결과**를 말하는가 (실제 결과를 단언해 놓고 통과시킨 것이 아닌가)
- [ ] 마지막 `run` 의 결과가 **실패**이고, 그 뒤에 파일을 바꾸지 않았는가
- [ ] 본문 소스를 한 줄도 고치지 않았는가

## 5. 산출물 → 다음 단계 입력

- **산출물**: 실패하는 테스트
- **[02] 입력**: 그 테스트의 실패 메시지 — 고칠 자리가 여기서 특정된다
