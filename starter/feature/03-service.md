# [feature 03] Command · Query 처리

> **선행**: [01] Entity · [02] Repository · **다음**: [04] Controller + DTO
> **근거**: 참조 표준 도메인의 `command/` `query/` `facade/`

## 0. 사용법

이 단계가 **배선**을 정한다 — 어느 계층이 트랜잭션을 열고, 어느 계층이 Repository 를 부르고, 예외는
어디서 던지는가. 그 답은 전부 참조 표준에 있다. 컨벤션 문서의 문장보다 참조 표준의 실제 코드가 근거다.

**do-not-touch**: `outputDirs` 밖에 파일을 만들지 않는다. Repository 에 메서드를 더해야 한다면 `note`.

## 1. 입력 게이트

- [ ] [01]·[02] 산출물이 실려 있다
- [ ] 스펙에 유스케이스와 그때의 제약·에러가 있다 — 처리 단위는 유스케이스마다 하나다. 없으면 `ask`
- [ ] 참조 표준의 처리 계층 파일들이 실려 있다 (디렉토리형 참조는 상한까지만 실린다 — 목록은 전부 보인다)

## 2. 규칙 게이트

| 규칙 | 근거 | 위반 시 |
|---|---|---|
| 계층 간 호출 방향은 참조 표준과 같다. 건너뛰거나 거슬러 부르지 않는다 | 참조 표준 배선 | 무효 |
| 트랜잭션 경계는 참조 표준이 두는 계층에 둔다 | 참조 표준 | 무효 |
| 예외를 던지는 계층과 잡는 계층이 참조 표준과 같다 | 참조 표준 | 무효 |
| 유스케이스 하나 = 처리 단위 하나. 스펙에 없는 유스케이스를 만들지 않는다 | 스펙 | 무효 |
| 다른 도메인의 처리 계층을 직접 부르지 않는다 — 참조 표준이 하는 방식을 따른다 | 참조 표준 | 무효 |
| 스펙의 제약이 깨질 때의 에러는 스펙에 적힌 것을 쓴다. 에러 코드를 발명하지 않는다 | 스펙 | 무효 |

## 3. 작업 — 스켈레톤

1. 참조 표준에서 **유스케이스 하나의 흐름**을 골라 끝까지 따라간다 — 어느 파일에서 시작해 어디를 거쳐 Repository 에 닿는가
2. 그 흐름의 파일 구성(클래스 수·이름 규칙·주입 방식)을 이 도메인의 유스케이스마다 복제한다
3. 검증·제약 처리는 참조 표준이 하는 자리에서 한다. 스펙의 제약 목록을 하나씩 대응시킨다
4. 참조 표준에 대응이 없는 처리(외부 연동·비동기 등)가 필요하면 만들지 말고 `ask`

## 4. 자가검증 체크리스트

- [ ] 만든 파일이 계획의 목록과 같은가
- [ ] 각 처리 단위가 스펙의 유스케이스 하나로 되짚어지는가
- [ ] 계층 간 호출 방향이 참조 표준의 흐름과 같은가 — 표로 나란히 놓아 확인했는가
- [ ] 트랜잭션 어노테이션·예외 처리가 참조 표준과 **같은 계층**에 있는가
- [ ] 스펙의 제약이 전부 대응됐고, 스펙에 없는 에러 코드가 없는가

## 5. 산출물 → 다음 단계 입력

- **산출물**: 처리 계층
- **[04] 입력**: 처리 단위의 이름과 입력·출력 타입 — Controller 와 DTO 가 이것에 맞춘다
