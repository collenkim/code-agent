**질문·동의** — 사람에게 묻거나 승인·확정·반영을 받기 직전에 `.claude/skills/ca-answer/SKILL.md`를 읽고 그 절차(`AskUserQuestion`·같은 세션 동의)를 따른다. 일반 답변은 승인이 아니며, 적용 뒤에는 이 흐름을 자동으로 이어간다.

`.claude/skills/ca-feature/SKILL.md` 의 절차를 그대로 따른다 — 접수는 **종류 `fix`** 로 하고, 같은 단계 스킬을 같은 순서로 돈다.
접수에서 `target` 은 결함이 있는 **저장소 경로**, `scope`(건드려도 되는 경로)와 `preserve`(바뀌면 안 되는 것)는 필수다 — 원문으로 정할 수 없으면 묻는다.
**fix 는 오류 로그로 고친다.** 접수에 오류 로그(`errorLog`·`errorLogFile`)가 필수이고, 로그가 없는 신고만 `noErrorLog`(사유·재현 절차)로 대신한다 — 지시서의 `## 오류 로그` 절이 1차 근거다. 로컬 재현은 될 수도 안 될 수도 있다.
다른 점은 아래 넷이고, **전부 코드가 막는다** (지시가 아니다).

- **영향도 (`/ca-impact`)**: `02-analysis.md` 의 `기존 시스템 분석` 은 **결함이 나는 경로까지** 적는다 — 증상이 어느 코드 경로에서 나는지.
  `해당 없음` 으로 비울 수 없고 근거 `path:line` 이 최소 하나 있어야 `code-agent next` 가 넘어간다.
  지시서에 오류 로그가 있으면 **로그 대응 줄**이 최소 하나 필요하다 — 로그 문구를 백틱으로 **그대로** 인용하고 같은 줄 백틱 밖에 저장소에 있는 원인 코드 `path:line` 을 적는다
  (`- \`NullPointerException: items is null\` → src/main/java/app/OrderService.java:42 — items 를 확인하지 않는다`). 스택 트레이스를 따라 실제 원인 줄까지 내려간다.
- **테스트 명세 (`/ca-plan`)**: `07-test-spec.md` 에 `## 재현` 절을 두고 결함을 재현하는 TC id 를 `- TC-1` 로 한 줄씩 적는다.
  거기 적은 id 는 `테스트 케이스` 표에 실재해야 하고, **수준(Unit/Integration/E2E)은 무엇이든 된다.** 없으면 `plan submit` 이 거부한다.
  로그의 발생 조건(운영 데이터·동시성·외부 연동 등)을 로컬에서 만들 수 없다고 판단되면 그 절에 `- 방식: 로그 근거 — <로컬에서 재현하지 않는 사유>` 를 함께 적는다.
  그러면 그 TC 는 **로그의 발생 조건(입력·상태)을 담은 회귀 TC** 다 — 수정 전 실패를 요구하지 않고 수정 후 통과해야 한다. 지시서에 오류 로그가 없으면 로그 근거로 계획할 수 없다. 사람은 계획 승인 때 이 방식을 함께 본다.
- **계획 (`/ca-plan`)**: `sequence[0]` 은 `kind: "test"` 단계여야 하고, `files[]` 에 그 단계의 파일이 있어야 한다.
  그 단계에 적는 파일은 **그 단계가 밝힌 테스트 자리 안**이어야 한다 (`code-agent context` 가 그 자리를 찍어 준다) —
  고칠 파일을 테스트 단계에 적어 넣는 계획은 거부된다. '재현 먼저' 를 단계 이름표로 재기 때문이다.
  고칠 파일은 지시서의 scope 안에서만. 지시서의 보존 조건(preserve)은 계획의 `preserve[]` 에 문장 그대로,
  하나도 빠짐없이 옮기고 각각 어떻게 지켜지는지 적는다 — 빠지면 `plan submit` 이 거부한다.
- **구현 (`/ca-implement`)**: 커서가 **테스트 단계에 먼저** 선다. 재현 테스트를 쓰고 Bash: `code-agent repro` —
  로컬 재현이면 지금 코드에서 그 TC 가 **실패**하는 것을 본 뒤에야, 로그 근거(계획 승인 또는 사람 확인)면 수정 전 결과를 남긴 뒤에 hook 이 고칠 파일 쓰기를 연다.
  고치고 나서 쓴 테스트는 결함을 재현한 적이 없다. repro 를 지난 순간 `kind: "test"` 단계의 파일은 **언다**
  (단언을 약하게 하면 재현이 증거가 아니게 된다). 고친 뒤 `check` → `test` 에서 **같은 TC 가 이제 통과**해야 끝난다.

**재현 테스트의 이름에 TC id를 남긴다** (컨벤션의 `테스트 규칙`). `code-agent repro`는 이번 실행의 콘솔 또는 새 JUnit 보고서에서 **지정한 재현 TC 자체가 failed**인 것을 확인한다. ID가 로그·주석에 있거나 다른 TC가 실패했다는 사실만으로는 재현이 아니다.

원인을 확신할 수 없으면 추정으로 계획하지 않고 `questions.md` 에 가설과 확인 방법을 질문으로 남긴다.

**로컬 재현이 안 될 때** (`code-agent repro` 가 `재현하지 못했습니다`·환경 오류로 끝남):
- 먼저 재현 테스트가 로그의 발생 조건을 제대로 담았는지 다시 본다. TC 이름·결과 보고서 연결 문제면 고쳐 다시 돌린다. 러너나 어댑터 선택을 사용자에게 반복해서 묻지 않는다.
- 그래도 재현되지 않고 지시서에 오류 로그가 있으면, 시도 기록을 근거로 **사람에게 로그 근거 전환을 확인받는다** — ca-answer 의 동의 절차, 동작은 `{"action":"repro-log"}`. 확인 화면은 CLI 가 시도 결과와 로그 앞부분으로 만든다. 확인 전에는 고칠 파일을 쓰지 않는다.
- 확인되면 고칠 파일이 열리고, 재현 TC 는 회귀 TC 로 남아 수정 후 통과해야 한다. 반영 기록에 `로그 근거 · 운영 로그로 확인 필요` 가 남는다.
- 지시서에 오류 로그가 없는 결함(`## 오류 로그 없음`)이 재현되지 않으면 고치지 말고 그대로 보고한다 — 근거가 없는 수정은 고쳤는지 알 수 없다.
