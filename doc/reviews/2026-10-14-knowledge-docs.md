# 문서·지식 관리 개선 — 2026-10-14

대상 프로젝트의 기능·업무 정책·업무 흐름을 최신으로 유지하고 다음 작업에서 필요한 맥락을 빠르게 찾도록 KNOWLEDGE 와 그 갱신·검색·최신성 흐름을 고쳤다. 목표는 문서 생성량이 아니라 **바뀐 것만 갱신하고 필요한 줄만 찾는 것**이다. 현재 동작은 [design.md §2.2](../design.md#22-공통-knowledge--비어서-시작하고-반영마다-자란다)·[usage.md](../usage.md)·[process-flow.md](../process-flow.md) 가 정본이고, 이 기록은 판단 경위와 검증 결과다.

## 무엇을 바꿨나 (요구사항별)

1. **기능·흐름** — KNOWLEDGE 에 `features`(기능 목록)·`flows`(업무 흐름)를 더했다. 기능 항목은 목적·진입점·입력·출력·정책 키·흐름 키·예외·코드·테스트·별칭·`상세`(기존 문서 연결), 흐름은 시나리오와 단계별 기능 키. 빈 뼈대로 시작하고 반영마다 닿은 것만 자란다. 인덱스는 문서를 그때 읽어 만든다.
2. **정책** — `business-rules` 항목에 구분(필수·권장)·상태(확정·관찰)·출처·범위·예외·검증. 확정의 출처는 R·Q 만(반영이 거른다), 관찰은 반드시 적용 목록에서 빠진다. 컨벤션은 `[필수]` 줄만 참조 코드보다 앞선다(구현·리뷰 지침). 정책 본문은 `business-rules` 한곳, 04 의 업무 규칙은 기존 BR 키로 근거를 댈 수 있다.
3. **개발 흐름 연결** — 새 작업의 02 에 `## 문서 영향` 표(갱신·신규·삭제·이름 변경·영향 없음·충돌 + 근거). impact 게이트가 표·판단·근거와 영향 범위 파일에 걸린 기존 항목의 판단을 본다. 반영 단계의 `지식 제안:` 줄이 쓸 키를 고르고, 영향이 없으면 제안을 쓰지 않는다. 제안 검사는 구현되지 않은 경로·출처 없는 확정 정책을 거른다. 갱신을 선언하고 적용하지 않으면 `문서 갱신 보류` 와 목록의 `보류`. `- 삭제:`·`- 대체:` 로 삭제·이름 변경·이동. 새 승인 단계는 없다.
4. **맥락 찾기** — context 참고 문서와 `knowledge find` 가 키·코드 경로·별칭·본문으로 항목·절을 골라 줄 범위·최신성·연결을 준다. 반드시 적용하는 업무 정책은 순위와 관계없이 싣는다. 잘리면 수를 적고, 낡은 항목은 원문·코드 확인을 지시한다. 플러그인 요청·응답 형식은 그대로이고 장식은 `code-agent context` 가 붙인다.
5. **최신성** — 항목 줄의 마지막 커밋(`git blame`) 이후 근거 경로를 바꾼 커밋이 있으면 `재검토 필요`. 관련 없는 변경은 어떤 항목도 흔들지 않고, 그 작업의 02 가 `영향 없음` 으로 판단한 변경은 세지 않는다. 승인과는 묶지 않는다.
6. **호환** — 아래 '호환'.

## 결정과 이유

| 결정 | 이유 |
|---|---|
| 인덱스·최신성을 저장하지 않는다 | 저장본은 그 자체가 낡고, 모든 반영이 그것을 고쳐야 하며 병렬 작업이 같은 파일에서 부딪힌다. 문서 다섯 개와 git blame 은 요청 때 계산해도 싸다 |
| 계획 제출에서 문서 영향을 다시 검사하지 않는다 | 처음에는 계획 파일에 걸린 미판단 항목을 계획 제출에서 막았다. 02 는 계획 단계에서 고칠 수 없어 막으면 되감기가 된다 — 반영의 `지식 제안:` 줄이 그 항목을 알리는 것으로 옮겼다 |
| `영향 없음` 판단을 검토로 친다 | 근거 코드를 바꾼 작업이 그 항목을 보고 영향 없다고 적었으면, 그 변경 때문에 다시 재검토 필요로 띄우는 것은 소음이다 |
| `knowledge find` 만 모델에게 연다 | 읽기 전용이라 작업 임대·쓰기 경계를 건드리지 않는다. `knowledge`(목록)·`prune` 은 사람의 자리로 둔다. 교차 검증 자식(`CROSS_CHILD_READONLY`)에는 넣지 않았다 — 교차 리뷰·critic 은 받은 문서와 코드를 읽는 자리다 |
| 플러그인 프로토콜을 바꾸지 않는다 | 등록된 플러그인이 그대로 돈다. 줄 범위·최신성·반드시 적용 정책은 플러그인 결과가 인덱스의 항목·절과 맞을 때 code-agent 가 붙인다 |
| 문서 영향은 새 작업만 | 진행 중인 작업의 02 에 없는 절을 요구하면 그 작업이 멈춘다 |
| 손으로 쓴 `관련 정책:` 도 `정책:` 으로 읽는다 | 실제 CLI 확인에서 `- 관련 정책:` 으로 쓴 기능 항목의 연결이 빠지고 반드시 적용 정책도 붙지 않았다. 필드 이름 앞의 `관련` 을 뗀다 |
| 04 의 BR 키 대조는 낱말 경계로 | 부분 문자열 대조면 `BR-ORDER-1` 이 `BR-ORDER-10` 줄의 근거로 통과한다 |

## 호환

- 매니페스트 `docs.knowledge.features`·`flows` 는 선택이다. 없으면 기본 경로, 파일이 없어도 아무것도 막지 않는다 — 기존 프로젝트는 `docs begin`·`docs skeleton knowledge` 나 첫 반영에서 생긴다.
- 승인·계획 입력 해시는 그대로다 — KNOWLEDGE 는 원래 해시 밖이고, 02 의 새 절은 새 작업에만 생긴다.
- 문서 영향 게이트·`지식 제안:` 줄·⑩ `문서 영향` 표·업무 정책의 구분·상태·출처 필수는 `knowledgeVersion: 1` 작업에만 걸린다. 이전 작업의 제안은 예전처럼 선택이고 R 번호·경로 검사만 받는다.
- 필드가 없는 옛 항목은 본문 전체가 검색 대상이고, 근거 경로가 없으면 최신성 표시 없이 나온다.
- 계획의 충돌 항목(`conflicts`)에 선택 필드 `level`(필수·권장)을 더했다 — 없는 계획도 그대로 통과한다.

## 측정 — 같은 픽스처의 단계별 `code-agent context` 글자 수

`stageFixture` 의 주문 작업(ORD-1)을 기준 빌드(`43c77cf`, 별도 worktree)와 지금 빌드에서 같은 순서로 진행하며 단계마다 `context` 출력 길이를 쟀다. `knowledge` 시나리오는 업무 정책 4개(필수 확정·권장·다른 도메인 필수·관찰)·데이터 2·API 2·기능 1·흐름 1과 컨벤션 `[필수]` 한 줄을 넣었다(기준 빌드는 기능·흐름 문서를 읽지 않는다). 원자료는 [evidence](evidence/2026-10-14-knowledge-docs.json).

| 단계 | 지식 없음 기준 → 지금 | 지식 있음 기준 → 지금 |

| analysis | 1,472 → 1,514 | 2,070 → 2,399 |

## 검증

- 시험: `npm test` 1,450개 중 1,446개 통과·실패 0·생략 4(플랫폼 조건). 새 시험은 `knowledgeDocs.test.ts` 13개(최신성·검색·반드시 적용 정책·제안 삭제·대체·검사·usage 문서 탐색·접수부터 반영까지·hook)와 `planning.test.ts` 의 04 BR 키 근거 1개다. 중간 실행에서 반영 context 의 "제안 없음" 문구에 제안 파일 경로가 빠져 `stage-commands.test.ts` 1개가 실패했고 문구에 경로를 넣었다.
- 실제 CLI(`dist/agent/cli.js`, 임시 저장소):
  - `init --host both` — `ca-integrate/knowledge.md` 가 두 호스트에 같은 내용으로 설치되고, Codex 의 `ca-integrate/SKILL.md` 는 `.agents/skills/ca-integrate/knowledge.md` 를 가리킨다. `ca-docs` 의 `argument-hint` 에 `features | flows`. `docs skeleton features`·`flows`·`knowledge` 출력.
  - 작업 중(check) 판정 — Claude `hook`: Bash `code-agent knowledge find 주문` 허용, `knowledge`·`knowledge prune` 거부, Write `doc/knowledge/features.md` 거부. Codex `codex-event`: Bash·PowerShell `knowledge find` 허용, `knowledge prune` 거부, `apply_patch` 로 `doc/knowledge/features.md` 거부.
  - 반영 단계 — `next`·`status` 가 `지식 제안: \`FEAT-ORDER-REGISTER\`(신규) · 02 에서 판단하지 않은 관련 항목 \`FEAT-ORDER-QUERY\` …` 줄을, `context` 가 같은 범위의 `## 지식 제안` 절을 낸다.
  - `knowledge`·`knowledge find` — 근거 코드를 바꾼 커밋 뒤 `[재검토 필요: <커밋> 가 src/order/cancel.ts 를 바꿈]`, 찾은 기능이 가리키는 필수 확정 정책이 `반드시 적용하는 업무 정책` 에 붙음, 걸린 것이 없으면 찾은 문서와 직접 찾으라는 안내. 이 확인에서 `- 관련 정책:` 필드가 연결로 읽히지 않는 것을 찾아 고쳤다(위 '결정과 이유').
  - `usage` — 공통 문서 Read·`knowledge find` 기록이 `문서 탐색(스테이지별 …): impact 2` 로 나오고 코드 읽기는 세지 않는다.

## 남은 일·한계

- 유료 모델 완주 비교(기준 빌드 대 지금 빌드)를 하지 않았다 — 위 '측정'.
- 검색은 낱말 단위다. 한국어 조사(`주문을`)는 낱말 그대로 걸리므로 별칭과 키로 보완한다. 의미 검색은 `context.docs` 플러그인 자리로 둔다.
- 셸이 없는 담당(조사·리뷰)은 `knowledge find` 를 부를 수 없다 — context 가 준 줄 범위와 지식 문서 검색으로 찾는다.
- 기능·흐름 문서는 반영을 거친 작업만큼만 자란다. 도입 때 전체를 역공학하지 않는 것은 의도다.
