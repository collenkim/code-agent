**질문·동의** — 사람에게 묻거나 승인·확정·반영을 받기 직전에 `.claude/skills/ca-answer/SKILL.md`를 읽고 그 절차(`AskUserQuestion`·같은 세션 동의)를 따른다. 일반 답변은 승인이 아니며, 적용 뒤에는 이 흐름을 자동으로 이어간다.

너는 **메인 에이전트**다. 소스 코드는 읽지 않는다 — 사람이 준 글 · `code-agent` 출력으로 일한다.
`code-agent` 가 거부하면 **사유를 그대로 전하고 멈춘다.** 우회하지 않는다.

요구사항은 사람이 **말로** 준다. 너는 그것을 정리하고, 코드가 지시서(`requirement.md`)를 렌더하고, 사람이 같은 세션의 동의 질문으로 확정한다.
확정된 요구사항만 분석이 받는다 — 정리하다 원문과 뜻이 달라지면 그 자리에서 사람이 잡는다.

**자리 확인** — Bash: `code-agent status`.

- 진행 중인 작업이 있으면 **멈춘다** — 한 번에 하나다. 같은 ID의 요구사항을 고치는 것이면 아래 3~5로 초안을 고쳐 다시 제출하고 새 `request` 공통 동의 절차로 재확정한다.
- 다른 ID 를 접수 중이면 멈추고 그것을 전한다.
- 접수 중 `다음:`이 준비를 가리키면 확정 여부보다 준비를 먼저 처리한다. `/ca-adopt`·`/ca-docs`로 문서를 갖추고 열린 문서 세션은 `docs end`로 닫는다. 원문 초안과 ID는 유지한다.
- 같은 ID 를 접수 중이면 이어서 한다. `요구사항: 반려됨` 이면 아래 **반려됐다면** 으로 간다.
  `확정됨`이면 접수는 끝났다 — 아직 작업 시작 전이면 Bash: `code-agent start doc/work/<ID>/requirement.md`로 시작하고 `analysis`부터 같은 흐름을 이어간다
  (접수 때 받은 `--base` · `--target` 은 접수 세션에 남아 있어 다시 줄 필요가 없다).

## 1. ID 와 종류

- 티켓 ID가 있으면 그대로 쓴다. 없으면 `request begin`에서 ID를 생략하고 출력의 자동 발급 ID를 사용한다. ID를 고르라고 질문하지 않는다.
- **종류**는 `--kind`가 있으면 따른다. 없으면 명확한 요청에서 판단한다: 신규·기능 개선은 feature, 결함 수정은 fix, 동작 보존 구조 개선은 refactor. 판단한 종류를 짧게 알리고 진행한다. 요청이 두 가지로 해석될 때만 쉬운 말로 묻는다.

정리본에는 `sourceMap`으로 원문 인용과 REQ/DONE/CON 항목을 연결한다. 원문을 그대로 옮긴 항목은 자동 연결된다. 바꿔 쓴 문장도 원문을 빠짐없이 연결하고, 제외한 내용은 OUT 항목과 이유를 명시한다. `원문 대조`의 미연결은 에이전트가 원문에 근거해 보완한다. 사용자가 표를 작성하게 하지 않는다. 기존 요구 확정 한 번에 반영·변경·제외를 함께 보여준다.

Bash: `code-agent request begin [ID] --kind <종류>` — 접수를 열고 초안 형식 · 규칙 · 대상 후보를 찍는다 (다시 보려면 `code-agent request`).
사용자가 기준 브랜치나 대상을 말했으면 `--base <기준 브랜치>` · `--target <대상>` 을 함께 넘긴다 — 사람의 확정을 사이에 두고 끊긴 뒤에도 `start` 가 그 값을 쓴다.

## 2. 원문

사람이 준 것을 **한 글자도 바꾸지 않고** 보관한다 — 요약 · 교정 · 번역하지 않는다.
- 글(서술 · 붙여넣은 티켓)이면 초안의 `original` 에 그대로.
- 파일 경로면 `originalFile` 에 그 경로 — 코드가 파일을 그대로 옮긴다. 저장소 밖 파일이면 사람에게 저장소 안에 두라고 묻는다.

**프로젝트 준비를 먼저 연결한다.** 먼저 `request.json`에 ID·종류·원문을 저장한다(필수값이 아직 없는 초안도 저장은 가능).
status의 `다음:`이 준비를 안내하면 `/ca-adopt` 또는 `/ca-docs`를 같은 흐름에서 따른다. `docs begin`은 접수와 원문을 유지한다.
최초 준비는 `setup` 공통 동의 절차로 POLICY 전체 확정과 필요한 준비 커밋(최초 커밋 또는 기존 저장소의 도입 파일 반영)을 한 질문으로 확인받는다. 적용 성공 후 저장된 초안에서 자동으로 이어간다. 분석은 준비·요구 확정 뒤에 시작한다.

## 3. 정리 — `doc/work/<ID>/request.json`

`code-agent request` 의 형식대로 쓴다 (이미 시작한 작업의 요구사항을 고칠 때도 같은 명령이다). 원문에 **근거가 있는 것만** 옮긴다.
- `title` — 사람이 목록에서 알아볼 한 줄.
- `target` — feature 는 만들 도메인·기능의 **이름**(대상 후보 줄의 앞쪽 이름 — 경로가 아니다), fix · refactor 는 고칠 코드가 있는 **저장소 경로**. 대상 후보에서 고른다.
- `scope` · `preserve` — fix · refactor 는 필수. preserve 는 바뀌면 안 되는 것(공개 시그니처 · 테이블 스키마 · 동작)을 사람의 말로.
- **fix 의 오류 로그** — fix 는 오류 로그로 고친다. 셋 중 정확히 하나: 사람이 준 로그 글은 `errorLog` 에 **그대로**(줄이거나 고치지 않는다), 로그 파일이면 `errorLogFile` 에 저장소 안 경로(코드가 그대로 옮긴다), 로그가 없는 신고(화면 증상만)는 `noErrorLog: {"reason": "<없는 사유>", "steps": ["<재현 절차>", …]}`. 원문에 로그가 섞여 있으면 그 구간을 `errorLog` 로도 옮긴다. 로그도 사유도 없으면 사람에게 로그를 달라고 묻는다. 비밀번호·토큰·개인정보가 보이면 가린 로그를 다시 받는다.
- `requirements` — 요구 한 가지씩. **원문에 없는 요구를 더하지 않는다** — 있으면 좋겠다 싶은 것은 질문으로.
  CLI가 각 항목을 REQ-1부터, 완료 조건을 DONE-1부터, 제약을 CON-1부터 표시한다. 확정된 이 목록이 이후 추적의 기준이다.
  원문과 이 목록을 대조해 빠뜨린 요구가 없는지 확인한다. 원문 그대로 보관하는 것만으로 정리의 완전성이 증명되지는 않는다.
- `done` — 원문이 말한 완료 조건. 없으면 비운다 (분석 단계의 수락 기준이 정한다).
- `background` · `outOfScope` · `constraints` — 원문에 있을 때만.
- `approver` · `extra` — 프로젝트가 선언한 것만 (context 가 찍는다).

## 4. 질문

기존 구성과 대상 후보로 정할 수 있는 기술값은 근거를 붙여 추천하고 확인 화면에 포함한다. 원문만으로 정할 수 없는 **의미·범위 결정**과 원문이 두 가지로 읽히는 곳만 묻는다.
- 질문·전체 후보·추천 이유를 작업 폴더의 `questions.md`에 먼저 기록하고 `AskUserQuestion`으로 받는다. 최대 4개 질문, 화면당 2~4개 옵션이며 5개 이상 후보는 공통 절차대로 나눈다. 질문 하나에 결정 하나.
- 답을 받으면 초안에 반영하고, 물은 것과 답을 `clarifications` 에 **사람의 말 그대로** 남긴다.
  답으로 확정된 요구·완료 조건·제약도 해당 목록에 반영해 분석 추적의 기준에 포함한다.
- 업무 규칙의 세부 · 설계 · 테스트 방법은 여기서 묻지 않는다 — 분석 단계가 맡는다.

## 5. 제출

Bash: `code-agent request submit doc/work/<ID>/request.json`
- 거부되면 사유대로 초안을 고쳐 다시 낸다. 원문으로 정할 수 없는 값 때문이면 4 로 묻는다.
- 통과하면 코드가 `doc/work/<ID>/requirement.md` 를 렌더한다 — **손대지 않는다** (hook 이 거부한다).
- 렌더됐어도 `원문 대조에 미연결` 안내가 있으면 원문에 근거해 sourceMap을 보완하고 다시 제출한다. 연결이 끝나기 전에 사용자에게 확정을 요청하거나 다음 턴을 기다리지 않는다.

## 끝

`{"action":"request","id":"<ID>"}`으로 공통 동의 절차를 수행한다. `summary` 전문과 원문·정리본 링크를 보여 주고 CLI가 반환한 `toolInput` 전체를 그대로 호출해 실제 응답을 받는다. `approved`인 동의를 적용한 뒤 현재 상태를 확인하고, 시작 전이면 `code-agent start doc/work/<ID>/requirement.md`로 분석부터 개발 흐름을 자동으로 이어간다. 진행 중인 작업의 재확정이면 현재 상태가 요구하는 재계획·재승인으로 이어간다.
수정 요청이면 이전 동의를 적용하지 않고 초안을 고쳐 재제출·새 동의를 준비한다. 사용자가 명시적으로 반려 기록을 요청하면 `decision: "reject"`와 실제 사유인 `comment`를 넣은 `request` 동작을 별도 공통 동의 절차로 처리한다. 같은 내용을 그대로 다시 내면 `request submit`이 거부한다.

## 반려됐다면

1. `code-agent status` 의 `요구사항: 반려됨 — <사유>` 를 읽는다.
2. 사유가 가리키는 곳(원문과 다른 정리 · 빠진 요구 · 대상 · 범위 · 보존)을 초안에서 고친다. 원문은 그대로 둔다.
3. 사유만으로 정할 수 없으면 공통 선택 절차로 질문하고, 필요한 답이 없을 때만 멈춘다.
4. 5로 다시 제출하고 새 `request` 공통 동의 절차로 확정받는다. **사유를 읽지 않고 같은 초안을 다시 내지 않는다.**
