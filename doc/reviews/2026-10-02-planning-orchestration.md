# 요구 분석·설계·계획의 서브 에이전트 실행 구조 보완

변경일: 2026-10-02. [문서·검증 이력](README.md) · [계획 작업 안내](../planning.md).

## 검토와 적용 결과

요구 분석·구체화·계획 단계에서 담당, 입력, 완료 근거와 재실행 조건이 불명확했던 부분을 보완했다. 신규 작업은 관찰된 실행 결과로 진행하며 이전 작업은 기존 형식으로 재개한다.

| 검토에서 확인한 문제 | 적용 내용 | 구현 근거 |
|---|---|---|
| 보류·상태 메모를 답으로 인정 | 명시 보류와 상태 설명은 미응답, 중복 질문 차단, 관련 요구 연결 | questions.ts |
| 가짜 경로·미결 설계·내용 없는 AC·근거 없는 BR 통과 | 필수 작업 문서의 미결 표시·실제 파일과 줄·AC 내용·BR 근거 검사 | planningValidation.ts |
| critic이 절차 안내에만 존재 | 실제 시작·완료 관찰, 입력·배정·세션 대조, 차단 지적이 없을 때만 제출·승인 | planningHook.ts, commands.ts |
| 작성 담당에게 설계 판단까지 요구 | ca-analyst가 설계·기능 정의·계획 판단, ca-writer가 영향도 정리 | 에이전트·단계 스킬 템플릿 |
| 서브 작업의 결과·재시도·합류 계약 부재 | 작업 ID·입출력·선행 조건·완료 상태·근거·질문·문서·지적 계약 | planning.ts, planningState.ts |
| KNOWLEDGE 키 존재로 조사 생략 | 키는 조사 단서, 현재 코드 확인. 같은 작업·입력 해시의 완료 결과만 재사용 | planningState.ts, 탐색 지침 |
| 구현 Task가 단계와 일대일 | 같은 단계의 여러 Task, 파일 단일 소유·의존성·AC 연결과 실행 커서 | core/plan.ts, commands.ts, hook.ts |
| 전역 문맥 반복 전달 | 영역별 입력 파일과 선행 결과를 배정. 조사 기본 3개·최대 4개 동시 실행 | planning dispatch, 영향도 스킬 |

`planning prepare`는 DAG와 출력 소유를 검사한다. `dispatch`는 선행 결과·관련 미결 질문·동시 실행 한도·동일 입력 최대 3회 제한을 확인하고 배정 계약을 반환한다. 상태는 작업별 planning.json에 저장한다. 잠금 안에서 완료 결과를 합쳐 병렬 기록의 덮어쓰기를 방지한다.

관찰되지 않은 결과, 취소한 배정의 늦은 결과, 중복 완료, 입력 변경 뒤 결과, 범위 밖 근거와 출력은 완료 근거로 받아들이지 않는다. 조사 결과의 동일 사실 키가 상충하면 합성을 막는다. 파일 추가·삭제·내용과 관련 질문 변경은 해당 결과와 후속 결과를 다시 확인하게 한다.

독립 검토한 초안과 실제 제출본도 대조한다. 새 초안을 검토했더라도 이전 제출본을 승인할 수 없다. 승인 해시는 작업 정의와 관찰 결과를 포함하며, 승인 후 정상 구현은 조사 당시 소스가 변경됐다는 이유만으로 무효화하지 않는다.

## 검증 기록

기능 커밋: `53c0ad6`.

전체 회귀 679개 중 675개 통과·실패 0·생략 4개 (454.8초, `dist/planning-final-regression.log`). 후속 계획·승인·반영 검사 29개와 질문·선택 검사 11개 모두 통과. 근거는 [구조화된 검증 기록](evidence/planning-orchestration-2026-10-02.json)에 있다.

전체 회귀 후 질문 본문 변경·여러 줄 보류 응답·프로젝트 설정과 계획 형식 전달을 보완했다. 실제 세 프로세스에서 동시에 도착하는 조사 완료 보존 검사 1개도 추가했다. 최종 고유 범위는 680개 중 676개 통과·실패 0·생략 4개다. 이는 전체 회귀에 추가 1개를 합친 범위이며 후속 중복 검사는 더하지 않았다.

최종 빌드·타입 검사·`git diff --check`를 통과했고 README와 doc의 Markdown 15개에서 상대 파일 링크 누락 0개를 확인했다.

- 초기 전체 회귀: 673개, 통과 664·실패 5·생략 4 (`dist/planning-full-regression.log`). 동의·반영 준비 4건은 번호 문서를 직접 쓰던 fixture라 신규 관찰 게이트에 막혔다. 실제 배정과 시작·완료 이벤트로 문서를 생성하도록 수정했다. 기존 sequence 기반 통합 1건은 이전 작업 호환 fixture로 명시했다.
- 보완 후 집중 검사: 28개 모두 통과 (`dist/planning-final-focused.log`). 신규 계획 검사 18개, 원문·기존 작업 흐름 6개, 신규 관찰 흐름을 거친 같은 세션 승인·반영 4개다.
- 초기 신규 검사 12개 중 2건은 취소한 뒤 시작 이벤트를 보내던 준비 방식과 scaffold 주석의 `[Answer]`를 먼저 치환하던 테스트 오류였다. 실제 시작 후 취소와 답변 필드 줄 치환으로 수정했고 후속 검사에서 통과했다.

검증 대상은 신규 시작의 관찰 필수화, 문서 쓰기 경계, 전체 계획→승인→Task 실행, critic 누락·차단 지적, 검토와 제출본 불일치, 입력·문서 변경, 영역별 합류·상충·재사용, 질문 영향 범위, 배정 한도, 취소·중복 결과, 가짜 근거·문서, DAG·파일 소유, 설치 hook 중복 방지, 같은 세션 승인과 반영이다.

## 검증의 한계

임시 Git 저장소에서 실제 CLI 함수·파일·게이트·명령을 실행했다. 에이전트와 사용자 응답은 테스트가 합성한 런타임 이벤트이며 실제 모델 대화나 실제 사람의 조작 측정은 아니다. 기존 모델 완주 결과를 이번 변경의 모델 완주 결과로 재사용하지 않는다.

실제 토큰·시간 절감량, 큰 저장소의 비용, 자연어 충돌과 설계 판단의 품질은 별도 실측 대상이다. 프로그램은 문서 형식·근거 위치·결과 연결을 검사하며 의미의 정확성을 증명하지 않는다. 여러 메인 세션이 동시에 단계 커서를 변경하는 운영과 프로세스 강제 종료 시 잠금 복구는 자동 테스트로 보장하지 않는다. CLI는 모델 API를 직접 호출하지 않으며 사람의 승인을 생성하지 않는다.
