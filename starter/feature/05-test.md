# [feature 05] 테스트 코드

> **선행**: [01]~[04] · **다음**: [06] 빌드·테스트 통과시키기
> **근거**: 참조 표준 도메인의 테스트 (`base` 가 테스트 루트다 — 같은 패키지 구조를 다른 루트에 미러링한다)

## 0. 사용법

참조 표준의 테스트가 **무엇을 어떤 수준에서 검증하는지**를 이 도메인에 옮긴다. 테스트의 종류(단위·통합)와
픽스처 방식·명명은 참조 표준을 따른다. 스펙의 제약과 상태 전이가 검증 항목의 원천이다.

**do-not-touch**: 본문 소스를 고치지 않는다. 테스트가 통과하지 않는 것을 발견해도 이 단계에서 고치지 않는다 — 그것은 [06] 의 일이고, 여기서는 `note` 로 남긴다.

## 1. 입력 게이트

- [ ] [01]~[04] 산출물이 실려 있다
- [ ] 스펙의 제약·상태 전이·에러 목록이 있다 — 검증 항목은 여기서만 나온다
- [ ] 참조 표준 테스트가 실려 있다

## 2. 규칙 게이트

| 규칙 | 근거 | 위반 시 |
|---|---|---|
| 테스트 종류·기반 클래스·픽스처 방식은 참조 표준과 같다 | 참조 표준 테스트 | 무효 |
| 파일·클래스·메서드 명명은 참조 표준의 규칙을 따른다 (`Tests` 인지 `Test` 인지 참조 표준이 정한다) | 참조 표준 | 무효 |
| 스펙의 제약 하나 = 검증 하나 이상. 제약 없는 검증을 만들지 않는다 | 스펙 | 무효 |
| 상태 전이가 있으면 **허용되지 않는 전이**도 검증한다 | 스펙 | 무효 |
| 본문 소스를 고치지 않는다 | 경계 | 무효 |

## 3. 작업 — 스켈레톤

1. 참조 표준 테스트 하나를 골라 골격(기반 클래스·어노테이션·픽스처 준비)을 가져온다
2. 스펙의 제약을 표로 만들고, 제약마다 검증 메서드 하나를 참조 표준의 메서드 모양으로 쓴다
3. 상태 전이가 있으면 허용 전이와 금지 전이를 각각 검증한다
4. 참조 표준에 없는 검증 방식(외부 시스템 모킹 등)이 필요하면 만들지 말고 `ask`

## 4. 자가검증 체크리스트

- [ ] 만든 파일이 계획의 목록과 같은가, 그리고 전부 테스트 루트(`base`) 아래인가
- [ ] 스펙의 모든 제약이 검증 하나 이상으로 대응되는가
- [ ] 명명·기반 클래스가 참조 표준과 같은가
- [ ] 본문 소스를 한 줄도 고치지 않았는가

## 5. 산출물 → 다음 단계 입력

- **산출물**: 테스트
- **[06] 입력**: 없음 — [06] 은 이것을 **돌린다**
