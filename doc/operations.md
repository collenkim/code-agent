# 운영 — 코드가 보장하지 않는 것

> 개념과 설계는 [README](../README.md), 지시서 규격은 [work-order.md](work-order.md),
> 요청 보내는 법은 [usage.md](usage.md). 이 문서는 **코드가 막을 수 없어 사람이 정해야 하는 것**을 다룬다.

이 도구는 곳곳에서 같은 말을 한다 — "보장하는 것은 여기까지이고, 증명은 다른 데 있다."
그 *다른 데* 를 한자리에 모은 것이 이 문서다. 여기 적힌 것을 하지 않으면 게이트는 남지만
게이트가 뜻하는 것은 사라진다.

## 무엇을 코드가 보장하나

| | 코드가 보장한다 | 사람이 해야 한다 |
|---|---|---|
| **승인** | 승인 없이는 진행되지 않는다. 지시서·계획·경계가 바뀌면 자동 무효 | 승인한 사람이 **실제로 읽었는지** |
| **신원** | 인증을 켜면 누구의 요청인지 원장에 남는다 | 그 계정이 그 사람인지 — 프록시의 인증 강도가 정한다 |
| **원장** | append only. 나중에 고치면 사슬이 끊겨 읽기를 거부한다 | **커밋하는 것.** 커밋되지 않은 원장은 아무것도 증명하지 않는다 |
| **경계** | 승인한 계획·경계 밖의 파일은 쓰기 전에 거부된다 | 경계를 무엇으로 잡을지 (`outputDirs`·`scope`·`--root`) |
| **전송** | 요청이 어느 자리의 것인지, 다른 사이트가 보낸 것인지 | **TLS.** 이 서버는 평문 HTTP 만 말한다 |
| **격리** | 작업마다 out/ 이 갈리고, 남의 작업은 404 | 사람마다 계정이 갈리는 것 — 프록시가 정한다 |

읽는 법은 하나다. **왼쪽은 우회할 수 없고, 오른쪽은 규율이 무너지면 같이 무너진다.**

## 배치 — 앞단에 프록시를 둔다

`code-agent serve` 는 인증도 TLS 도 하지 않는다. 일부러다 — 사내 인증 체계는 회사마다 다르고,
그것을 이 도구가 흉내 내면 어느 쪽에도 맞지 않는다. 이 서버가 요구하는 것은 하나다.

> **앞단이 인증하고, 그 주체를 헤더 하나로 넘겨 준다.**

```
사람 ──TLS──▶ 프록시(인증) ──평문, 루프백──▶ code-agent serve
                   │
                   └─ X-Auth-User: kai@crm.co.kr  를 덮어쓴다
```

### 프록시가 반드시 하는 두 가지

**① 헤더를 덮어쓴다.** 더하는 것이 아니라 덮어써야 한다. 클라이언트가 스스로 적어 보낸
`X-Auth-User` 가 그대로 지나가면 인증이 아니라 자기 신고가 된다.

**② code-agent 를 루프백에만 묶는다.** 프록시를 우회해 서버 포트에 직접 닿을 수 있으면
①이 무의미하다.

```nginx
server {
  listen 443 ssl;
  server_name code-agent.corp.example;

  ssl_certificate     /etc/ssl/corp.crt;
  ssl_certificate_key /etc/ssl/corp.key;

  # 사내 SSO 가 끝난 뒤의 주체. auth_request·OIDC·mTLS 무엇이든 여기서 값이 나오면 된다.
  auth_request /_auth;
  auth_request_set $user $upstream_http_x_forwarded_user;

  location / {
    proxy_pass http://127.0.0.1:4319;

    # 덮어쓴다. 클라이언트가 보낸 같은 이름의 헤더는 여기서 사라진다.
    proxy_set_header X-Auth-User $user;

    # Host 는 그대로 넘긴다 — 루프백 바인딩일 때 서버가 이것을 본다.
    proxy_set_header Host $host;

    # 검증 명령이 몇 분씩 걸려도 202 로 갈리므로 긴 타임아웃은 필요 없다.
    proxy_read_timeout 60s;
  }
}
```

```bash
code-agent serve \
  --host 127.0.0.1 --port 4319 \
  --auth-header X-Auth-User --trust-proxy \
  --root /srv/repos --root /srv/specs \
  --state /var/lib/code-agent/jobs.json
```

`--trust-proxy` 는 위 ①·②를 **당신이 했다고 선언하는 자리**다. 붙이지 않으면 서버가 뜨지 않는다.

### `--root` 를 무엇으로 잡나

작업이 가리킬 수 있는 경로의 뿌리다. 없으면 요청 본문의 절대경로 하나로 이 프로세스가 닿는
모든 곳이 사정권에 든다.

| 두는 것 | 왜 |
|---|---|
| 대상 저장소들이 있는 디렉토리 | `repo`·`templates` 가 그 아래여야 한다 |
| 스펙 문서 디렉토리 | `specs` 가 그 아래여야 한다 |
| out/ 을 둘 디렉토리 | 작업마다 갈리되 한 뿌리 아래 |

**서버 프로세스의 계정 권한도 같이 좁힌다.** `--root` 는 이 도구가 거절하는 경계이고,
그 밖을 읽고 쓸 수 있는지는 OS 가 정한다. 둘 다 좁혀야 경계가 하나가 된다.

### 검증 명령은 이 머신에서 돈다

`### run build` 는 대상 저장소의 임시 worktree 에서 **서버 머신의 셸로** 실행된다.
그러므로 이 서버가 있는 머신은 **빌드 머신과 같은 신뢰 수준**이어야 한다.
빌드 도구(gradle·npm·pip)가 깔려 있어야 하고, 그것들이 받는 의존성도 이 머신에서 내려온다.

## 승인이 증거가 되려면

### ① 원장을 커밋한다

승인 기록은 **대상 저장소 안**에 남는다.

```
<대상 저장소>/.code-agent/approvals/
  PROJ-1421.jsonl                      판정 한 줄 = 사건 하나 (append only)
  PROJ-1421/
    app-settlement-1.plan.json         그때 승인한 계획 전문
    app-settlement-entity-1.files.json 그때 확정한 파일 목록
```

**이것을 `.gitignore` 에 넣지 않는다.** 커밋되지 않은 원장은 그 머신의 파일일 뿐이고,
파일은 아무것도 증명하지 않는다. 사슬(`prev`)이 지키는 것은 *나중에 고친 것이 드러나는 것*
까지이며, 고쳐지지 않았다는 증거는 git 히스토리에 있다.

| 하는 일 | 왜 |
|---|---|
| 작업이 끝나면 `.code-agent/approvals/` 를 커밋한다 | 증거가 되는 순간이 여기다 |
| 생성물 커밋과 **같은 PR** 에 넣는다 | 무엇을 승인하고 무엇을 만들었는지가 한자리에서 읽힌다 |
| 원장만 되돌리는 커밋을 만들지 않는다 | 사슬이 끊겨 다음 판정이 거부된다 |

사슬이 끊기면 코드는 **읽기를 거부하고 멈춘다.** 추측으로 잇지 않는다 — git 으로 복원하는 것이
사람의 일이다.

### ② 신원은 원장이 증명하지 않는다

인증을 켜면 원장의 `approver` 는 프록시가 말한 주체가 되고, 본문에 적어 보낸 이름은 무시된다.
그래도 원장이 증명하는 것은 **"그 계정으로 요청이 들어왔다"** 까지다.

```
presence: { channel: "server", verified: false,
            detail: "HTTP 요청 — 인증 주체 kai@crm.co.kr. 그 사람이 실제로 읽고 판단했는지는 관측할 수 없습니다" }
```

`verified: false` 는 고장이 아니라 사실이다. 서버는 버튼을 누른 손이 그 사람의 것인지,
그 사람이 계획을 읽었는지 알 수 없다. **읽었다는 증명은 커밋 서명·PR 리뷰·티켓에 있다.**

| 이 도구가 주는 것 | 그것만으로 부족한 것 | 어디서 채우나 |
|---|---|---|
| 승인 없이는 진행되지 않았다 | 승인한 사람이 읽었다 | PR 리뷰 승인 |
| 그 계정으로 들어왔다 | 그 사람이 맞다 | 커밋 서명 · 프록시의 인증 강도 |
| 무엇을 승인했는지 (스냅샷) | 왜 승인했는지 | 티켓 · `comment` |

### ③ `requireVerifiedApproval` 을 켤 것인가

`code-agent.json` 의 선언이고, **기본값은 꺼짐**이다.

| | 끈 채로 | 켰을 때 |
|---|---|---|
| 서버 화면 승인 | 된다 | **안 된다** — 기록으로만 남는다 |
| 터미널 `approve` | 된다 | 된다 (확인 문구를 입력해야) |
| 비대화형 셸·스크립트 | 된다 | 안 된다 |
| 무엇이 보장되나 | 승인이 있었다 | 승인할 때 **사람이 그 자리에 있었다** |

켜면 막히는 것은 모델이 셸로 `approve` 를 부르는 길이다. TTY 가 없으면 그 문이 닫힌다.
**같은 이유로 서버 경로도 함께 닫힌다** — 인증을 붙여도 그렇다. 신원을 아는 것과
사람이 그 자리에 있었는지는 다른 문제이기 때문이다.

> **정하는 기준.** 승인이 규제·감사 대상이면 켜고, 화면으로 도는 팀의 속도가 더 중요하면 끈다.
> 켜기로 했다면 **승인만 터미널에서** 하고 나머지 왕복은 화면으로 도는 방식이 현실적이다.

## 지시서 `id` 작명

원장 파일은 지시서 `id` 하나에 하나다 — `<대상 저장소>/.code-agent/approvals/<id>.jsonl`.
그래서 `id` 는 파일 이름이자 네임스페이스다.

**규칙: 티켓 번호를 그대로 쓴다. 티켓 하나에 지시서 하나.**

같은 저장소에서 서로 다른 지시서가 같은 `id` 를 쓰면, 판정 줄이 한 파일에 섞이고
같은 대상을 다루는 경우 **둘이 서로의 승인을 계속 무효화한다.** A 를 승인하면 B 가
`stale-order` 로 막히고, B 를 승인하면 A 가 막힌다 — 원장은 늘 마지막 판정만 유효하기 때문이다.

반대로, **같은 지시서·같은 계획·같은 경계라면 승인이 이어지는 것은 설계다.** 승인은
"이 작업"이 아니라 "이 계획, 이 지시서, 이 경계"에 대한 것이므로, 같은 것을 다시 승인받게
하지 않는다. 셋 중 하나라도 다르면 그 순간 무효가 된다.

| 상황 | 어떻게 되나 |
|---|---|
| 같은 지시서를 out/ 만 새로 잡아 다시 돈다 | 계획이 같으면 승인이 이어진다 (설계) |
| 계획을 다시 받았는데 내용이 달라졌다 | `stale-plan` — 달라진 항목만 보여 주고 재승인 |
| `code-agent.json` 의 경계를 고쳤다 | `stale-manifest` — 재승인 |
| `preserve` 한 줄을 지웠다 | `stale-order` — 0차부터 다시 |
| 다른 지시서가 같은 `id` 를 썼다 | 서로 무효화한다. **이것만 사고다** |

## 배치 전 점검

각 줄은 확인하는 방법까지 적었다. 확인되지 않으면 통과한 것이 아니다.

| | 확인 |
|---|---|
| 프록시 없이 서버 포트에 닿지 않는다 | 다른 호스트에서 `curl http://<서버>:4319/` → 연결 거부 |
| 인증 헤더 없이는 아무것도 안 된다 | `curl https://<도메인>/api/jobs` (쿠키 없이) → 401 |
| 클라이언트가 보낸 인증 헤더가 무시된다 | `curl -H 'X-Auth-User: someone-else' …` → 내 계정으로 기록되거나 401 |
| 남의 작업이 안 보인다 | 다른 계정으로 `GET /api/jobs` → 내 것만 |
| 뿌리 밖 경로가 거부된다 | `--root` 밖을 `out` 으로 주고 작업 생성 → 400 |
| 원장이 커밋된다 | 대상 저장소에서 `git log -- .code-agent/approvals/` → 기록이 있다 |
| `.gitignore` 가 원장을 막지 않는다 | `git check-ignore -v .code-agent/approvals/` → 아무것도 안 나옴 |
| 빌드 도구가 깔려 있다 | 검증 단계에서 `### run build` → `통과` 또는 `실패` (`실행 오류` 가 아님) |
| 종료가 기다린다 | `SIGTERM` → "새 요청을 받지 않습니다" 후 종료 |

> **마지막 한 줄.** 위를 전부 통과해도 이 도구가 보장하는 것은 "승인 없이는 진행되지 않는다"
> 까지다. 그 승인이 **읽고 내린 판단**이 되게 하는 것은 코드가 할 수 있는 일이 아니다.
