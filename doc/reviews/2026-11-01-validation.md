## 자동 시험

`npm test`(`tsc` → 옛 `dist/test` 산출물 정리 → `node --test --test-concurrency=4`)로 전체 시험을 한 번 실행했다. 1913건 중 1909 통과·4 생략(플랫폼 조건)·0 실패이고 벽시계는 474초(시험 실행 473.4초)다. 가장 긴 묶음은 `npm 패키지 진입점` 57.6초다.

- `planningBudgetEpoch`는 계획 배정 예산 구간을 고정한다. 같은 구간에서는 정상 완료까지 세어 6회에서 막는다. 확정한 요구 항목이 바뀌거나 새 실행 회차를 열면 새 구간이라 과거 성공 때문에 허용을 묻지 않는다 — 같은 ID 에서 구간마다 6회를 다 쓰는 정상 개정을 세 번 거듭해도 사람 허용 없이 진행하고, 지난 구간의 배정은 `earlier`(6·13·20)로만 보인다. 준비 반복·작업 정의·입력 변경·확정하지 않은 지시서 변경은 구간을 바꾸지 않는다(확정하지 않은 변경은 준비·배정도 멈춘다). 막힌 조사 작업을 새 ID 로 다시 준비하면 새 작업은 배정되지만 종합은 막힌 작업의 완료를 기다리고, 선행에서 막힌 작업을 뺄 수 없다. 같은 입력의 실패는 구간과 무관하게 3회에서 막는다. 구간 기록이 없는 기록은 이행 시각부터 지금 구간으로 이어받아 같은 사용량을 보인다. 그 기록을 새 실행 회차에서 처음 이어받으면 이전 회차 반영 커밋 시각부터 센다 — 이전 회차 배정 6건은 `earlier`로만 보이고(0/6), 그 회차의 사람 허용은 쓰지 않으며, 이전 회차 정의(`REQ-1`·`CON-1`)의 분석 작업은 지금 요구(`REQ-1`·`REQ-2`)로 맞춘다. 같은 회차에서는 마지막 배정이 읽은 지시서가 지금과 다를 때만 맞춘다. 두 시험은 80a0ea0 빌드에서 실패한다(사용량 6/9·범위 `REQ-1`·`CON-1` 유지).
- `answers`는 새 실행 회차에서 이전 회차 반영 커밋과 질문 원문·답·출처 줄이 같은 답을 `delivered`(이전 회차 반영본)로 이어받는 것을 본다 — 질문 본문 결속(`documentHash`) 전 형식의 관찰 행만 있는 답도 다시 묻지 않고, 회차 밖에서는 그 형식을 인정하지 않으며, 반영 뒤 고친 질문·답은 출처 미확인이다.
- `wakeHook`·`agentContinuation`은 담당 완료 뒤 끝나는 턴의 1회 이어가기와 처리하지 않은 완료가 남은 채 쉬는 메인의 1회 깨우기를 본다. 같은 완료의 재알림·동시 hook·재시작·이전 개정의 늦은 완료에서도 효과는 한 번이고, 사람 판단 자리에서는 멈춘다.
- `reproScenarios`의 `completionStall`은 격리 가짜 호스트에서 완료 뒤 사람 입력 없이 다음 행동까지 20초(`CONTINUATION_BOUND_MS`) 안에 이어지는 것을 고정한다. 이 상한은 자식 프로세스 기동을 포함한 시험 환경의 값이며 실제 호스트 지연의 기준이 아니다.
- `testRepair`는 테스트 수정 창을 실제 check·test·integrate·hook 으로 본다. test 단계의 null 원인 단언(Q58 TC-127 유형)과 통합 worktree 에서만 실패한 빈 디렉터리 단언(Q62 유형, 작업 트리 통과·통합 실패)을 계획 되감기·재승인 없이 고친다 — 창의 파일은 지정 테스트 담당만 쓰고(메인·구현 담당 거부), 다음 check 가 창을 받아들여 동결 기준을 갱신하며, 다음 리뷰 회차 context 에 창의 원인·근거·단언 수 변화가 실린다. 건너뛰기 표지(`@Disabled`)를 더한 수정은 거부하고 창을 열어 둔다. 동결 전·⑦ 에 없는 TC·통과한 TC·잘못된 원인은 열지 않고, 고친 것 없는 창은 새 창이 대신한다.
- `changeImpact`는 요구 개정의 영향을 본다. 수정한 항목은 출처 R → Task·AC → TC → 파일로 좁히고, 권한·JWT 글은 보안 영향(`권한`·`JWT·토큰`), 응답 형식·컬럼 글은 `데이터 계약`이다. 새 항목·추적되지 않는 ID·범위 밖·대상 머리말 변경·01 이나 계획이 없음·개정 기록 없음은 전체로 본다. 보안 영향이 있으면 계획·트리가 그대로여도 check·test 를 같은 회차로 다시 돌리고(회차를 쓰지 않음), 같은 트리의 요구 변경 회차로 리뷰를 다시 열며(리뷰 회차 한도에 세지 않음), 통합 검증도 다시 돈다. 파일·보안·전체 어디에도 닿지 않는 영향은 다시 요구하지 않는다.
- `planningReturns`는 계획 담당 결과의 반려를 본다. 결과 줄은 경로 뒤 설명·백틱·따옴표·저장소 안 절대 경로를 받고, 다른 배정·staging 밖·저장소 밖·되짚는 경로는 바른 `resultFile`을 알리며 되돌린다. 저장소 안 절대 경로 근거는 상대 경로로 기록하고 저장소 밖·범위 밖 근거는 한 결과에서 함께 거부한다. 형식 오류·출력 집합 오류는 staging 문서 문제와 한 반려에 싣고, 문서 문제가 있는 형식 오류는 교정 대신 두 사유로 실패를 남긴다(문서가 통과하면 교정 그대로). `DOC-REF`는 파일 이름만 쓴 근거를 막고 전체 경로를 통과시키며, 요구 원문을 그대로 인용한 `호스트:포트`·`파일:줄`은 `REQ-TRACE`와 함께 지나되 원문에 없는 인용·인용 밖 참조·인용 안 참조를 근거로 쓴 업무 규칙은 막는다. 고친 계획의 critic 재검토는 직전 차단 지적·바뀐 입력을 받고 advisory 는 받지 않는다. 되돌림 뒤 재개한 담당의 시작은 새 담당이 아니다.
- `requestRevisionFlow`는 확정한 개정(JWT 권한 수정)을 흐름이 따를 때 영향이 커서와 `status --json` 에 남는 것을, `answers`는 변경 분류가 있는 질문이 분류를 보인 응답만 관찰된 답으로 인정하고 계획 작업 입력·승인 묶음에서 분류만큼만 빠지는 것을 본다.
- `contractAdoption`은 JWT·JWKS 계약 문서 모양의 제공 저장소로 외부 계약 채택을 본다. 범위 밖 절·줄바꿈(CRLF)만 바뀐 계약을 다시 등록하면 낡은 작업 0, 승인 해시·영향 기록 그대로다. R1 에 연결된 헤더 항목이 바뀌면 explore-r1·synthesis 만 낡고(같은 접수 항목에서 나온 R2 의 조사·analysis 는 그대로) 낡은 이유에 항목 키가 보인다. JWT claim 항목(`tenant_id` → `workspace_id`)을 채택하면 explore·synthesis·design·plan·critic 이 낡고, 승인 해시가 바뀌며, 영향(`외부 인증 계약`, Task T1~T3·계획 파일 3개)이 검증 게이트의 `impactAfter`로 이어진다. 보안 항목은 요구가 겹치지 않아도 design·plan·critic 이 기대고 조사는 기대지 않는다. 채택 전 제공 저장소의 작업 트리 편집(범위 안)·새 커밋은 `drift`(worktree·head)로만 알리고 아무것도 낡게 하지 않는다. `pending` 항목은 `contracts.waits`·대기 안내로 보이고 두 조사 작업이 모두 배정된다.
- `dependencyContracts`는 등록·검증 경계를 본다. 같은 판정 구간의 Git 검사 메모(검증마다 3회), 제공 저장소 작업 트리 변경에 영향받지 않는 검증, 사본 변조(범위 원문·항목 줄)의 미확인, 범위 밖 글·줄바꿈만 바뀐 재등록 뒤 재인용 유지와 항목이 바뀐 재등록 뒤 미확인, 잘못된 등록(해시·커밋·경로·항목 줄·상충·크기·없는 섹션·모르는 종류·요구 ID 꼴·지시서에 없는 요구 ID) 거부, 버전 1 입력·사본 읽기를 고정한다. `planningChain`은 `drift`가 있으면 어느 action 이든 `next` 줄 끝에 채택 여부를 사용자에게 알리라는 문장이 붙는 것을 본다.

### 쉬는 메인 깨우기의 기반

Claude Code 2.1.312 바이너리에서 hook 옵션 `asyncRewake`는 "백그라운드로 돌다가 exit 2 면 모델을 깨운다"이다. asyncRewake hook 은 대화형이거나 스트리밍 입력일 때만 백그라운드로 돌고, 그 밖의 `-p`에서는 동기로 돈다. exit 2 의 stderr 는 다음 메시지로 큐에 들어간다.

임시 폴더의 프로젝트 hook 으로 스트리밍 입력 모드(`-p --input-format stream-json`, haiku, 비용 약 $0.013)를 실행했다. SubagentStop 에 15초 뒤 exit 2 로 끝나는 asyncRewake hook 을 달았다. hook 은 담당 종료를 막지 않았고, 메인이 쉬는 동안 exit 2 로 끝난 뒤 26ms 만에 메인의 새 턴이 열렸다. 첫 메시지 뒤 사용자 메시지는 없다.

- SubagentStop 입력에는 `transcript_path`·`agent_id`·`agent_type`·`agent_transcript_path`·`last_assistant_message`가 있고, 메인 대화 기록에는 `"version":"2.1.312"`가 있다. hook 환경은 `-p`·스트리밍 입력에서 `CLAUDE_CODE_ENTRYPOINT=sdk-cli`, 대화형 세션에서 `cli`다.
- `-p`와 스트리밍 입력을 hook 환경으로 가를 표지가 없다. 그래서 `wake-event`는 대화형 CLI(`cli`)에서만 기다리고 그 밖에서는 바로 0 으로 끝낸다.
- `wake-event`가 대화형 CLI 에서 실제로 메인을 깨우는 모습은 관찰하지 않았다 — 위 대화형 실행에서는 완료 알림이 새 턴을 열어 깨울 자리가 생기지 않았다.

상태 형식 세대는 22다. 외부 의존 계약 사본은 형식 2(출처·항목별 종류·요구·availability·범위 해시·의존 범위 원문·정규화 해시)이고, 답 기록의 `contract` 행은 그 항목의 의미 해시(`claimHash`)를 가지며, 커서의 영향 기록에는 외부 계약 채택(`contracts`)이 있다. 세대 21 이하의 릴리스는 형식 2 사본을 읽지 못해 계약을 미확인으로 보고 배정을 막으며, 형식 1 로 다시 쓰면 의존 범위가 사라진다. 형식 1 사본은 지금 코드가 기준 커밋으로 범위를 다시 유도해 읽고, 묶음 해시만 있는 `contract` 행은 미확인이다. 검증 증거는 테스트 수정 창 `testRepairs`와 창이 옮긴 동결 기준(`rebased.by: repair`·`repair`)을, 커서의 따르는 요구는 개정의 영향 `request.impacts`를, 리뷰 회차는 요구 변경 회차 표지(`cause: requirement`·`impact`)를 가진다. 세대 20 이하는 그 밖에도 맞지 않는다 — 영향 기록을 모르고 커서를 다시 쓰면 보안 영향 뒤 다시 검증·리뷰하라는 요구가 사라지고, 창을 모르면 열린 창의 파일 판정과 창의 받아들임이 어긋나기 때문이다. 세대 20 이하의 기록은 그대로 읽는다(창·영향이 없는 기록이다). 계획 사람 허용의 범위는 예산 구간을 담고(`planning:<작업>@<구간>`·`planning:<작업>:<입력 해시>@<구간>`), 계획 기록의 `retry`는 지금 구간 `epoch`와 지난 구간 `epochs`를 가진다. 구간을 모르는 세대 19 이하는 구간 표기가 붙은 허용을 읽지 못하고 구간 밖 배정까지 센다. 세대 19 의 기록은 첫 기록 때 지금 구간을 이행 시각(`retry.since`)부터 이어받아(`migrated`) 이행 전과 같은 사용량을 보이고, 구간 표기 없는 이전 허용은 그 이행 구간에서만 쓰인다. 담당 실행 장부(`agent-runs.json`)는 게이트·배정·승인 판정에 쓰지 않는 이어가기 안내용이라 세대에 넣지 않는다. 새 실행 회차에서 이전 형식 기록을 읽는 해석(구간 기록 없는 계획 기록은 반영 커밋 시각부터, `basis` 없는 작업의 정의 맞춤, 질문 본문 결속 전 관찰 행만 있는 답의 `delivered` 이어받기)은 기록 형식이 아닌 읽는 해석이라 세대에 넣지 않는다. 세대 13(f8c67b8)이 쓴 기록은 위 users-api 사본처럼 그대로 읽는다.

## 배포와 검증 한계

- 패키지 dry-run은 227개 파일이다. `dist/agent/agentHook.js`·`dist/agent/agentRuns.js`·`dist/agent/wakeHook.js`·`dist/agent/changeImpact.js`·`dist/agent/testRepair.js`·`dist/agent/testRepairCommand.js`·`template/claude/skills/ca-test/repair.md`를 포함하고 `dist/test`는 포함하지 않는다. 재현 시나리오와 기준선 스크립트는 이 소스 저장소에서만 실행된다.
- 예산 구간은 계획 배정(작업 총 배정)에만 있다. 검증·리뷰 회차 한도와 교차 지점 한도는 그 회차·지점에서 센다. 비용·시간 안전장치는 따로 두지 않았다 — 작업 총 배정·같은 입력 실패·동시 실행 한도, 시작·실행 기한(고아), 반복 전달 실패 차단이 그 몫이다. 예산 구간은 결정적 판정이라 실제 호스트로 따로 실행하지 않았다.
- 새 ID 로 준비한 계획 작업은 제 예산을 받는다(계획 작업 수 상한 100개). 막힌 작업은 지워지지 않고 뒤 역할의 선행으로 남아 새 ID 로 우회하지 못한다.
