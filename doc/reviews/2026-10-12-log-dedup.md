# 로그 접수 중복 판별과 재발 관리

## 범위

사용자가 로그를 직접 붙여 넣는 검증 절차다. Sentry 조직·이슈 ID를 필수로 받지 않고 프로젝트와 원문으로 접수한다. Jira 생성·조회와 배포 확인은 사람이 수행하며 CLI는 원격 상태를 검증하지 않는다. 큐·Sentry API·공용 DB는 추가하지 않았다.

## 변경

- `errorFingerprint.ts` v1은 예외·스택이 있는 로그만 자동 중복 판별한다. 이벤트·요청·추적 ID와 ISO 시각을 정규화하지만 숫자·오류 코드·스택은 보존한다. 불충분하거나 유사한 로그는 후보 비교를 요구하며 임의로 버리지 않는다.
- 최초 원문은 줄바꿈까지 보존한다. 반복 원문·발생 버전·접수 시각은 별도 파일로 보존하며 접수 횟수를 누적한다. 접수 횟수는 Sentry의 실제 발생 횟수가 아니다.
- 같은 저장소에서 중복 조회와 새 조사 예약은 한 잠금 안에서 수행한다. 기존 조사·수정·배포 대기·운영 판정은 재사용한다. 원인이 같다고 조사한 후보를 연결하면 이후 같은 로그도 원본 기록으로 연결한다.
- 후보별 비교 근거가 없거나 불확실하면 Jira 준비·연결·인계를 막는다. 명시적 재판별 사유나 수정 배포 버전의 재발은 재조사를 허용한다.
- 작업 시작·중단·로컬 반영을 판별 상태에 연결한다. 다른 개발 작업은 해당 작업의 triage 사본이 없으면 판별 기록을 열지 않는다. 로컬 반영은 배포 대기이며 배포 완료를 추정하지 않는다.
- `deployed`는 사람이 확인한 버전과 근거를 기록한다. 동일 배포 버전의 재발은 새 조사, 다른 버전이나 버전 불명은 관계 확인으로 분기한다. 버전 문자열의 대소 관계를 추측하지 않는다.
- 기존 Jira 작업 폴더는 덮어쓰지 않는다. 완료된 티켓의 재사용은 기존 작업을 확인한 후 직접 fix 절차로 재개하거나 별도 후속 티켓으로 접수한다.

## 템플릿 예산

`ca-fix/triage.md`는 사전 판별 때만 읽는 보조 문서다. 후보 비교·중복 종료·배포 확인·재발 처리 절차를 담기 위해 파일 예산을 3,400자에서 4,000자로 올렸다. 신규 스킬·에이전트나 공통 흐름 예산은 추가하지 않았다.

## 한계

중복 상태는 로컬 체크아웃에만 보존된다. 여러 PC·실행 서버에서는 공용 저장소와 원자적 예약이 필요하다. 로그 특징은 동일 원인을 수학적으로 보장하지 않으므로 새 근거가 있으면 재판별한다. 실제 cloud 서비스·Sentry·Jira 및 실제 배포 연동은 검증하지 않았다.
