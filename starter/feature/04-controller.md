# [feature 04] Controller + DTO

> **선행**: [03] 처리 계층 · **다음**: [05] 테스트
> **근거**: 참조 표준 도메인의 `controller/` `dto/`
> 이 단계는 스타터 매니페스트에서 `confirm: false` 다 — [05]·[06] 이 곧바로 검증하므로 사람 확정을 생략한다. 프로젝트가 켤 수 있다.

## 0. 사용법

참조 표준의 Controller 가 **어떤 종류가 있고**(API·화면 등) **URL 을 어떻게 짓고** **DTO 를 어떻게 나누는지**를
옮긴다. 스펙의 화면·API 정의가 있으면 그것이 목록이고, 없으면 유스케이스 목록에서 API 를 도출한다.

**do-not-touch**: `outputDirs` 밖에 파일을 만들지 않는다. 화면 템플릿·정적 자원은 이 단계 밖이다 — 필요하면 `note`.

## 1. 입력 게이트

- [ ] [03] 산출물이 실려 있다
- [ ] 스펙에 화면·API 정의가 있거나, 유스케이스 목록에서 API 가 특정된다. 둘 다 없으면 `ask`
- [ ] 참조 표준 Controller · DTO 가 실려 있다

## 2. 규칙 게이트

| 규칙 | 근거 | 위반 시 |
|---|---|---|
| Controller 의 종류·어노테이션·URL 접두어는 참조 표준과 같다 | 참조 표준 Controller | 무효 |
| DTO 의 나눔(요청/응답, 생성/수정)과 명명은 참조 표준과 같다 | 참조 표준 `dto/` | 무효 |
| DTO 의 불변성·검증 어노테이션 수준은 참조 표준을 따른다 — 더 강하게도 약하게도 하지 않는다 | 참조 표준 | 무효 |
| Controller 는 [03] 의 처리 단위만 부른다. Repository 를 직접 부르지 않는다 | 참조 표준 배선 | 무효 |
| 스펙에 없는 API 를 만들지 않는다 | 스펙 | 무효 |

## 3. 작업 — 스켈레톤

1. 참조 표준 Controller 하나를 골라 클래스 선언·공통 어노테이션·URL 접두어 규칙을 그대로 가져온다
2. 스펙의 API 마다 메서드 하나. HTTP 메서드·경로 규칙은 참조 표준의 같은 성격 API 를 따른다
3. DTO 는 참조 표준의 나눔대로 만든다. 필드는 [01] 엔티티와 스펙의 화면·API 정의에서 온다
4. 참조 표준에 없는 응답 형태·에러 매핑이 필요하면 만들지 말고 `ask`

## 4. 자가검증 체크리스트

- [ ] 만든 파일이 계획의 목록과 같은가
- [ ] 모든 API 가 스펙의 항목 하나로 되짚어지는가
- [ ] URL·어노테이션·DTO 명명이 참조 표준과 같은 규칙인가
- [ ] Controller 가 처리 계층 외의 것을 주입받지 않는가
