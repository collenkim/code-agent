# 외부 의존 계약 인계와 재인용

선행 프로젝트의 확인된 계약을 계획 담당에게 전달할 때 사용한다. 계약은 근거 자료이며 사람 답·요구 확정·계획 승인·master 위임 권한을 대신하지 않는다. 등록된 자료가 없으면 기존 입력 범위와 질문 절차를 따른다.

## 등록

진행 중인 작업의 계획 단계에서 실행 중 배정이 없을 때 `code-agent planning contracts <계약.json>`을 실행한다. 입력 JSON은 다음 형태다. 경로는 정확한 파일 하나이며 디렉터리·와일드카드·저장소 전체 탐색을 받지 않는다.

```json
{
  "version": 2,
  "contracts": [{
    "id": "auth-jwt",
    "repository": "C:/projects/authorization-api",
    "path": "doc/contracts/jwt-jwks.md",
    "commit": "40자리 소문자 Git 커밋 SHA",
    "sha256": "그 커밋 blob 바이트의 64자리 소문자 SHA256",
    "claims": [
      { "key": "jwt.service-path", "kind": "jwt-claim", "requirements": ["R2"],
        "text": "| service-api | `/api/**` | 공간 소유 업무 경로는 `workspace_id` 클레임이 필요하다. 없으면 403 `WORKSPACE_CONTEXT_REQUIRED` |" },
      { "key": "jwt.verify", "kind": "auth", "section": "공통 검증 기준", "requirements": ["R1"],
        "text": "| `iss` | `JWT_ISSUER` 와 정확히 일치 |" },
      { "key": "jwt.workspace-issue", "kind": "jwt-claim", "requirements": ["R2"], "availability": "pending",
        "text": "| 클레임 | `workspace_id` | 현재 작업공간 PK 의 숫자 ID 표현 |" }
    ]
  }]
}
```

- `repository`는 로컬 Git 저장소 루트의 절대 경로다. `path`는 그 안의 일반 파일이다. 경로 탈출·커밋의 심볼릭 링크·하위 모듈을 거부한다.
- 계약 원문은 `commit`의 blob이다. `sha256`은 `git show <commit>:<path>` 바이트의 해시다. 제공 저장소의 작업 트리와 이후 커밋은 채택된 계약이 아니라서 판정·해시에 쓰지 않는다(아래 「새 계약 채택」). 네트워크 조회·checkout·원본 파일 변경은 하지 않는다.
- 계약은 최대 20개, 계약별 항목은 최대 40개다. 입력·기준 원문·저장된 묶음은 각각 131072바이트 이하 UTF8 텍스트다. 큰 소스 대신 작고 명확한 커밋된 계약 문서를 인계한다.

항목(`claims`)의 필드는 다음과 같다.

| 필드 | 뜻 |
| --- | --- |
| `key` | 저장소들을 통틀어 같은 사실을 가리키는 이름이다. 같은 키의 서로 다른 값과 중복 계약 ID를 거부한다 |
| `kind` | `api`·`header`·`jwt-claim`·`auth`·`config`·`data`·`other`. `jwt-claim`·`auth`는 보안 계약이다. 항목 줄에 권한·인증·토큰·데이터 계약 같은 보안 낱말이 있어도 보안 계약으로 본다 |
| `text` | 원문의 한 줄과 앞뒤 공백·표기 차이를 빼고 정확히 같아야 한다. 새 요약·추론을 인증하지 않는다 |
| `section` | 선택. 원문의 ATX 제목(`#`~`######`) 글이다. 있으면 그 섹션 전체(다음 같은·상위 수준 제목 전까지)가 의존 범위이고 `text`는 그 섹션 안의 줄이어야 한다. 같은 제목이 둘 이상이면 거부한다 |
| `requirements` | 선택. 이 항목에 기대는 요구 ID(`R<n>`·`REQ-<n>`·`DONE-<n>`·`CON-<n>`)다. 확정 지시서·`01-requirements.md`에 없는 ID는 거부한다(01이 아직 없으면 `R`은 대조하지 않는다). 없으면 모든 계획 작업이 이 항목에 기댄다 |
| `availability` | `provided`(기본)·`pending`. `pending`은 제공 저장소에 아직 구현되지 않은 기능이다(「외부 의존 대기」) |

의존 범위는 지정한 섹션 전체와 상위 제목이다. section을 생략하면 항목이 속한 가장 가까운 제목의 직접 본문(다음 제목 전까지)과 상위 제목을 묶는다. 제목 앞의 항목은 빈 줄로 구분한 문단을 묶는다. 따라서 필수 절에서 선택 절로 옮긴 같은 문장도 변경이다. 같은 원문 줄이 여러 번 나오면 고유한 section으로 범위를 정해야 한다. 사본은 버전 3으로 기록한다. 버전 2 사본은 저장 당시 범위의 무결성을 확인한 뒤 커밋 원문에서 현재 문맥 범위를 계산하며, 조회만으로 파일을 다시 쓰지 않는다. 범위의 글은 비교·해시 전에 표기 차이를 지운다 — BOM, 줄바꿈(CRLF·CR), 줄 끝 공백, 끝의 빈 줄, 유니코드 조합(NFC). 그 밖의 글자 차이는 모두 의미 있는 변경이다. 범위 밖 줄은 판정에 쓰지 않는다.

버전 1 입력(항목에 `key`·`text`만)도 받는다. 종류 `other`, 요구 연결 없음(모든 작업이 기댄다), `provided`로 읽는다.

검증 후 `.code-agent/work/<ID>/dependency-contracts.json`에 출처, 항목별 범위 해시, 의존 범위 원문, 기준 원문의 정규화 해시를 원자 기록한다. 이 파일은 반영 대상이며 동의 스냅샷에도 포함된다. 모든 계획 담당의 `inputs`에 사본을 연결하고, 배정의 `externalContracts`에는 그 작업이 기대는 항목만 싣는다. 담당은 사본만 읽으며 원본 저장소를 추가 탐색하지 않는다. 등록 명령은 기존 묶음을 전체 교체하고 실행 중 배정에서는 거부한다.

## 작업이 기대는 항목과 다시 판정

계획 작업마다 기대는 항목을 고른다.

- `requirements`가 없는 항목은 모든 작업이 기댄다.
- 있으면 작업의 요구와 겹칠 때 기댄다. `R`끼리는 직접 비교한다(같은 접수 항목에서 나온 다른 `R`은 다른 요구다). `R`과 접수 항목 ID는 01의 `출처:`로 잇고, 출처를 모르면 겹친다고 본다. 항목의 `R`이 01에 없으면(01이 생기기 전에 등록했거나 개정으로 사라졌다) 모든 작업과 겹친다고 본다.
- `R`은 analysis가 정하므로 `R`에만 연결된 항목은 analysis가 기대지 않는다.
- 보안 항목은 요구 연결과 무관하게 design·plan·critic이 언제나 기댄다.

계획 작업의 입력 해시는 기대는 항목의 의미 해시(계약 ID·키·종류·요구·availability·항목 줄·섹션·범위 글)만 묶는다. 사본 파일의 바이트·기준 커밋·경로는 묶지 않는다. 그래서 범위 밖 글·표기·기준 커밋만 바뀐 재등록은 어떤 작업도 낡게 하지 않고, 기대지 않는 항목만 바뀐 작업도 그대로다. 바뀐 항목은 낡은 이유에 `외부 의존 계약 항목: <계약ID>/<키>`로 보인다. 승인 문서 해시는 모든 항목의 의미 해시 묶음이라 바뀐 항목이 있을 때만 승인이 무효가 된다.

계획 입력 판정·답 출처 판정·승인 해시는 사본을 기준 커밋의 blob과 다시 대조한다. 기준 커밋·파일을 읽지 못하거나 사본이 원문과 다르면 미확인이다. 미확인은 계약이 있는 모든 작업의 결과를 낡게 하고 배정을 막으며 승인을 무효로 한다. 계약이 없는 작업의 해시·답 출처는 그대로다.

## 새 계약 채택

제공 저장소의 변경은 자동으로 채택하지 않는다. `planning status`와 `planning advance`의 `contracts`가 제공 저장소의 지금 상태(HEAD·작업 트리)를 기준 커밋과 범위 안에서 비교해 알린다.

- `drift` — 범위가 바뀌었거나 항목 줄이 사라진 항목이다. `where: head`는 커밋된 변경이라 그 커밋으로 다시 등록해 채택할 수 있다. `where: worktree`는 커밋되지 않은 변경이라 채택할 수 없다.
- `outOfScope` — 범위 밖만 달라진 계약이다. 갱신할 작업이 없다.
- `problems` — 제공 저장소를 읽지 못한 이유다.

알림은 배정·해시 판정에 쓰지 않는다. 메인은 사용자에게 채택 여부를 확인한다. 채택하면 그 커밋과 바뀐 항목 줄로 `planning contracts`를 다시 등록한다. 등록 출력은 다음과 같다.

- 이전 사본과 항목별로 비교한 `채택 판정 — 바뀐 항목 N(보안 M) · 그대로 K`와 기준 커밋만 바뀐 계약
- 바뀐 항목마다 추가·변경·삭제, 보안 여부, 연결된 요구
- 다시 판정할 계획 작업 — 그 작업이 기대는 항목의 의미 해시가 바뀐 것이다. 선행 결과가 바뀌면 후속 작업도 다시 돈다.

이전 사본을 검증하지 못했으면 항목별로 비교하지 않고 계약을 쓰는 작업을 모두 다시 판정한다.

바뀐 항목이 있고 이전 등록·영향받는 완료 작업·승인된 계획 파일 중 하나가 있으면, 그 영향을 요구 개정의 영향과 같은 자리(`request.impacts`)에 남긴다(`changeImpact.ts` `contractImpact`). 바뀐 항목의 요구는 01 R → 계획 Task·AC → ⑦ TC → 계획 파일로 추적한다. 보안 계약이 바뀌었거나 바뀐 글에 보안 낱말이 있으면 보안 영향이다. 요구에 연결되지 않은 항목은 범위를 입증하지 못한 것으로 본다. 검증 게이트는 이 영향 뒤의 check·test·통합 검증 실행과 리뷰 회차를 다시 요구한다. 그래서 JWT claim·인증·인가 계약을 채택하면 설계·계획·독립 검토가 다시 돌고, 승인을 다시 받으며, 구현 검증·테스트·리뷰도 다시 돈다.

## 외부 의존 대기

`availability: pending`인 항목은 제공 저장소에 아직 없는 기능이다. 배정 지침은 담당에게 구현 여부를 다시 조사하거나 묻지 말고 계약 원문을 기준으로 판단하라고 하며, 그 요구를 외부 의존 대기로 문서에 표시하게 한다. 대기 항목은 `contracts.waits`에 보인다. 배정을 막지 않으므로 독립 작업은 계속한다. 기능이 제공되면 `provided`로 다시 등록한다. 그 항목의 의미 해시가 바뀌므로 그 항목에 기대는 작업이 다시 판정된다.

## 질문에 기존 계약 재인용

`code-agent planning reuse-answer Q1 auth-jwt jwt.service-path`는 답이 없는 단일 질문에 확인된 항목 원문을 기록한다. 이미 답했거나 보류한 질문은 덮어쓰지 않는다. 질문 본문·답·그 항목의 의미 해시를 `answers.jsonl`의 `contract` 행에 결속하고 `[Source]: 기존 계약 auth-jwt jwt.service-path`로 표시한다. 그 항목이 그대로인 재등록(기준 커밋·범위 밖 글·다른 항목만 바뀜)은 재인용을 유지한다. 그 항목이 바뀌면 미확인이다. 항목 해시 없이 묶음 해시만 기록된 행도 미확인이다.

출처 `contract`는 `conversation`·`observed`·`intake`·`delegated`·`relayed`와 별개다. 확인 화면에 **기존 계약 재인용 — 사람 응답 아님**으로 나타난다. Source 문자열만 적으면 미확인이다. 질문·답·근거·기록이 다르면 열린 질문으로 취급한다. Source를 대화로 바꾸어 검증 실패를 숨길 수 없다. 이후 실제로 관찰한 사람 답이나 권한 있는 master 답은 기존 경로로 처리한다.

코드는 같은 키의 값 충돌과 원문 동일성을 확인한다. 서로 다른 키나 자연어 요구 사이의 의미상 모순, 해당 계약이 질문에 충분한지는 담당·독립 검토가 확인한다. 자료가 없거나 모순이 있으면 재인용하지 않고 질문한다. 임의 답을 원문과 연결한 추론으로 인증하는 기능은 없다.

## master 연동 계약

master는 확인된 선행 산출물에서 API·헤더·JWT claim·설정·오류 조건을 담은 커밋된 계약 문서를 선정하고 위 JSON을 개발 호스트에게 전달한다. `claims.key`는 같은 의미에 같은 키를 사용하고, 항목마다 종류와 기대는 요구 ID를 적는다. 개발 호스트는 작업을 시작한 뒤 첫 세부 배정 전에 등록한다. 원래 배정의 criteria를 대화 문자열로만 보내는 것은 계약 등록이 아니다.

`code-agent.master` v1의 submit·위임·사람 전달 형식은 그대로다. 상위 러너가 위 계약 JSON을 생성·전달하고 등록 명령을 연결하는 것은 master 쪽 구현 범위다. code-agent는 상위 저장소를 수정하거나 이전 실행의 증거를 재작성하지 않는다.
